## G5-C05 — Info — 100ms anti-spin floor adds latency to refresh starts even when a slot is genuinely due

**Scorecard row:**
```
| G5-C05 | Info | src/schedule.rs (anti-spin floor) | code | 100ms anti-spin floor adds latency to refresh starts even when the slot is genuinely due (no spin present) |
```

**Working description:**
The 100ms floor has two sites — `wait_until_next_step` (`startup_dns.rs:3010-3013`, startup window) and `poll_timeout` (`serving.rs:3148-3150`, serving loop). In the serving loop, `Runtime::turn` (`runtime.rs:251-273`) polls via `run_once` with the `poll_timeout()` timeout FIRST, then calls `starts_due_dns_if_idle` (`:259`), so a genuinely-due selectable slot (`wake <= now`, no active exchange) folds a `now + 100ms` floor at `serving.rs:3149` — adding up to 100ms latency to every refresh start in the common case.

The wake-guarantee defense does not justify the 100ms: a due slot must fold SOME finite value (else `poll_timeout()` returns `None` → `poll.poll(None)` blocks indefinitely on a quiet proxy, `serving.rs:1270-1279`), but `Duration::ZERO` satisfies that equally well (`earliest = Some(now)` → `deadline <= now` → `Some(Duration::ZERO)` at `:3155-3160` → exchange starts on the next turn). The floor's only genuine anti-spin purpose is the one-time post-boot probe sweep, where `starts_due_dns_if_idle` is suppressed while `sweep_active()` (`runtime.rs:297-302`) — yet the floor is applied unconditionally in the common case. The fix is a one-line condition: `sweep_active()` is a `pub(crate) const fn` on the DNS transport (`startup_dns.rs:2656-2660`) and `poll_timeout` already calls `self.storage.dns()` (`serving.rs:3125`, `:3141`), so `self.storage.dns().sweep_active()` is directly reachable — return ZERO when the slot is due and not sweeping, floor only while `sweep_active()`. No state threading required.

Severity is **Info**, not Medium: impact is negligible (100ms vs 5-900s refresh intervals, spec `:76-77`; requests never wait on DNS, spec `:63`), both floors are documented (`startup_dns.rs:2980-2985`) and the serving floor is directly tested (`serving/tests.rs:66-82` `serving_poll_timeout_folds_bounded_floor_for_idle_selectable_now_due`), and there is no spec deviation (`:146` single-owner bounded waits; hrdn2 `:390` whole-second scheduling). But the mechanism is real, reachable in the common case, and trivially fixable with no downside — a genuine (minor) over-application of the floor worth reporting at Info severity. **Spec deviation:** none. **Fix target: code** (`src/serving.rs:3148-3150` — gate the floor on `self.storage.dns().sweep_active()`; fold `Duration::ZERO` for a due slot otherwise).

## G5-C06 — Info — workspace byte-arithmetic constants have no absolute-value boundary test

**Scorecard row:**
```
| G5-C06 | Info | src/inventory.rs:15 (workspace byte arithmetic) | code (test) | Test gap: workspace byte-arithmetic constants (SLOT_WORKSPACE_BYTES) have no boundary test |
```

**Working description:**
`SLOT_WORKSPACE_BYTES` (`src/inventory.rs:18`) = `CONNECT_LIMIT + (MAX_CLIENT_HELLO * 2)` = 8 KiB + 2 × 64 KiB = 136 KiB, and `SERVING_WORKSPACE_BYTES` (`:21`) = 512 × 136 KiB = 68 MiB. The spec documents these as EXACT figures explicitly tied to these constants (alumina-mema `:449` "Retained serving workspace total | 512 slots | 136 KiB | 68 MiB"; `:451` names the constants); the "design estimate" language at `:925`/`:929` applies only to the JA4-reconciled ~152.4 KiB ≈ 76 MiB figure, not to this exact arithmetic. The constants drive real retained inline allocation (`ConnectParser.head [u8; CONNECT_LIMIT]` `connect.rs:184`; `ChInspector` buf/scratch `[u8; MAX_CLIENT_HELLO]` `client_hello.rs:346/350`; `Serving.slots: Vec<SlotWorkspace>` `serving.rs:922-944`).

Every existing test touching these constants is SELF-REFERENTIAL — it derives the expected value from the same constants on both sides: `src/boot.rs:168-174` (`report.storage.len() == TRAFFIC_STORAGE_BYTES`; `named_fixed_buffer_bytes() == TRAFFIC_STORAGE_BYTES + SERVING_WORKSPACE_BYTES + DNS_NAMED_BUFFER_BYTES`) and `tests/boot.rs:620-674` (boot inventory report assertions). No test anywhere asserts the absolute values (grep confirms no 136/68 literals in `src/` or `tests/`). A regression in `CONNECT_LIMIT` or `MAX_CLIENT_HELLO` would change real retained memory and the boot report while every test still passes and the documented `:449`/`:451` arithmetic silently drifts — precisely the doc-code drift the alumina-mema amendment exists to prevent.

The FP counter-argument (compile-time arithmetic, no overflow/behavioral risk, design-estimate figures, over-constrained golden-value testing) fails: the `:449`/`:451` figures are exact documented invariants tied to the constants, not fuzzy estimates, and the fix is a trivial two-line absolute-value boundary test (e.g. `assert_eq!(SLOT_WORKSPACE_BYTES, 136 * 1024)`; `assert_eq!(SERVING_WORKSPACE_BYTES, 68 * 1024 * 1024)`), cheap and doctrine-aligned with the existing precedent of pinning the traffic-storage allocation length at boot. **Spec deviation:** none. **Fix target: code (test)** — add an absolute-value boundary assertion for `SLOT_WORKSPACE_BYTES`/`SERVING_WORKSPACE_BYTES` in `src/inventory.rs` tests (or the boot inventory test).

## G5-C08 — Info — `select_due(u64::MAX)` DeadlineOverflow path untested

**Scorecard row:**
```
| G5-C08 | Info | src/schedule.rs (`select_due(u64::MAX)`) | code (test) | Test gap: `select_due(u64::MAX)` DeadlineOverflow path untested |
```

**Working description:**
`select_due` (`src/schedule.rs:502-531`) has exactly one error path, at `:521` `let not_before = now.checked_add(1).ok_or(ScheduleError::DeadlineOverflow)?;`, which fires only at `now == u64::MAX` (checked_add(1) overflows) and short-circuits via `?` **before** the `slot_mut` at `:522`, so no slot is mutated on error. The doc comment at `:495-496` explicitly documents this path: "Returns `DeadlineOverflow` only when the start-rate timestamp cannot be represented (at `now == u64::MAX`); no slot is changed." No test anywhere calls `select_due(u64::MAX)` — all test call sites pass 0/1/1000/1001/1005/3000 (incl. the alloc-witness test at `:1062-1063`).

The decisive precedent (4 of 5 voters): the author DID test the equally-unreachable insert-path overflow branches — `deadline_overflow_errs_without_mutation` (`:1031-1048`, `note_positive`/`note_nxdomain` with `u64::MAX - 10`) and `nxdomain_without_soa_one_family_overflow_commits_nothing` (`:954-965`, `u64::MAX - 1`) — with near-max values that are just as unreachable in practice (~584 Gyr). The codebase's own testing convention treats defensive overflow branches as worth testing; `select_due` is the only documented error path without a test, making this a genuine error-surface coverage asymmetry. A one-line test (`select_due(u64::MAX)` → `Err(DeadlineOverflow)`, asserting no slot mutated) would pin the documented no-mutation guarantee and complete the error-surface coverage at negligible cost.

Dissent (voter 3, FP): the branch is trivially correct (`checked_add(1)` on `u64::MAX` → `None` is a tautology) and the no-mutation guarantee is structural (the `?` precedes `slot_mut`), unlike the insert paths whose overflow tests pin a genuine two-phase-commit no-partial-application invariant that `select_due` structurally lacks. Unreachable + no behavioral protection → FP per the explicit "unreachable" criterion. This is a reasonable counter but does not outweigh the precedent argument: the codebase's own convention (testing defensive overflow branches with near-max values) makes the documented-but-untested `select_due` branch a real, if Info, coverage asymmetry. **Spec deviation:** none. **Fix target: code (test)** — one-line `select_due(u64::MAX)` no-mutation test in `src/schedule.rs`.

## G5-C09 — Info — serving-loop DNS-turn suppression guard (`sweep_active`) untested

**Scorecard row:**
```
| G5-C09 | Info | src/runtime.rs:298-300 (`sweep_active` guard) | code (test) | Test gap: serving-loop DNS-turn suppression guard (`sweep_active`/`has_active_exchange`) untested |
```

**Working description:**
The `starts_due_dns_if_idle` suppression guard (`src/runtime.rs:298-300`) is `if self.serving.storage().dns().sweep_active() || self.serving.storage().dns().has_active_exchange() { return Ok(()); }`, and its two halves have asymmetric coverage:
- `has_active_exchange()` (`src/startup_dns.rs:1288-1292`) is exercised throughout `src/runtime/tests.rs` (`:1413`, `:1447`, `:1521`, `:1610`, `:1722`, `:1764`, `:1825`) — asserting a due refresh starts when the transport is idle.
- `sweep_active()` (`src/startup_dns.rs:2656-2660`) has ZERO serving-loop coverage. `src/runtime/tests.rs` has no sweep/probe_sweep match at all; `src/serving/tests.rs` "sweep" hits are all `expire_sweep` (slot-deadline sweep), not the DNS probe sweep. The only `sweep_active()` tests are transport/unit-level in `src/startup_dns/tests.rs` (`:2404-2581`, `:2833-2837`), which exercise the sweep state machine in isolation — never the serving-loop deferral interaction.

The runtime harness structurally makes the state unreachable: it uses a single-resolver config (`resolver = ["1.1.1.1"]`, `src/runtime/tests.rs:12`), and `maybe_begin_sweep` short-circuits for single-resolver sets (`src/startup_dns.rs:2641-2643`; pinned by `probe_sweep_does_not_begin_for_single_resolver_set`). So no test drives the documented corruption-prevention interaction: `turn()` runs `step_sweep()` (`:258`) then `starts_due_dns_if_idle()` (`:259`), and the doc comment (`:290-296`) states an interleaved refresh would corrupt the sweep's restore of the pre-sweep active resolver. That invariant is real, documented, and unpinned at the serving-loop level.

All five voters independently confirmed the asymmetry, the single-resolver harness short-circuit, and the missing deferral test. The FP arguments (trivial 2-line boolean, transport-level sweep coverage, `sweep_ran`-provable boundedness at `src/startup_dns.rs:2635`/`:2711`, boot-time-only transient event) were weighed and found to argue low priority, not unreality — the codebase's own convention tests suppression branches exhaustively, and the `has_active_exchange()` half of the SAME guard is already tested at runtime level. **Spec deviation:** none. **Fix target: code (test)** — add a runtime/serving-loop test that drives a multi-resolver set through the completed window into an active probe sweep and asserts a due refresh is deferred until the sweep restores the pre-sweep resolver (and that suppression terminates via `sweep_ran`).
