## G8-C17 — Info — `linux_dispatch` mounts the host checkout read-write as root; root-owned artifacts left in host tree

**Scorecard row:**
```
| G8-C17 | Info | scripts/verify.sh:915-921 (`linux_dispatch`) | code | Container mounts host repo read-write (`:Z`) with no `--user`, runs as root → `target/` artifacts created root-owned in the host checkout; container has write access to the entire checkout; `:Z` SELinux relabel can surprise on some hosts; fix: `--user "$(id -u):$(id -g)"` and/or mount build output separately with source read-only |
```

**Working description:**
`linux_dispatch` (`scripts/verify.sh:915-921`) runs `podman --connection flock-vm run --rm --pull=never -v "$ROOT:/app:Z" ... "$IMAGE" sh -c "$prov$inner"` — the entire host checkout is mounted read-write (`:Z`) with no `--user`, so the container runs as root (rust image default user) and cargo build writes `target/` artifacts as root into the host checkout after every `boundary phase1` run. The container has write access to the entire checkout, not just `target/`. `:Z` is the SELinux relabel option (host-specific surprise on SELinux hosts; no-op on macOS + podman VM).

Decisive repo-internal inconsistency (all five voters): this is the ONLY read-write checkout mount in the file — `verify.sh:330` uses `-v "$ROOT:/app:ro,Z"` and `:548` uses `-v "$ROOT:/app:ro,Z" --user 0:0`. `linux_dispatch` (`:916`) is the sole exception: read-write mount AND no `--user`, while the repo's own conventions elsewhere are deliberately read-only with an explicit user. The container runs trusted repo code (not untrusted input), so there is no security impact — the finding is operational hygiene: the host user cannot `git clean -fdx` or rebuild without sudo after a run, and the container has broader-than-needed write surface. **Spec deviation:** none. **Fix target: code** — add `--user "$(id -u):$(id -g)"` to the `linux_dispatch` podman run (`:915`) and/or mount the source read-only (`:ro,Z`) with build output on a separate volume, matching the repo's own conventions at `:330` and `:548`.

## G8-C18 — Info — toolchain declared in three places; bump silently drifts the container path

**Scorecard row:**
```
| G8-C18 | Info | scripts/verify.sh:15, :277, :1101; rust-toolchain.toml:2 | code | Toolchain version declared in three places: `rust-toolchain.toml:2` (authoritative) + hardcoded literals `verify.sh:15` (`TOOLCHAIN="1.99.0"`), `:277` and `:1101` (`cargo +1.99.0` inside container strings); a bump would silently drift the two container strings from `TOOLCHAIN` and from the repo pin; fix: thread `TOOLCHAIN` into `linux_dispatch` strings for a single source of truth |
```

**Working description:**
The toolchain version is declared in three places: `rust-toolchain.toml:2` (`channel = "1.99.0"`, authoritative) plus hardcoded literals `verify.sh:15` (`TOOLCHAIN="1.99.0"`) and the container strings `:277` (single-quoted) and `:1101` (double-quoted) which hardcode `+1.99.0`. `linux_dispatch` (`:897-926`) passes only CARGO_HOME/CARGO_INCREMENTAL/CARGO_TERM_PROGRESS_WHEN in its `-e` list (`:917-919`) — `TOOLCHAIN` is NOT exported into the container; the inner `sh -c "$prov$inner"` runs with the caller's already-expanded string. A toolchain bump would silently drift the two container strings from `TOOLCHAIN` and from the repo pin. The single-quote trap makes the fix non-trivial: `:277` is single-quoted, so a naive `+${TOOLCHAIN}` substitution there would NOT host-expand and the container has no `TOOLCHAIN` env → `cargo +` (empty) fails; `:1101` (double-quoted) would host-expand correctly. Robust fix: thread `-e TOOLCHAIN=...` into the container and use `+${TOOLCHAIN}` in both strings (or unify quoting). No gate asserts `rust-toolchain.toml` channel equals `$TOOLCHAIN`; the identity snapshot records both inputs but never compares them, so drift is silent.

All five voters voted TP unanimously at Info (all three agree at 1.99.0 today; no current functional bug). **Spec deviation:** none (spec silent on toolchain declaration). **Fix target: code** (`scripts/verify.sh` — thread `TOOLCHAIN` into `linux_dispatch` strings for a single source of truth).
