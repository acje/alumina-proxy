## G4-C01 — Info — allowlist dedup key is bare hostname only, excludes port

**Scorecard row:**
```
| G4-C01 | Medium→Info | src/config.rs:899-908 | code | Allowlist dedup key is bare normalized hostname only, excludes port → same hostname on two ports (e.g. `api.github.com:443` + `:8443`) rejected as `DuplicateAllowlistName`; spec :19/:41 entry identity includes port. Fail-closed (exit 78), functional data-model limitation |
```

**Working description:**
All five voters verified the code facts — `build_allowlist` (`config.rs:899-908`)
dedups on the bare hostname only (`fqdn.as_str().to_owned()`, `:904`, port
excluded after `Fqdn::parse` splits on `rsplit_once(':')`), so
`api.github.com:443` + `api.github.com:8443` collide as
`DuplicateAllowlistName` (exit 78); while the runtime `allowlist_position`
(`config.rs:394-401`) matches hostname AND port — the `<fqdn>:<port>` pair is
the runtime identity. Spec `:19`/`:41`/`:54` consistently define the entry as
an exact `<fqdn>:<port>` pair and nowhere forbid the same hostname on two
ports. The split (3 TP / 2 FP) turns on whether the behavior is a genuine gap
or deliberate/spec-faithful: the two FPs note the dedup is test-pinned
(`tests/boot.rs:230-237` "the same FQDN at a second port is a duplicate") and
read spec `:58` "Reject duplicate allowlist names after normalization" with the
FQDN as the "name". The majority (3) found the runtime/spec pair-identity
inconsistency genuine enough to report: the config layer cannot express what
the runtime data model and spec entry identity support. Fail-closed (exit 78,
no bypass) → severity **Info** at aggregation (not the claimed Medium).
**Spec deviation:** yes — spec entry identity includes port; config layer
cannot express same-hostname-two-ports. **Fix target: code** (dedup on the
full `<fqdn>:<port>` pair) — note the behavior is test-pinned and arguably
spec-faithful, so this is a borderline expressiveness finding.

## G4-C02 — Info — single-label allowlist entry widens bailiwick to whole TLD

**Scorecard row:**
```
| G4-C02 | Medium→Info | src/config.rs:27-63, :175-198; src/dns.rs:799-810, :833-841, :1193-1203 | code\|spec | Single-label allowlist entry (e.g. `com:443`) accepted (no min label count in config or runtime `FixedHostname::normalize`); `zone_of` falls through to self → whole-TLD bailiwick, widening CNAME-acceptance surface; spec :540 defines only >2-label and 2-label cases |
```

**Working description:**
All five voters verified the code facts — `Fqdn::parse` (`config.rs:27-63`) and
`FixedHostname::normalize` (`config.rs:175-198`) impose no minimum label count,
so a single-label allowlist entry like `com:443` is accepted; `zone_of`
(`dns.rs:833-841`) returns the name itself for ≤2 labels, so a single-label
entry makes the entire TLD the bailiwick zone; `BailiwickZones::from_allowlist`/
`covers`/`soa_covers` (`dns.rs:799-810`, `:1193-1203`) then accept any
label-boundary subdomain within it. Spec `:540` (Vec 11) defines zone
derivation for only two cases — ">2 labels → parent domain" and "2-label apex →
itself" — and `:54`/`:61` impose no minimum label count, so the single-label
case is a genuine, reachable underspecification that widens the CNAME-acceptance
surface to the whole TLD. All voters downgrade severity to **Info** at
aggregation (not the claimed Medium): the whole-TLD bailiwick is the natural
generalization of the 2-label apex rule, single-label entries are degenerate
(TLDs don't resolve), and impact requires a degenerate operator config plus a
compromised resolver. **Spec deviation:** yes — `:540` underspecifies the
single-label case. **Fix target: spec** (define the single-label case) **or
code** (reject single-label entries / require ≥2 labels). Strongest G4
candidate.

## G4-C03 — Info — config vs resolver FQDN grammar divergence (all-numeric final label)

**Scorecard row:**
```
| G4-C03 | Info | src/config.rs:27-63, :112-116 vs src/resolver.rs:72-78 | code | Grammar divergence: config `Fqdn::parse` accepts all-numeric final label (`dns.123`), resolver `Fqdn::parse` rejects it; spec :626 "matches the allowlist label rule" claim inaccurate; config ⊋ resolver name sets |
```

**Working description:**
All five voters verified the grammar divergence — config `Fqdn::parse`
(`config.rs:27-63`) accepts an all-numeric final label like `dns.123` (its only
IP-shape rejection `is_ip_literal_shape`, `config.rs:112-116`, requires a digit
FIRST byte AND all bytes digits/dots, so `dns.123` passes), while resolver
`Fqdn::parse` (`resolver.rs:72-78`) rejects any name whose FINAL label is
all-numeric (`value.rsplit('.').next()` all digits → `FqdnError::Invalid`;
pinned by a resolver test). Config ⊋ resolver name sets. Spec `:626` (V37)
claims the resolver FQDN rule "matches the allowlist `config::Fqdn` label rule"
— accurate only for the digit-leading-label sentence; the resolver's stricter
all-numeric-final-label rule is documented nowhere in the byte-canonical spec
nor the resolver's own doc comment. **Spec deviation:** yes — `:626` parity
claim inaccurate. **Fix target: code** (align the two parsers) **or spec**
(document the resolver's stricter rule). Both surfaces fail closed; no security
impact.

```
| G4-C07 | Info | docs/alumina-proxy.md:62 | spec | Body clause stale: still reads "read the platform-provided resolver configuration… first declared nameserver, port 53"; hrdn4/V37 moved source into validated TOML `resolver` array, deleted resolv.conf reader. Docs drift, amendments authoritative |
```

**Working description:**
All five voters verified the claim. The spec body clause at
`docs/alumina-proxy.md:62` still reads "**Resolver selection:** Read the
platform-provided resolver configuration once at startup and select its first
declared nameserver address, using port 53" — describing the pre-hrdn4/V37

`config.rs:420-422` "Sourced from the config document, never from a platform
resolver file"; `boot.rs:72` "no separate platform resolver file is read").
The hrdn4 and V37 amendments are recorded and authoritative, but the `:62` body
clause was never corrected. Decisive: the repo's own amendment practice edits
body clauses in-place (precedent 6c1f40e, alumina-5sx, edited 2s→5s at
`:82`/`:176`), and the hrdn4 amendment explicitly enumerates `:62` as an
amended surface yet left it untouched — so this is genuine docs drift deviating
from the repo's own amendment practice, not deliberate immutable-body design. A
reader of the primary normative body text is misled about how the resolver is
selected. **Spec deviation:** yes — `:62` body clause stale vs hrdn4/V37.
**Fix target: spec** (corrective amendment is the sanctioned fix path).
