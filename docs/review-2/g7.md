## G7-C01 — Medium — DoT warm path has zero alloc-witness coverage; spec `:235` verification mandate undischarged

**Scorecard row:**
```
| G7-C01 | Medium | src/runtime/tests.rs:1771-1855; src/startup_dns/tests.rs:1145-1151; src/alloc.rs:130-172 | code (test) | Warm DoT path has no alloc-witness coverage: every `run_phase` site avoids DoT (bare-IP configs / plain-TCP responders); rustls 0.23.46 warm-path per-record allocs (≤~16-18 KiB, spec :795) documented as bounded seam but never measured/asserted — the `alumina-dotrt` serving-lifetime warm-reuse path is never mechanically verified for first-party zero allocation; spec :235 verification not discharged for DoT serving-refresh |
```

**Working description:**
All five voters verified the DoT (DNS-over-TLS) path has zero alloc-witness coverage and that this is a genuine verification gap, not a design deviation.

Verified facts:
- Spec `docs/alumina-proxy.md:235` (Resource profile verification) explicitly mandates: "Use allocator instrumentation and dependency checks to verify that startup DNS resolution, serving, background refresh, logging, and shutdown perform no heap allocation or deallocation after boot initialization."
- `src/startup_dns/dot_tests.rs` (the DoT test module, ~794 lines) has ZERO `run_phase`/alloc-witness usage. Its only alloc-adjacent assertion is the structural pointer-identity reuse check at `:788-791` ("the serving refresh must reuse the same rustls client allocation, not rebuild it") — that is a structural assertion, NOT an allocator measurement, and cannot detect a first-party heap allocation in the refresh state machine.
- `src/startup_dns/tests.rs:1145-1151` — the boot-window allocation witness explicitly documents its own limit: it qualifies the boot alloc-zero claim "for a plain-DNS (bare-IP) resolver only"; `config()`'s `resolver = ["1.1.1.1"]` keeps `upgrade_to_tls` unreachable, so a DoT-configured boot (which allocates in-window via the documented rustls bounded seam) is NOT covered.
- All 36 `run_phase` call sites across dns.rs, schedule.rs, worker.rs, log.rs, startup_dns/tests.rs, client_hello.rs, cache.rs, runtime/tests.rs, serving/tests.rs, serve.rs use bare-IP configs or plain-TCP responders — none exercise the DoT TLS path.
- The rustls 0.23.46 warm-path per-record alloc bound (≤~16-18 KiB, spec `:795`) is documented as a bounded seam but never measured or asserted by any test.
- Spec `:747` (alumina-dotrt) makes the serving-lifetime warm-reuse path a real, user-authorized feature; spec `:795` makes a first-party, in-scope claim that retained-transport serving refresh "allocates nothing" — but this is never mechanically verified.

Why TP (not FP): the ZAI first-party scope (`:793`) and the spec-blessed rustls seam (`:795`) address CONFORMANCE, not the missing VERIFICATION EVIDENCE. The codebase's own test comments record the gap ("does not cover a DoT-configured boot") — they document it, they do not authorize it. A first-party allocation regression in the DoT serving-refresh state machine (refresh/repoint/exchange over the retained warm connection) would go undetected, silently violating the fixed-profile ZAI (`:211`). The right fix is a seam-aware witness over a DoT warm exchange (e.g., an event-count/bound assertion calibrated to the documented per-record seam rather than all_zero), plus optionally an assertion that the rustls seam stays within the documented ≤~16-18 KiB bound. **Spec deviation:** none (the spec is not violated; its verification requirement is simply not discharged for this path). **Fix target: code (test)**.

## G7-C02 — Info — ungated heap-allocating `fault` harness ships in the fixed-profile production binary

**Scorecard row:**
```
| G7-C02 | Info | src/fault.rs:118-131; src/lib.rs:10 | code | `fault.rs` heap-allocating fault-injection harness (`BTreeMap<String, Vec<Outcome>>`, `to_owned()`, `clone()`) compiled into production binary via ungated `pub mod fault;`; dead in prod (no production caller), so no runtime alloc occurs — latent invariant site + ships alloc-capable code in a fixed-profile binary; gate `#[cfg(test)]`/feature |
```

**Working description:**
All five voters verified the `fault` fault-injection harness is compiled into the production binary via an ungated `pub mod fault;`, is dead at runtime (zero production callers), and is a genuine latent allocation site in a project whose identity is the fixed memory profile. The finding is honest (Info severity, concedes no runtime allocation) and the fix is trivial and unambiguously correct.

Verified facts:
- `src/lib.rs:10` — `pub mod fault;` is UNGATED (no `#[cfg(test)]`, no feature gate). The module is part of the public lib API, so it is compiled into the lib and linked into the production binary.
- `src/fault.rs` — heap-allocating structures: `Script { id: String, points: BTreeMap<String, Vec<Outcome>> }` (`:63-66`), `Outcome::Data { bytes: Vec<u8> }` (`:37`), `Clock { Vec<u64> }` (`:141`), `Replay::next` does `point.to_owned()` (`:124`) and `outcomes[index].clone()` (`:125`). No `#[cfg(...)]` gates anywhere in the file.
- Callers: the ONLY references to the `fault` module are `tests/foundations.rs:3,141` (an integration test). Zero production callers in `src/` (grep confirmed). `src/inventory.rs:84/202/207` references the separate, feature-gated `alloc_fault` module (gated `#[cfg(test)] mod alloc_fault` at `src/inventory.rs:210-211`) — the project's own precedent for gating exactly this kind of machinery.
- Spec `docs/alumina-proxy.md:211` (ZAI) is a runtime invariant ("While serving traffic or refreshing DNS, first-party proxy execution paths must not allocate or deallocate heap storage"). The `fault` module is not on any serving/DNS path, so no runtime allocation occurs today.

Why TP (not FP): the ZAI is runtime-scoped, so dead code does not currently allocate — but the finding is not a runtime violation; it is a latent invariant site plus a code-hygiene gap. In a project whose entire identity is the fixed no-alloc memory profile, shipping an alloc-capable fault-injection harness as ungated public API in the production binary means any future production caller would silently allocate, violating the ZAI. Gating `#[cfg(test)]` structurally makes the harness uncallable from production ("make illegal states unrepresentable", fleet Priority 2), and matches the repo's own `alloc_fault` gating precedent. The FP "unreachable" criterion does not apply cleanly: the finding is about binary composition and latent risk, not a claimed effect in unreachable code. **Spec deviation:** none (spec not violated; the harness is simply not on any runtime path). **Fix target: code** (gate `#[cfg(test)]` or a feature).

## G7-C05 — Medium — composed serving owner-loop path never alloc-witnessed under Phase::Serving

**Scorecard row:**
```
| G7-C05 | Medium | src/runtime/tests.rs:134-331 (hot_relay_many_slots_body), :241-271 | code (test) | Composed serving path — the integration owner-loop `Runtime::turn` with concurrent relays, DNS advance, expired-idle closure, backlog admission — is never phase-wrapped; unit witnesses cover isolated seams only (worker admit/select, monitor report/drain, logging, ClientHello, background refresh); a first-party allocation anywhere in the composed relay/CONNECT/ClientHello/DNS loop would go unmeasured; coverage gap against :235 |
```

**Working description:**
All five voters verified that `hot_relay_many_slots_body` (`src/runtime/tests.rs:134-331`) is the only composed serving integration test — a real `Runtime` running `turn()` in a loop over 17 hot relays + expired-idle sweep + stalled DNS advance + 4-deep accept backlog — and its turn loop (`:241-271`) is never phase-wrapped. All 36 `run_phase` sites in the repo cover isolated seams only; `Runtime::turn`'s own glue (mio poll, event dispatch, relay I/O, DNS advance, deadline sweep, backlog admission) is unmeasured under Phase::Serving.

Verified facts:
- Spec `docs/alumina-proxy.md:235` — "Use allocator instrumentation and dependency checks to verify that startup DNS resolution, serving, background refresh, logging, and shutdown perform no heap allocation or deallocation after boot initialization." "Serving" is an explicit, separately-listed phase.
- `hot_relay_many_slots_body` (`src/runtime/tests.rs:134-331`): boots real `Runtime`, installs 17 hot relays + 1 expired-idle relay + stalled DNS exchange + 4-connection accept backlog, drives `runtime.turn(Some(2ms))` in a loop (`:241-271`) asserting DNS advance bound, expired-idle closure, backlog admission, byte-exact relay completion, second-visit starvation bound, and timer/DNS recheck high-water. NO `run_phase` wrapper anywhere in the function or around the turn loop.
- `Runtime::turn` (`src/runtime.rs:251-273`) composes `Serving::run_once` (poll + event dispatch + relay I/O + backlog admission), `expire_sweep`, `cooperative_dns_turn`/`advance_dns`, `sync_dns_shared`, `report_monitor_if_due`, `drain_sink` — none alloc-witnessed under Phase::Serving.
- All 36 `run_phase` sites are isolated seams: `worker.rs:1861-1879` (admit/select), `serve.rs:1243-1298` (serving/logging seams), `serving/tests.rs:4174` (Shutdown) + `:5358,:5417,:5458,:5508,:6611,:6914` (Serving unit seams), `client_hello.rs:2050` (parse), schedule.rs/cache.rs/dns.rs (BackgroundRefresh), `startup_dns/tests.rs:1156,1177` (StartupDns boot), log.rs (Logging), `runtime/tests.rs:1811` (BackgroundRefresh).
- The strongest counter-evidence, `refresh_alloc_witness_body` (`runtime/tests.rs:1783-1855`), DOES wrap real `turn()` calls and asserts `counts.all_zero()`, but attributes the whole turn to `Phase::BackgroundRefresh` (not `Serving`, which `:235` lists separately) and runs with no concurrent relay traffic — so the composed relay/DNS/deadline/backlog path remains unmeasured.
- The `serving/tests.rs:4174` Shutdown witness wraps a composed `turn_pump` but runs in draining, where the doc comment at `runtime.rs:243-245` says the cooperative DNS turn is skipped — it cannot cover the Serving-phase DNS/backlog/sweep composition.
- Feasibility: the allocator instrumentation is thread-local (`src/alloc.rs:68-71`), so wrapping the owner-thread turn loop in `run_phase(Phase::Serving, ...)` would cleanly measure the owner thread despite the test's reader threads; the `:1811` refresh witness proves this exact fix is precedented.

Why TP (not FP): the "composition of alloc-free seams is alloc-free" counterargument fails because the turn-loop glue in `run_once`/`turn` itself is first-party code that no seam witness covers; the reader-thread concurrency objection fails because the thread-local witness measures only the owner thread. A first-party allocation introduced anywhere in the composed Serving-phase turn glue would go unmeasured, directly violating the `:235` mandate. Same class as G7-C01 (KEPT 5TP/0FP). **Spec deviation:** none (a test-coverage gap, not a spec deviation). **Fix target: code (test)** — wrap the `hot_relay_many_slots_body` turn loop in `alloc::run_phase(Phase::Serving, ...)` and assert `counts.all_zero()`.

## G7-C10 — Medium — `measure` silently drops allocations when `CURRENT_PHASE` is `None`; ZAI witness fails open

**Scorecard row:**
```
| G7-C10 | Medium | src/alloc.rs:73-77 | code | `measure` silently drops every allocation when `CURRENT_PHASE` is `None` (early return): any serving-loop path not wrapped in `run_phase` escapes detection entirely and can never fail a zero-allocation assertion; verification blind spot (phase-dimension — distinct from G7-C04 thread-dimension) weakening :235 mechanical verification; fix: fail/log on allocation with no active phase |
```

**Working description:**
All five voters independently confirmed the mechanical premise: `measure` (`src/alloc.rs:73-77`) early-returns and silently drops every `Event` when `CURRENT_PHASE` is `None` (`let Some(phase) = phase else { return; }`). Because `Counting` (`src/alloc.rs:130-172`) calls `measure(Event::*)` on every `alloc` (`:137`), `dealloc` (`:151`), and `realloc` (`:165`), EVERY heap allocation on the measured thread passes through `measure` — and any allocation occurring outside an active `run_phase` (`src/alloc.rs:97-111`, the only writer of `Some(phase)`) is invisible to the witness and can never fail `counts.all_zero()`.

Why TP (5 of 5):
- **Fails OPEN on the central invariant.** This is the dangerous direction, opposite to discarded G7-C07 (over-reporting, fails closed). A first-party allocation regression on an unwrapped serving/DNS-refresh path produces a false negative: every `counts.all_zero()` witness passes while the ZAI (spec `:211`) is violated. Under-reporting on the ZAI is more serious than over-reporting because a regression can slip through the entire suite.
- **Not spec-excluded.** The phase dimension concerns the single measured thread (spec `:144`/`:159` single-threaded profile), so it is squarely in scope — unlike G7-C04's thread dimension (no other threads in the serving profile, DISCARDED 5FP/0TP). Spec `:235` mandates mechanical verification that serving/DNS-refresh perform no heap allocation; unwrapped paths on the measured thread are unverified against that mandate.
- **Concrete instance (G7-C05, KEPT).** The composed serving loop `hot_relay_many_slots_body` (`src/runtime/tests.rs:134-331`) drives `Runtime::turn` (`src/runtime.rs:251-273`) → `run_once`/`step_sweep`/`cooperative_dns_turn`/`sync_dns_shared`/`report_monitor_if_due`/`drain_sink` with no `run_phase` wrapper; all 36 `run_phase` call sites are `#[cfg(test)]` sub-path witnesses, never the composed serving machinery. The `:235` "serving performs no heap allocation" mandate is therefore verified per-path only, never on the real composed loop. G7-C10 is the general mechanism underlying that gap — even if C05's specific loop were wrapped, any unwrapped path would still silently escape.
- **Cheap fix seam.** `active_phase()` (`src/alloc.rs:113-116`) exposes the current phase; the fix (fail/log on no-phase allocation in the `alloc-witness` build, or wrap the composed serving loop in `run_phase(Phase::Serving, ..)` and assert `all_zero()`) is concrete and actionable.

Severity note: 4 of 5 voters affirmed Medium as defensible (a genuine verification weakness on a central invariant, not a demonstrated current violation); voter 4 argued arguably Low/Info since no current allocation is demonstrated. Majority keeps **Medium** (consistent with G7-C05, which also stayed Medium on a 4/5 split). The boot-exemption nuance (spec `:211` "Only boot initialization is exempt"; boot/test setup allocate with no active phase, so a naive global fail would false-positive) refines the fix (must distinguish exempt boot/test-setup context) but does not negate the gap — the silent drop is a choice, not a necessity. **Spec deviation:** none (verification-harness gap weakening spec `:235` mechanical verification, not a deviation from a spec clause). **Fix target: code**.
