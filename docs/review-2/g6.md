## G6-C01 — Info — `dp=` downgrade counter misses failback-begin relocation

**Scorecard row:**
```
| G6-C01 | Info | src/startup_dns.rs:2598-2604 (`maybe_begin_failback`) | code (+ spec :774) | `dp=` counter misses failback-begin relocation: `maybe_begin_failback` relocates DoT backup → bare-IP primary without `note_downgrade_if_dot_to_plain`; spec :774 scopes counter to the two `on_exchange_failed` choke points only, undercutting :770 intent "surfaces the failover downgrade path" |
```

**Working description:**
`maybe_begin_failback` (`src/startup_dns.rs:2585-2606`) relocates a non-primary backup onto `ActiveResolver::primary(...)` at `:2601` without ever calling `note_downgrade_if_dot_to_plain`. In a plain-primary + DoT-backup config, that move matches the helper's own downgrade predicate (`from_is_dot && to_is_plain`, `:2612-2626`) exactly, yet is uncounted — so `dp=` can read 0 despite a genuine DoT→plain serving relocation. The helper is called at exactly three sites (`:2700` `relocate_for_probe`, `:2757` failback re-seat, `:2769` failover relocation), none of which is failback-begin, making `maybe_begin_failback` the only one of the four relocation paths that never counts.

Spec `docs/alumina-proxy.md:774` (alumina-dotdg amendment) enumerates only the two `on_exchange_failed` choke points, but `:770` states the counter's purpose is to "surface the failover downgrade path (`dp=`)". Voters read the narrow `:774` enumeration as codifying the incomplete implementation (the amendment records only user authorization of already-implemented behavior) rather than a deliberate semantic exclusion — the helper's predicate encodes no "restoration to primary" distinction, so failback-begin is a real downgrade transition during recovery that goes uncounted. The FP arguments (spec-conformant narrow enumeration, observability-only impact, semantic "restoration to primary" reading) were weighed and rejected: the intent-vs-surface inconsistency is genuine, and no test covers it (existing tests at `tests.rs:1890`/`:2105`/`:2843` cover failover, failback re-seat, and probe relocation only). **Spec deviation:** yes — `:774` enumeration undercuts `:770` intent. **Fix target: code** (count the relocation — call `note_downgrade_if_dot_to_plain` at failback-begin) **+ spec** (`:774` enumeration would need a recorded amendment).

**Cross-group:** duplicate family with **G1-C09** (primary) and **G2-C09** — merged at aggregation; G4-C05 (DISCARD) is the config-layer complement.

## G6-C03 — Info — spec `:596` implies a 4th-failure relocation; code relocates on the 3rd (degrading) failure

**Scorecard row:**
```
| G6-C03 | Medium→Info | src/startup_dns.rs:2751-2776 (`on_exchange_failed`) | code\|spec | Failover relocates on the 3rd (degrading) failure, not the spec's "next counted failure": `note_failure()` advances to `Degraded` and same-turn `== Degraded` check relocates; spec :596 implies 4th failure relocates; code + test (startup_dns/tests.rs:1870-1874) agree with each other, spec sentence is the drift; direction safe (relocates sooner, fails closed) |
```

**Working description:**
`on_exchange_failed` (`src/startup_dns.rs:2733-2777`) calls `note_failure()` at `:2751-2752` and then evaluates the relocation condition `== ResolverDegradation::Degraded` at `:2766-2768` in the SAME turn; `note_failure` (`:630-643`) flips `Healthy{2}` → `Degraded` when `consecutive + 1 >= DEGRADED_AFTER (3)`. Therefore the 3rd consecutive failure both degrades AND relocates atomically — pinned by the test at `src/startup_dns/tests.rs:1870-1874` ("the third consecutive failure relocates the transport onto the backup").

Spec `docs/alumina-proxy.md:596` (alumina-hrdn4, Vec 18) states "Once the active resolver is degraded, the next counted failure relocates the transport to the next healthy resolver in the set" — implying a two-phase 3rd-degrades/4th-relocates sequence and describing a degraded-but-still-active state the code never reaches. Spec `:595` ("the third consecutive failure relocates it into passive degraded mode and emits one `rd` enter crossing") matches the code's `rd` enter crossing on the 3rd failure (`tests.rs:1879-1881`). So code and test agree with each other; only the spec sentence drifts.

Direction is safe: the code relocates SOONER than the spec sentence implies (3rd vs 4th failure), failing closed by moving off a failing resolver one exchange earlier. No security/data-path concern. The spec is byte-canonical and immutable, so this is an observation-only finding (fix target: spec reconciliation note; no code change warranted). A reader/operator relying on `:596` would mis-model when the transport leaves a failing resolver. Consistent with the G5-C10 precedent (spec-doc drift kept 5/5 TP). **Spec deviation:** yes — `:596` sentence drift. **Fix target: spec (observation)**. Severity normalized to **Info** (direction safe, observation-only, no code defect).

## G6-C04 — Info — failover drops `FailureReason::TlsIdentity`; operator cannot distinguish pin rejection from network failure mid-serving

**Scorecard row:**
```
| G6-C04 | Info | src/startup_dns.rs:2566-2577 (`next_healthy_after_active`) | none\|spec | Failover trust-form selection treats pin-rejection like a timeout: no escalation, no persistent flag distinguishing "resolver is untrusted" from "unreachable"; operator cannot tell a security-relevant pin rejection from a network failure in the failover path; failback re-probes pin-rejecting resolver every 900s |
```

**Working description:**
`FailureReason::TlsIdentity` (`src/startup_dns.rs:338`, as_str "tls_identity" `:348`) carries a doc comment (`:332-337`) explicitly promising the operator a TLS-specific reason "instead of an indistinguishable plain-TCP connect failure". The reason IS genuinely carried through the exchange — `advance_exchange` (`src/startup_dns.rs:2428-2490`) returns `TurnResult::Failed(reason)` at `:2443`/`:2451`/`:2460`/`:2469`/`:2476`, and the step functions call `note_failure(..., reason)` with the appropriate reason (TlsIdentity at `:1629`/`:1648`, Timeout at `:1568`/`:1660`, Connect at `:1527`/`:1534`/`:1541`).

BUT the serving loop discards it: `src/runtime.rs:395-398` matches `Some(TurnResult::Failed(_) | TurnResult::Published(_)) => break` — the `Failed(_)` pattern drops the reason. The only serving-path monitor signals are `rd=` crossings (`drain_resolver_transitions` `src/serve.rs:393-398` → `note_fact_resolver_degraded`) and `dp=` downgrades (`drain_downgrade_to_plain` `:418-423`). `on_exchange_failed` (`src/startup_dns.rs:2733-2777`) folds every failure into a bare degradation counter (`:2751-2752`) and relocates on `== Degraded` (`:2766-2768`); `next_healthy_after_active` (`:2566-2577`) checks only degradation state, never trust-form or failure reason. `maybe_begin_failback` (`:2585-2606`) re-probes the primary every 900s (FAILBACK_AFTER) regardless of why it failed — a permanently pin-rejecting (untrusted) resolver is re-probed forever.

The reason IS surfaced in the STARTUP window (`NameOutcome::Failed(FailureReason::TlsIdentity)` at `tests.rs:888`; probe-sweep verdicts at `:2855`; surfaced via `log.rs:1021-1024`) — so the distinction exists and is operator-visible at startup, but is silently dropped mid-serving, where the proxy actually operates. An operator whose proxy has relocated off a resolver cannot tell whether it was a security-relevant pin rejection (misconfigured pin, cert rotation, possible MITM) or a plain network failure.

Correctly scoped: this is NOT a spec deviation. Spec `docs/alumina-proxy.md:701`/`:673`/`:675` bless "a DoT entry's failure is a counted connect failure" with "no cleartext downgrade and no dynamic pin update"; `:681` "There is no dynamic pin update at runtime — the pin is fixed at startup." So counting pin-rejection as a counted failure is spec-conformant, and the failback re-probe fails closed (a pin-rejecting resolver can never pass a probe since the pin is fixed, so it never becomes active again). The finding is an internal inconsistency between the code's own documented intent (`:332-337`) and its serving-path behavior — a genuine, operator-relevant observability gap, not recorded-for-completeness. **Spec deviation:** none. **Fix target: code** (surface the reason in the serving path, e.g. fold a reason into the `rd=`/monitor surface or a per-failure log) — spec unchanged (observation only).
