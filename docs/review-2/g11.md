## G11-C01 — Medium — `emit_reject` omits requested hostname for non-Peer refusals

**Scorecard row:**
```
| G11-C01 | Medium | src/serving/reject.rs:31-40 (`emit_reject`); src/serving.rs:2363 (hostname parse), :2368/:2375/:2380/:2384/:2388 (refusals), :2398 (approved set) | code | Genuine spec :198 telemetry-contract deviation: reject records for Forbidden, NoResolvedAddresses, SetupTimeout, and DialFailed-from-candidate-exhaustion omit the requested hostname even though it was parsed as a valid `FixedHostname` at :2363 before the refusal; `emit_reject` derives the hostname solely from `slot.approved`, which is set ONLY at :2398 (ConnectPhase::Peer branch, after `decide`), initialized None at :718, cleared on close at :784; BadRequest refusals (:2105/:2232/:2354) are pre-parse and correctly omit; spec :198 says "requested hostname when valid" (not "approved hostname"); operator cannot attribute Forbidden/NoBinding/SetupTimeout rejections to a hostname; no raw-SNI leak (value is the allowlist-derived normalized FixedHostname); no serving-level test asserts the reject-log hostname for these refusals (only src/log.rs:1723 formatter unit test, hardcoded Some); fix: carry the parsed FixedHostname into `emit_reject` (e.g. pass `request.fixed_hostname()` alongside the refusal, or set `slot.approved` at admission before `decide()`), keeping BadRequest refusals None | 
```

**Working description:**
Genuine spec :198 telemetry-contract deviation — the only spec deviation and only Medium in G11.
`emit_reject` (src/serving/reject.rs:31-40) does `let hostname = self.slots[index].approved.as_ref()
.map(crate::config::FixedHostname::as_str)` then `reject(secs, reason, client, hostname)`. When
`slot.approved` is `None`, the record omits the hostname field (`Val::OptStr(None)` → field absent).
`slot.approved` is set ONLY at src/serving.rs:2398, in the `ConnectPhase::Peer` branch after
`self.storage.decide(...)`; initialized `None` at :718, cleared on close at :784. Refusals after the
hostname parse (:2363 `let approved = *request.fixed_hostname();`) but before :2398 therefore omit a
valid requested hostname: :2368 `Refusal::Forbidden` (domain blocked), :2375 `Refusal::DialFailed`
(CandidatesExhausted / decide `Err`), :2380 `Refusal::Forbidden` (not allowlisted), :2384
`Refusal::NoResolvedAddresses` (NoBinding), :2388 `Refusal::SetupTimeout` (DeadlineExhausted).
BadRequest refusals (:2105, :2232, :2354) are in the CONNECT-head parsing phase, before :2363 —
hostname not yet parsed, so omission is correct (all 5 voters agree). Dial-failure refusals after the
Peer branch (:2446, :2451, :2622) have `approved` set (at :2398) → include hostname — correct.
Spec :198 says "requested hostname when valid" (not "approved hostname") — the requested hostname is
available at :2363 for all the pre-Peer refusals. **No raw-SNI leak:** `approved` is the
allowlist-derived normalized `FixedHostname`, not raw SNI bytes. **Test coverage:** no serving-level
test asserts the reject-log hostname for Forbidden/NoResolvedAddresses/SetupTimeout; the only
reject-log test (src/log.rs:1723) is a formatter unit test with a hardcoded `Some`. This is a
single-pass finding (P5-C01). **Severity: Medium (5/5 defend)** — telemetry-only (no security
impact), but a real spec-contract deviation on common operational paths (blocked/no-binding/timeout),
in a repo where the spec is byte-canonical. Small, low-risk fix. **Spec deviation: YES** — spec :198
"Attempt one warn entry per rejected connection with the client address, reason, and requested
hostname when valid." **Fix target: code** — carry the parsed `FixedHostname` into `emit_reject`
(e.g. pass `request.fixed_hostname()` alongside the refusal, or set `slot.approved` at admission
before `decide()`), keeping BadRequest refusals None; add a serving-level test asserting the hostname
field for a Forbidden/NoResolvedAddresses/SetupTimeout rejection. Distinct from G11-C03/C04/C05/C06
(other G11 code-fix findings): this is the only spec deviation in G11. No cross-group merge needed.

## G11-C02 — Info — `Worker::release` unconditional decrement vs `finish_setup`'s `SlotState::InSetup` guard

**Scorecard row:**
```
| G11-C02 | Info | src/worker.rs:570-578 (`finish_setup`, guarded), :588-595 (`release`, unguarded), :604-610 (`release_tunnel`, unguarded), :631+ (`check_counter_lockstep`, debug-only) | code | Guard asymmetry on one handle lifecycle: `finish_setup` guards `if let SlotState::InSetup` (misplaced call is a no-op), while `release` unconditionally transitions to `SlotState::Free`, pushes to the free-list, and decrements `pending_count`/`occupied_count`; `release`'s own doc comment (worker.rs:579-583) asserts a no-corruption property the code does not enforce; the only tripwire `check_counter_lockstep` uses `debug_assert_eq!` and compiles out of release builds; unreachable today (consume-once non-Copy `SlotIndex` built only by `admit`; production call sites serve.rs:565 + reject.rs:70 only ever release granted in-setup slots), so Info not Medium; fix: mirror `finish_setup`'s `InSetup` guard (or a `debug_assert!`) in `release` for symmetric protection | 
```

**Working description:**
The guard asymmetry between `finish_setup` (guards `if let SlotState::InSetup`) and `release`
(unconditional destructive transition) is real and internal to one handle lifecycle. `finish_setup`
(worker.rs:570-578) is guarded — a misplaced call is a no-op, and its doc comment explicitly
justifies the guard as making misplaced calls no-ops. `release` (worker.rs:588-595) has NO guard —
unconditionally `self.slots[slot.index()] = SlotState::Free; self.push_free(slot.0);
self.pending_count -= 1; self.occupied_count -= 1;` then `check_counter_lockstep()`. Its doc comment
(worker.rs:579-583) asserts a no-corruption property the code does not enforce. `release_tunnel`
(worker.rs:604-610) is also unconditional (decrements `occupied_count` only) — voter 1's counterpoint
that no uniform defensive-guard convention exists is noted but does not negate the
`release`-vs-`finish_setup` asymmetry on the same lifecycle. The only tripwire,
`check_counter_lockstep` (worker.rs:631+), uses `debug_assert_eq!` — compiled out of release builds;
a future misplaced `release` would silently corrupt counters/free-list in release. **Unreachable-by-
construction:** production `release` call sites are src/serve.rs:565 (wrapper "Releases an in-setup
slot, consuming its handle") and src/serving/reject.rs:70 (`close_slot`, only when the slot handle
was taken); both only ever release granted in-setup slots via the consume-once `SlotIndex` handle
discipline (private-field non-Copy `SlotIndex` built only by `admit`; documented in doc comments +
`#[expect(clippy::needless_pass_by_value)]` for the linear-handle discipline). No production call
site releases a non-InSetup slot. This is a 2-pass cluster (P2-C04, P5-C02). **Raw tally: 4 TP / 1
FP** (voters 2/4/5 high, voters 1/3 medium). **Dissenting view (voter 1, FP):** `release_tunnel` is
equally unguarded, so no uniform defensive-guard convention is violated; unreachability is
type-enforced; the linear-handle discipline is deliberate/documented; a runtime guard on an
unrepresentable state is recorded-for-completeness scaffolding. Majority (4/5) judged the asymmetry
+ debug-only tripwire + doc-asserts-unenforced-property as a real, cheap-to-fix latent gap worth
recording at Info. **Severity: Info (5/5 defend)** — no live bug, unreachable today, no spec
deviation, no security impact. **Spec deviation: none** (internal invariant-hygiene, no spec
contract). **Fix target: code** — mirror `finish_setup`'s `InSetup` guard in `release` (or add a
`debug_assert!`/`#[cfg(debug_assertions)]` guard) for symmetric protection. Cheap, low-risk,
consistent with the codebase's own defensive convention. Distinct from G11-C01 (spec :198 telemetry
deviation, Medium): this is an internal invariant-hygiene asymmetry with no spec contract. No
cross-group merge needed.

**Scorecard row:**
```
| G11-C03 | Info | src/serve.rs:749-762 (`startup_final` call, passes `dropped: self.logs.dropped()`), :312 (`log_dropped()` accessor); src/log.rs:1204-1230 (`startup_final` encodes `dropped`), :1345-1350 (`shutdown_final`, no dropped), :1354-1366 + :569+ (`monitor_summary`/`encode_monitor`, no whole-record dropped) | code | The whole-record log-drop counter is invisible to the operator during a long run: surfaced only at boot via `startup_final` (serve.rs:749-762 → log.rs:1204-1230 `Field::new("dropped", …)`), absent from `monitor_summary` (log.rs:1354-1366 → encode_monitor :569+, which carries only the distinct monitor-report `report_drops`/`oreport_drops` counters) and absent from `shutdown_final` (log.rs:1345-1350, secs+status only; call sites runtime.rs:137/:366); `ServeStorage::log_dropped()` (serve.rs:312) has zero PRODUCTION call sites — exercised only by tests/stdout_stall.rs:94 (manifest's "dead code" corrected to "no production call sites"); during a long run with a stalled stdout sink, an operator cannot observe sustained log loss until exit; spec :199 only mandates drop-and-count (met); surfacing during serving is unspecified → observability gap, not spec violation; fix: add `dropped`/`dropped_overflow` to `monitor_summary` or `shutdown_final`, or wire up `log_dropped()` |

**Scorecard row:**
```
| G11-C07 | Info | src/serve.rs:343-359 (`report_monitor_if_due`), :1165-1228 (test call sites), :1257/:1301 (alloc-witness test call sites); src/log.rs:1354-1366 (`monitor_summary`), :594 (`report_drops` field); src/enforcement/monitor.rs:275-292 (`mark_reported`/`mark_forced_reported`), :240-243 (`note_report_drop`); src/enforcement/state.rs:179/:183/:187 (`monitor_due`/`mark_monitor_reported`/`mark_forced_monitor_reported`); src/runtime.rs:138/:270/:367 (production call sites); src/serving/tests.rs:7323 (return read as "committed") | none | `report_monitor_if_due` returns "due and attempted", not "committed": the bool is `monitor_due` (state.rs:179) — true even when the enqueue is dropped (full queue); the record is only "committed" if `mark_monitor_reported`/`mark_forced_monitor_reported` (state.rs:183/:187) ran; the return value is read two incompatible ways in-codebase: serve.rs:1165-1228 reads it as "due" (asserts true when the report was due but the queue was full — the drop is well-handled), while serving/tests.rs:7323 reads it as "committed"; all 3 production call sites (runtime.rs:138/:270/:367) ignore the return; manifest's "only caller ignores it" corrected to 13 call sites; full-queue drops are well-handled: `report_drops`/`oreport_drops` counters (log.rs:594) + `dirty` retry (monitor.rs:275-283) mean a dropped monitor summary is counted and retried next tick; observation only |

**Working description:**
The core "well-handled" claim is verified: a full-queue monitor-summary drop is counted via
`report_drops` and the monitor state is left `dirty` so the summary is retried on the next tick
(monitor.rs:275-283) — no silent loss. The finding is a boolean-return conflation in
`report_monitor_if_due` (serve.rs:343-359): the returned bool is `monitor_due` (state.rs:179), i.e.
"the report was due and an attempt was made", NOT "the report was committed". The record is only
committed if `mark_monitor_reported`/`mark_forced_monitor_reported` (state.rs:183/:187) ran. The
return value is read two incompatible ways in-codebase: serve.rs:1165-1228 (test call sites) reads it
as "due" — asserting `true` even when the queue was full (the drop is well-handled) — while
serving/tests.rs:7323 reads it as "committed". All 3 production call sites (runtime.rs:138/:270/:367)
ignore the return. **Manifest correction (verified):** the manifest's "only caller ignores it" is
imprecise — there are 13 call sites total (3 production + 10 test), and the test call sites read the
return as "due" (consistent with the function's actual contract), not "committed"; only
serving/tests.rs:7323 misreads it as "committed". No production misread exists, so no behavior
deviation. This is a single-pass finding (P4-C02). **Raw tally: 5 TP / 0 FP** (confidence mixed:
voters 1/2/3 medium, voters 4/5 high). **Severity: Info (5/5 defend)** — behavior is spec-compliant
(drop-and-count, retry); the finding is a documentation/contract-clarity observation on a boolean
whose name over-promises. **Spec deviation: none** — behavior is spec-compliant; observation only.
**Fix target: none** — no code change recommended; optionally rename the return or document the
"due and attempted" contract at serve.rs:343. Distinct from G11-C03 (whole-record log-drop counter
surfacing gap, fix code — C03 is *what is surfaced*, C07 is *what the boolean means*): C07 carries no
fix target. No cross-group merge needed.
