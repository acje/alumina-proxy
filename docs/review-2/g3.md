## G3-C03 — Info — `find_end_of_head` rescans whole head on every `feed` → O(N²)

**Scorecard row:**
```
| G3-C03 | Info | src/connect.rs:220-239, :246-256 | code | `find_end_of_head` rescans whole head from 0 on every `feed` → O(N²) across byte-at-a-time feeds (~33M byte comparisons/conn, ~17G across 512-tunnel profile); CPU-amplification/robustness, no correctness impact |
```

**Working description:**
Four of five voters verified `feed` (`connect.rs:220-239`) rescans the full
accumulated head from byte 0 via `find_end_of_head` (`:246-256`) on every call
with no incremental cursor in `ConnectParser`, so byte-at-a-time/small-chunk
feeds are genuinely O(N²) (~33.5M comparisons for an 8 KiB head; ~17G across
the 512-tunnel profile), and byte-at-a-time trickle is reachable through the
production serving path. The rescan is bounded by the 8 KiB CONNECT_LIMIT and
the 10 s setup deadline, so **Info** severity is correct. The single FP (v5)
argued duplication with W1-L1b-F6 and whole-chunk live feeds; the majority
found it distinct — W1-L1b-F6 documented only the per-invocation O(N) bound,
not the repeated-rescan amplification — and the code's own "O(N) linear scan"
comment understates the repeated-rescan cost. **Spec deviation:** none.
**Fix target: code** (incremental scan cursor / memoized end-of-head position).

## G3-C05 — Info — JA4 `ver` fallback yields "00" instead of spec's "else the Protocol Version"

**Scorecard row:**
```
| G3-C05 | Info | src/client_hello.rs:137-144, :842-850 | code | JA4 `ver` fallback `unwrap_or(0)` yields "00" instead of spec's "else the Protocol Version"; latent/unreachable (ja4() only on validated hellos) but contract deviation if baseline scope widens to rejected hellos |
```

**Working description:**
Four of five voters verified the JA4 `ver` fallback uses `unwrap_or(0)` → "00"
(`client_hello.rs:138-144`, `:848`) against the spec's "else the Protocol
Version" rule (`:888`), and spec `:889` explicitly contemplates JA4 being
computed on rejected/malformed hellos — making the fallback reachable if the
baseline scope widens. The struct never retains `legacy_version`, so the spec
branch cannot even be implemented without a change. The single FP (v5) argued
the fallback is provably unreachable today (parser requires ≥1 non-GREASE TLS
1.3 version; malformed hellos never produce a ClientHello), but the claim
explicitly frames this as a latent contract deviation and the spec's own `:889`
clause contemplates the wider scope; reachability today is not the test — the
deviation from the byte-canonical spec's stated `ver` rule is real. **Spec
deviation:** yes — `:888` "else the Protocol Version" branch unimplementable
without retaining `legacy_version`. **Fix target: code** (retain
`legacy_version` and implement the spec branch).

## G3-C09 — Info — `offered_versions()` doc comment claims "non-GREASE, filtered and ordered" but returns raw wire order

**Scorecard row:**
```
| G3-C09 | Info | src/client_hello.rs:78-82 | code | `offered_versions()` doc comment claims "non-GREASE, filtered and ordered" but returns raw wire-order list; callers re-filter; doc-only inaccuracy |
```

**Working description:**
All five voters verified `offered_versions()` (`client_hello.rs:78-82`) has a
doc comment claiming "non-GREASE supported versions, filtered and ordered", but
the implementation returns the raw wire-order slice — `parse_supported_versions`
retains GREASE verbatim and `validate_versions` skips but never removes, so the
`allows_grease_versions_alongside_tls13` test proves GREASE values are
retained. The sole caller `ja4()` must re-filter, and sibling accessors are
documented "unfiltered", making this a real, verifiable doc-only inconsistency.
The spec never requires this accessor to filter/order, so there is no
behavioral impact. **Spec deviation:** none. **Fix target: code** (correct the
doc comment to "raw wire order, unfiltered").

## G3-C10 — Info — JA4 baseline/fingerprint never computed for rejected/malformed hellos

**Scorecard row:**
```
| G3-C10 | Medium→Info | src/serving.rs:2703, :2714-2741 | code | JA4 baseline/fingerprint never computed for rejected/malformed hellos; xfbq8 `d/i` clause + "observes and retains" framing may contemplate fingerprinting rejected hellos; spec-interpretation, ambiguous |
```

**Working description:**
All five voters verified the JA4 baseline/fingerprint is computed only on the
validated-hello path — `maybe_record_ja4_baseline` (`serving.rs:2714-2741`) is
reached solely from `hello_complete` (`:2703`) / `dial` after acceptance, while
the reject path (`serving/reject.rs`) closes the slot without ever computing a
fingerprint. The xfbq8 amendment's format clause (`:889`) normatively states
"rejected or malformed initial ClientHellos with no SNI must yield `i`", and
the "observes and retains" (`:908`) / "INITIAL ClientHello only" (`:912`)
framings carry no validated qualifier — so the code's validated-only choice
(which makes the `i` token structurally unreachable) is an interpretation the
spec never clearly blesses. **Spec deviation:** yes — ambiguous
spec-interpretation gap on `:889`/`:908`/`:912`. **Fix target: code** (compute
JA4 on rejected/malformed hellos if the wider scope is intended) **or spec**
(explicitly scope JA4 to validated hellos). Severity normalized to **Info**
(observability-only surface).
