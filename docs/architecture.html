Alumina — Architecture of the DNS-bound exit-gate proxy

A source-grounded description of the as-built system at a fixed revision: the two forwarding barriers, the single-reactor serving loop, the typed enforcement lattice, the fixed-storage memory envelope, and the DoT-bound startup-to-serving DNS path that decides whether the process may listen at all.

Authority: the as-built source revision 590c197ca768055774a44a2484a3e849fd96a2a0 (branch main). All line citations are to that as-built source revision, were verified by the docs gate at the documentation revision carrying this document, and were re-derived for every file whose code moved after the previous architectural reference; none is copied from another document.

Identity: alumina is a single-binary, config-file driven, DNS-conditional CONNECT proxy. After a startup DNS window of at most 90 s it opens the listener early once every name is usable, else Full or Degraded at the deadline; it enforces a two-barrier forwarding gate per tunnel; it allocates its retained working set once at boot and never frees it — the fixed-memory contract is scoped to first-party execution paths, with dependency behavior a separately accounted, bounded seam (the DoT/TLS alloc profile in particular); and it treats every enforcement deviation as a counted, observable fact rather than a silent pass.

Method: this document is a static reading of the source at the commit named above. Every architectural claim cites src/*.rs, tests/*.rs, or the governing specification (docs/alumina-proxy.md, SHA-256 e39dd75d33635d582e981bfcb4f91fa92e3f23f2bf9a408c3d7dcd5079cd4401). Values the code itself prints or asserts are recorded as measured. No review apparatus — findings, severities, proposals, or open questions — is carried here; the architecture is described as it is built.

Acronyms. DoT = DNS over TLS. SPKI = Subject Public Key Info. JA4 = string hash of TLS client fingerprint features. SNI = Server Name Indication. FQDN = fully qualified domain name. MiB = 10242 bytes.

1. System purpose and boundary

Alumina is the castle’s exit gate. The specification is explicit (docs/alumina-proxy.md §Design philosophy): it does not police ingress, guard an interior, or inspect payloads; it guards the single exit through which a trusted-at-rest application reaches the outside world, with a fixed and opinionated design rather than a surface of configuration choices. The trust model is not distrust of the system: the application and the operator are trusted at rest, and the operator holds full privilege over both. Alumina exists because compromise is inevitable — when the application is compromised, the proxy’s task is to identify the compromise and protect against further exploitation purely through egress, which is the limit of its visibility and responsibility.

From that task follows the core promise that shapes the whole codebase: no silent acceptance of adversarial behavior and likewise no silent acceptance of internally inconsistent evidence. In the idiomatic deployment the only client is the trusted application on a fixed golden path, so a correctly configured, healthy workload produces zero deviations; the enforcement machinery that follows exists to turn any deviation into a typed, counted fact with a documented effect.

1.1 Boundary: what the binary is allowed to do

  • Fixed input, no policy from the environment. The only configuration input is config.toml relative to the working directory (src/main.rs:22, CONFIG_PATH); no CLI arguments or environment variables are read as policy. The configuration document is size-bounded (≤ 16 KiB at src/config.rs:15, CONFIG_DOC_LIMIT, schema-strict: an unknown key is an error), read once at boot through config::load_config_document (load entry at src/config.rs:706; strict schema and unknown-key rejection at :739-783).
  • Privilege floor. Preflight refuses root, refuses any non-empty effective/permitted/ambient capability set, and requires no_new_privs before the process may proceed (src/preflight.rs:96-116). Exit codes are fixed and documented: 75 EX_TEMPFAIL for the startup DNS verdict, 70 EX_SOFTWARE (given as program exit), 78 EX_CONFIG for configuration failure (src/main.rs:23-24, src/boot.rs:7).
  • Listener conditionality. The listener is opened only when the startup window’s canonical readiness rule holds — the unresolved count must be at most the configured allowance, otherwise the process exits with status 75 (src/serve.rs:98, :974-990, StartupDecision::{Serve,Exit75,Terminated}). A first observed SIGTERM short-circuits the window and never binds.
  • Egress only. Upstream tunnels carry approved hostname traffic; ingress policing, payload inspection, and inter-client traffic are explicitly outside scope (spec §Design philosophy, §non-goals).

1.2 Deployment boundary

The idiomatic deployment places alumina on the same host as the trusted application, listening on the configured listen address (the reference deployment uses a private endpoint), with the application pointed at it as its HTTP CONNECT proxy, and the process holding no elevated privileges. Upstream, the proxy performs its own DNS resolution — a plain-DNS or DoT exchange per query over a retained connection — and connects to the resolved peer on the allowlisted port. Figure 1 shows the boundary and the three surfaces that cross it (config in, tunnel traffic, DNS).

Two deployment facts recorded in source deserve emphasis. First, the startup window is the process’s single admission decision: it runs for at most 90 s, opening the listener early once every allowlist name is usable and, at the deadline, serving Full when none are unresolved or Degraded within the configured allowance, exiting 75 above it; a first-observed SIGTERM short-circuits the window as Terminated and never lets it bind (STARTUP_WINDOW_SECS: u64 = 90, src/startup_dns.rs:49; the readiness rule is the canonical decision of docs/alumina-proxy.md:108). Second, the process is single-threaded for both DNS and serving: one reactor loop, one owner of the poll, one set of timers (src/runtime.rs, src/serving.rs; the worker owns tunnel state inside the same thread — WorkerClock and slot tables live in src/worker.rs). There is no dedicated DoT thread: the only std::thread invocation in production code is the thread::sleep that parks the single thread inside the startup DNS driver (src/startup_dns.rs:25, :2901; resolve_window runs synchronously on the reactor thread before the listener opens, at src/startup_dns.rs:2787, and the serving-time DNS work is cooperative per-turn advance, not a second thread). No thread is ever spawned in production — the only std::thread::spawn/Builder sites in production-adjacent code are #[cfg(test)] doubles (src/serve.rs:1252). The single thread observes traffic, log, DNS, and shutdown readiness in one combined wait (docs/alumina-proxy.md:146).

Clock authority is single and explicit: one now0 origin plus whole-second offsets threads through worker, cache, DNS, and serving, with the retained worker re-anchored to the DNS epoch at the mount_clock seam when a startup window (or a test) establishes its own elapsed base (src/serve.rs:223; WorkerClock at src/worker.rs:97-105; the window anchor read back via window_start, src/startup_dns.rs:1387-1393).

2. Component ownership

Alumina’s crate root exports 21 public modules (src/lib.rs:4-27) under crate-level deny(clippy::unwrap_used, clippy::expect_used) (src/lib.rs:1-2), which is the first and strongest architectural verb: production code may not unwrap; every expect must carry a proven-bound justification and an #[expect] with a reason (e.g. src/serving.rs:509, src/config.rs:1001-1004, src/cache.rs:369-372). The public surface has three consumers: the serving binary (src/main.rs), the test corpus, and the dev-only src/bin/parser_bench.rs developer harness, a distinct binary importing alumina::client_hello::{ChInspector, Inspect, ja4_fingerprint} to drive those two parsing seams in a tight loop (src/bin/parser_bench.rs:1-9, :45; src/lib.rs:4-27). Figure 2 groups the modules into ownership layers and notes the dependency seams that cross the layer boundaries: the DNS/DoT transport calls the reactor core’s Cache/Schedules operations (src/dns.rs:348-380); the serving-surface inspector depends on top-layer config types (src/client_hello.rs:3, :1108-1118); and the gate’s two-barrier authority depends on the serving-surface HelloAccepted witness (src/gate.rs:27). Ownership is directional by layer; calls are not exclusively top-down — the seams above are real dependencies, not a strict acyclic layering.

The TLS trust-verification stack is a deliberately minimal and bounded seam. Cargo.toml declares three direct DoT-related manifest entries — rustls, rustls-webpki, and ring (Cargo.toml:198-209); two of them, rustls and ring, are direct source imports (src/startup_dns.rs:31-38): rustls supplies the TLS 1.3 client (default-features = false), and ring is promoted to a direct dependency so the strict SPKI pin can hash the server’s SubjectPublicKeyInfo directly (rustls keeps its digest surface crate-private). rustls-pki-types is not declared directly — it arrives via rustls and the source imports only the rustls::pki_types re-export, never rustls_pki_types itself (Cargo.toml:199-203; src/startup_dns.rs:36). rustls-webpki is retained as the sole feature-enabler of the ring provider in the resolved graph, not as a source import (Cargo.toml:199-203).

3. CONNECT and the tunnel sequence

A connection is admitted, parsed, validated, gated, and relayed through the slot’s Stage state machine (src/serving.rs:340-351). The stage machine is a typed, non-public enum with ten states — Idle, ReadingConnect, RunningDecision, Dialing, SendingConnected, ValidatingHello, WritingHello, Relay, Refusing(&'static [u8]), and Closing. Nine nominal steps: Accept (not a Stage variant) plus eight Stage variants — ReadingConnect, RunningDecision, Dialing, SendingConnected, ValidatingHello, WritingHello, Relay, Closing; ten enum variants overall, with Idle and the alternate Refusing branch completing the set.

3.1 Admission and the capacity answer

Admission is bounded by MAX_TUNNELS = TUNNEL_SLOTS = 512 and pending setups by MAX_PENDING_SETUPS = 128 (src/worker.rs:42-45); the spec’s historical “640” figure is explicitly rejected in the code comment (“never 640”). Upstream attempts are paced per tunnel at MAX_UPSTREAM_ATTEMPTS = 4, with an absolute setup deadline of SETUP_DEADLINE_SECS = 10 that is never reset, and per-attempt connect deadlines of CONNECT_DEADLINE_SECS = 2 clipped to the setup deadline (src/worker.rs:48-55).

On admission failure the code writes the fixed BODY_503 = "HTTP/1.1 503 Service Unavailable … no capacity\n" and records a RejectReason::Capacity log (src/serving.rs:1808-1836; body constant at :201-202). Accept re-arms are backed off 100 ms after a transient failure so a hot loop cannot spin (ACCEPT_BACKOFF, src/serving.rs:96-98). A successful admission assigns the slot’s fresh generation, freezes the setup deadline, registers the client on the reactor, and moves the stage to ReadingConnect (src/serving.rs:1819-1836).

Handles are linear and typed — SlotIndex during setup, TunnelIndex after graduation, consumed on release — so a stale handle can never free a reused slot (src/worker.rs:312-341, :590-615).

3.2 The CONNECT head parse

The head is bounded by MAX_HEADER_LINES = 16 (src/connect.rs:13; the “too many header lines” rejection at :103, :289) and ends at the first CRLFCRLF (:185). Two hardening details are architectural: a bare line feed (a 0x0a not preceded by 0x0d) and a bare carriage return are both rejected rather than tolerated (src/connect.rs:332-340), as required by the spec’s L3 bare-CR rejection. The result limits the parser to the head only — tunnel bytes after the delimiter are never treated as metadata.

3.3 Refusal classes and fixed bodies

The refusal surface is a typed Refusal enum with five cases — BadRequest, Forbidden, NoResolvedAddresses, DialFailed, SetupTimeout — mapping one-to-one onto fixed HTTP bodies so a refusal reason is never reverse-inferred from a byte match (src/serving/policy.rs:8-24). Table 2 lists the mapping.

3.4 Tunnel lifetimes and the shutdown deadline

The setup deadline starts at accept and is never reset (SETUP_DEADLINE_SECS, src/worker.rs:51), and connect attempts are clipped to it. The relay idle deadline is 300 s, starting at gate open and reset only on successful tunnel-byte writes — never by readiness alone (IDLE_SECS, src/serving.rs:84). The first orderly EOF starts a 5 s drain that is never reset (DRAIN_SECS, src/serving.rs:88). The first SIGTERM stops admission, closes pending setups, cancels the DNS transport, and fixes an 8 s grace that later signals cannot extend (SHUTDOWN_GRACE, src/serving.rs:93; on_sigterm, src/serving.rs:1544-1558). The single poll timeout folds every deadline into one wait, and the expiry sweep runs before dispatch (poll_timeout, src/serving.rs:3163-3223; expire_sweep, src/serving.rs:3245). A drained shutdown exits 0, a forced close exits 70, resources are released exactly once, and the process exits without deallocating (ShutdownExit, src/serving.rs:178-196).

4. The two-barrier forwarding gate

gate.rs is the authority over byte flow, and it is a pure state machine: no sockets, no I/O, small, fixed-offset, deterministic, and unit-testable (src/gate.rs:1-8). The bytes themselves live in the boot-owned per-slot workspace, so the gate makes decisions only. There are two barriers, and each is an invariant from the spec (docs/alumina-proxy.md §Authorization-Before-Forwarding):

  • Barrier A (client → upstream): no client bytes, including ClientHello, are forwarded before complete validation with exactly one SNI normalized-equal to the approved CONNECT hostname, no ECH, and the TLS 1.3 profile. crate::client_hello::validate supplies the verdict; the gate tracks the hello boundary in the stream.
  • Barrier B (upstream → client): no upstream bytes are forwarded before the gate opens. A successful CONNECT response alone authorizes neither direction.

4.1 The gate state machine

The gate returns a typed UpstreamWrite verdict per client write: BlockedByBarrierA while the hello is not yet fully validated; WritingHello { total } when exactly the validated hello prefix may pass; GateOpened { crossing, relay_from_open } for the single transition that crosses H and may include coalesced trailing bytes; and Open once fully relayed (src/gate.rs:41-67). Upstream activity while barrier B is closed is typed as Activity::{Data, Eof, Reset} (src/gate.rs:74-78); only observation of such activity terminates setup — WouldBlock/readiness alone is not activity (D4, src/gate.rs:66-78).

4.2 The witness-minted hello boundary

ValidatedHello { end } is mintable only with a HelloAccepted witness, which only client_hello::validate can produce — so the gate can never be told a caller-invented hello boundary (src/gate.rs:114-142; the type-level invariant is recorded in Appendix A). A test-only test_new constructor exists under #[cfg(test)] and can never be reached in a production build (src/gate.rs:131-137).

4.3 Gate opening is atomic with the crossing write

The gate opens atomically in the same transition whose successful client→upstream write accounting reaches the end of the validated ClientHello (H), before any subsequent upstream read (D3, src/gate.rs:217-244). A single successful write may cross H and carry coalesced trailing bytes; those trailing bytes are relay-from-open and are already forwarded by that same write (relay_from_open). Ordered progress is kept by monotonic committed offsets, so a partial successful write advances only its own bytes. This is the mechanism that makes “no silent acceptance” hold in the streaming direction: bytes cannot leak across the barrier before the hello is fully validated and authorized.

4.4 GatePhase: the typed tunnel lifecycle

GatePhase is the pure lifecycle carrier of the two-barrier gate — the phase plus the byte-offset ledger for both barriers live in TunnelGate (src/gate.rs:73-90, :93-94). The order is monotonic — AwaitConnect → Connecting → AwaitResponse → Validating → RelayActive — and Terminated is reachable only from the pre-open phases; every terminator forbids forwarding in both directions (TerminateReason, src/gate.rs:63-68).

5. DNS, DoT, and the refresh path

Alumina performs its own resolution over one retained transport with one outstanding query — StartupDns is a hand-rolled nonblocking state machine over a single reusable connection (src/startup_dns.rs:1147-1282). It carries four control planes: the refresh schedule per name × family, resolver failover on counted failure, failback after relocation, and sensor probes that never apply cache state. This section covers the classifier, the DoT profile, the startup decision, the exchange lifecycle, and the refresh/retry schedule.

5.1 Resolver classification: FQDN ⇒ DoT, bare IP ⇒ plain, no silent fallback

A resolver entry is either a bare IP (port 53, plain DNS) or an IP-with-attached-FQDN (port DOT_PORT 853, DoT). The FQDN presence is both the DoT signal and the port signal, and there is no silent plain-DNS fallback for a DoT entry (src/resolver.rs:215-235). Trust homogeneity across the resolver set is enforced at configuration time — a mix of trust classes is rejected rather than degraded (ConfigError::MixedResolverTrust, src/config.rs:829-836). A separate guard restricts the early_data control’s block scope to connection only — an upstream-sourced early-data signal therefore cannot select a per-domain or process-wide latch (src/config.rs:1074-1082, :1110-1115; see §6.2).

5.2 DoT trust: pin-or-nothing

The DoT client pins via #pin-sha256= and authenticates the peer three ways: SNI/SAN matching against the server name, a SHA-256 digest of the end-entity certificate’s SPKI compared against the pin when one is configured, and TLS 1.2/1.3 handshake-signature verification with the configured provider algorithms — the peer must prove possession of the pinned certificate’s private key (src/startup_dns.rs:839-888; the verifier at :840 with SAN and pin checks at :849-856 and signature checks at :873-888). Certificate validity-window exclusion is best-effort and counted only when the DER validity parse succeeds (:858-860, expired_pin_certs); the DER walk fails open (cert_outside_validity_window, :1092-1098), so a parse anomaly reports no warning rather than a rejection — pin-or-nothing and fail-open validity parsing stay distinct facts. Without a pin, chain validation runs against an explicitly empty root store and therefore always fails — a deliberate “no trust anchors yet” position that surfaces as startup warnings (src/startup_dns.rs:863-870, src/main.rs:127-143). The result is deliberate: a pin is the only trust. “IP#fqdn without pin” is a deterministically unusable resolver rather than a degraded one — operator documentation must state this plainly.

5.3 The startup decision and its report

The canonical readiness rule (spec docs/alumina-proxy.md:108) is: open the listener when the unresolved count is at most the configured allowance, else exit EX_TEMPFAIL (75). The window is a maximum 90 s (src/startup_dns.rs:49): early closure opens Full the moment every name is usable, while at the deadline it opens Full (zero unresolved) or Degraded (within the allowance). The decision is typed as StartupDecision::{Serve(ServingMode), Exit75{unresolved}, Terminated} (src/serve.rs:98): a first-observed SIGTERM short-circuits the window as Terminated, which never binds or attaches a listener. A single 90-second exchange report is carried by StartupOutcome (src/serve.rs:107-117).

The startup window is driven cooperatively by the single serving poll: Serving::run_startup_window attaches the retained DNS transport to the serving poll before selection starts and advances the exchange per turn with an ExchangeClass::Startup exchange (src/serving/startup.rs:42-96, :147), so a first observed SIGTERM during the window is seen within one bounded poll instead of being invisible for the window’s full duration.

Only fully validated outcomes reach the cache: dns::apply_outcome prepares the schedule delta before mutating the cache (src/dns.rs:366-428; prepared deltas at src/schedule.rs:358-391, :502-537), so a DeadlineOverflow leaves both resources untouched. Responses are matched on tid + question fields (qname + qtype + qclass) (src/dns.rs:983-1027); QR/opcode/TC are validated from the response flags, and RCODE is classified or rejected — NOERROR/NXDOMAIN are handled, every other RCODE is refused (:1199-1230) — so RCODE is validated, not a query-equality field; DNAME and trailing bytes are rejected everywhere (:1181-1183).

5.4 Per-entry CNAME bailiwick

Each allowlist name derives its own bailiwick: itself plus only the CNAME suffixes it declared. Coverage is per-entry, so one entry’s declared suffixes never widen a neighbour’s trust (src/dns.rs:863-953), and same-bare-name entries across ports must declare byte-identical suffix lists or boot fails with DivergentCnameBailiwick (src/config.rs:1244-1262). The flat union of declared suffixes is bounded by the fixed ALLOWLIST_MAX (32) slot bound, and overflow is fail-stop (src/dns.rs:863-953).

5.5 The typed exchange lifecycle

ExchangeClass — Startup, Serving, or Probe — is a parameter of the single start_exchange call, so an exchange’s class is fixed at its start seam rather than by a later mark (src/startup_dns.rs:215-223, :2948-2959; the class is stored on the ActiveExchange). The retained-resolver refresh path requests a Serving exchange (src/runtime.rs:347; start_dns_exchange in src/serve.rs:767), and a cooperative startup window requests Startup (src/serving/startup.rs:147). Per-turn cleanup cancels exactly the Startup-class retained work while serving exchanges stay outstanding: cancel_retained_startup_exchange (src/startup_dns.rs:1606-1614, driven from src/runtime.rs:262) is scoped to the startup class by the typed lifecycle, so no servicing or probe exchange is ever cancelled as leftover startup work. Overlap fails closed: a second start_exchange while one is active returns ExchangeActive and leaves the outstanding exchange, its schedule accounting, and its connection untouched (src/startup_dns.rs:2957-2959).

The DoT serving path refreshes on a single connection with a 5 s exchange deadline (EXCHANGE_DEADLINE_SECS, src/startup_dns.rs:48): a failed handshake forces a full reconnect — and a fresh rustls configuration — on the next exchange (:2083-2117, build_tls_connection at :1113-1132), with retries governed by the schedule backoff ladder [1,2,4,8,16,30] (src/schedule.rs:16). Failover relocates to the next resolver on counted failures (on_exchange_failed, src/startup_dns.rs:3520-3597); failback returns after a 900 s grace with three consecutive successes (FAILBACK_AFTER_SECS, src/startup_dns.rs:679; maybe_begin_failback at :3168-3200, on_exchange_succeeded at :3598-3638). Sensor probes run behind the post-window sweep and sustained-negative corroboration and never apply cache state (maybe_begin_sweep :3222-3245, sweep_next_probe :3310-3350, step_corroboration :3374-3416). A relocation that would downgrade a DoT entry from TLS to plain DNS is counted as a dp monitor fact and never performed silently (note_downgrade_if_dot_to_plain, src/startup_dns.rs:3200-3221; src/resolver.rs:215-235).

5.6 Cache lifetime and the generation guard

The cache stores validated bindings only, keyed by configured name × Family (A/Aaaa) with a fixed address capacity of MAX_ADDRESSES = 16 per name and family (src/cache.rs:7). EntryState is a deadline-derived view, never stored: Empty | Fresh | Stale | Retired are computed from the freshness and retirement deadlines (src/cache.rs:66-77). Every publish is generation-guarded: a validated in-flight result carries the current Generation, and publish_positive refuses any mismatch (StaleGeneration), so a stale publish can never overwrite a newer entry (src/cache.rs:50-62, :373-382).

6. Enforcement: violations, effects, gates

The enforcement stack is deliberately small and typed: a violation lattice, a pure violation→effect projection, per-class counted gates, and a monitor that folds counted facts into a fixed record. Its purpose is to make “no silent acceptance” mechanically true — an internally inconsistent observation is reported as Unknown, never silently treated as a pass.

6.1 The violation lattice

There are six top-level Violation cases (src/enforcement/policy.rs:89-97): AnyIllegal { cause } (with four AnyIllegalCause payload classes — KIND_COUNT = 4, :84-87), EarlyUpstreamData, Ja4Change, EvidenceInsufficient, Unattributed, and MissingParseResult.

The last three cases exist precisely to keep “unknown” out of “harmless”: all three map to Effect::Unknown { reason } (src/enforcement/policy.rs:136-145) and none consumes the first-slot latch. That distinction is the mechanism that makes the “no silent acceptance” invariant honest: evidence that is internally inconsistent is reported as unknown rather than treated as a pass.

The effect type itself has exactly four forms: BaselineOnly, Notify { scope }, Block { scope }, and Unknown { reason } (src/enforcement/policy.rs:100-105). The projection is a pure function (decide, :113-146) over the ControlTable and the first-slot latch — no I/O, no mutation of the table, deterministic and unit-testable.

6.2 The per-class gates

Gates are per-class: bad_handshake, illegal_fqdn, early_data, and ja4 form GateSet (src/enforcement/state.rs:71-77). Each is an AllScopeGate whose threshold and window_secs are nonzero (NonZeroU32/NonZeroU64): the nonzero types make only zero parameter values unrepresentable and say nothing about whether a gate can ever arm (src/enforcement/state.rs:26-46). Defaults are threshold 1 in a 900-second window (:12-17).

Arming differs by class. An AnyIllegal counter is noted on every class fact; an early-data or ja4 counter is noted only when the raw decided effect is Effect::Block { scope: All }, and only a raw Effect::Block { scope: All } is gated into an all-scope action (src/enforcement/state.rs:262-334). Each class’s gate counts only that class’s facts: the per-class isolation between bad_handshake and illegal_fqdn is enforced by which counter each cause notes (src/enforcement/state.rs:264-286).

The [early_data] All-scope gate cannot arm in shipped configuration, and the restriction is structural rather than an oversight. A per-class all-scope counter is noted only when the raw decided effect is Effect::Block { scope: All } (src/enforcement/state.rs:262-278), and the configuration parser rejects any early_data block whose scope is not connection (ConfigError::EarlyDataBlockScopeInvalid, src/config.rs:1110-1115); the parser comment documents the restriction as the early-data block-scope close — an upstream-sourced early-data signal cannot select a per-domain or process-wide latch (docs/alumina-proxy.md:1007-1009). The only reachable raw effects for EarlyUpstreamData are therefore BaselineOnly, Unknown, Notify, or Block { Connection } — never Block { All } — so the early_data gate’s counter is never noted and its crossed flag never arms. The section is still parsed (src/config.rs:798-805), validated (:963-999), stored, and wired into the counter table (src/enforcement/state.rs:242-246); a unit test that builds a ControlTable directly with early_data = Block { All } (src/enforcement/state.rs:1415-1450) exercises the plumbing under a table state the production parser cannot produce, so it documents the unreachability rather than a live path. The per-connection control still fires; this is an inert knob, not an open bypass.

6.3 Typed ordinals and the monitor

DomainOrdinal is a 0-based configured-allowlist ordinal whose payload is a range-bounded u8 index; no table identity is stored, and from_index takes no table (src/enforcement/action.rs:98-132). On lookup the ordinal is validated against the current table’s entry count, so a table with the same or a larger count accepts the value and an out-of-range ordinal yields Unknown/no control (src/enforcement/action.rs:206-230): the type proves an index/range discipline against the current table, not table provenance, and attacker-controlled strings are never keys. The monitor (src/enforcement/monitor.rs) folds counted facts into FactCounters — the observed as-built counter families: any_illegal (per cause), early_data and ja4 (per ordinal), unknown, resolver degraded, dns anomaly, downgrade-to-plain, probe relocations, expired pin certs, ja4 seed and change — folded by ten note_fact_* recorder methods (src/enforcement/monitor.rs:178-290). Bounded Unix-time windows rotate the IncidentReport at REPORT_WINDOW_SECS = 3600 (recorded; src/incident_report.rs:14).

Counting is not uniform. The monitor’s FactCounters counters saturate and are bounded, and the monitor record itself is encoded in place into the fixed log slot budget; a WindowedCounter gate counter, in contrast, is a plain u32 increment (self.count += 1, src/enforcement/state.rs:148-160) — a saturating add is not what bounds it. Anomaly kinds are discrete (DnsAnomalyKind) so a new sensor can never default to an unrelated class.

7. Memory envelope

Alumina pre-allocates its retained working set once at boot and never frees it — the plain-DNS profile; a DoT resolver additionally allocates per connect (see §7.2). The authoritative plan is inventory.rs — a set of named constants and type-derived figures that the binary prints at boot (src/main.rs:34-40), and that pinned ticket tests lock to exact values (src/inventory.rs:273-285). The number printed is 214 665 002 bytes ≈ 204.7 MiB — the printed, constant-derived named-buffer lower-bound plan (traffic 134217728 + serving workspace 80310272 + dns named buffers 137002), not a measured boot or RSS figure.

7.1 What the bound includes and excludes

  • Included: per-slot traffic buffers; retained parser + inspector (including the retained JA4 arrays as the Option<ClientHello> inside each ChInspector); DNS transport query/response/parse buffers; everything size_of over the retained types yields — with no second hand-maintained factor.
  • Excluded by design: per-slot gate/capture/cursors and the approved hostname, transient scratch, the reserved log queue, kernel socket buffers, allocator fragmentation, and rustls/ring heap. The bound is a lower bound over retained named buffers, never an RSS estimate (src/inventory.rs:173-181).

The printed bound deliberately excludes the remaining retained fixed structures. Their retained capacities: a worker slot table [SlotState; 512] plus free_heap [u16; 512] (src/worker.rs:372-379), a deadline-presence bitmap [u64; 8] = 64 B (src/serving.rs:852-863), the preallocated POLL_EVENTS_CAP = 1024-event snapshot (src/serving.rs:117), the JA4 baseline [[Ja4BaselineEntry;16];32] = 512 × 36 B = 18 432 B (src/serving.rs:584-619), the 64-entry capture ring (src/enforcement/monitor.rs:11-115), 32 incident windows plus 512 slot markers (src/incident_report.rs:243-244), and the enforcement control table [Control;4] with two [PerFqdnControl;32] (src/enforcement/action.rs:161-232).

Within the serving workspace the inspector dominates: each ChInspector retains two distinct 64 KiB arrays — buf and scratch, 128 KiB per slot — sized to MAX_CLIENT_HELLO = 64 * 1024 to inspect a handshake capped at MAX_HANDSHAKE_LEN = 16 * 1024 (src/client_hello.rs:6-21, :410-419). Across 512 slots the two arrays’ retained capacity is 64 MiB of the 76.6 MiB serving workspace, ≈ 83%. That capacity is retained capacity with distinct roles, not reclaimable headroom: each 64 KiB buffer is 4× the 16 KiB message bound, and a saving claim would require a concrete record-framing/resizing model rather than arithmetic on the cap.

7.2 The zero-allocation discipline and the DoT seam

The serving steady state is allocation-free by construction after boot: the slot table is built once by collect() over an exact-size iterator (src/serving.rs:1028-1035), so it is one boot allocation and any later growth would allocate post-boot. Per turn, run_once coalesces the poll batch into a fixed stack items array ([(Token, Readiness); POLL_EVENTS_CAP], src/serving.rs:1288) — a separate stack-owned buffer, not a reallocated Vec. Distinct from that, the reactor’s boot-retained per-turn events buffer is swapped with Events::with_capacity(0) and restored after polling (src/serving.rs:1263, :1307); that swap/restore property depends on mio not allocating for a zero-capacity buffer and on epoll_wait writing into the pre-existing buffer, and it is exercised by the steady-state allocation witnesses in src/serving/tests.rs.

The honest restatement of the fixed-memory contract is: first-party execution paths do not allocate or deallocate heap storage after boot (boot init is exempt; shutdown exits without deallocating), while dependency behavior is a bounded seam — the DoT profile allocates per connect (per-TLS-upgrade, src/startup_dns.rs:1101-1120, build_tls_connection at :1113-1132). On the retained serving refresh’s one warm successful-exchange fixture, the transport itself must not allocate or reallocate (counts.reallocs == 0), while the bounded rustls seam — the dependency scope — may allocate at most WARM_DOT_ALLOC_BOUND = 8 and deallocate at most 8 independently (src/startup_dns/dot_tests.rs:1371-1381, :1435-1472; per-TLS-upgrade allocation at src/startup_dns.rs:2067-2091). That is a calibrated fixture bound — total heap activity on that single warm exchange, distinct from the retained named storage the inventory reports — never a universal or total-event maximum. The boot-window zero-allocation witness is explicit that it applies to the bare-IP/plain-DNS path only (src/startup_dns/tests.rs:1217-1224).

7.3 The serving concurrency and scheduling envelope

The reactor is a single poll owner (poll: Poll on the Serving struct, src/serving.rs:917). Each turn reads a fixed POLL_EVENTS_CAP = 1024-event snapshot into the boot-reused buffer (src/serving.rs:117), coalescing the tokens into one fixed CoalescedBatch — a two-pass structure whose first pass folds arrivals in order and whose second pass re-dispatches each slot contiguously within a single complete visit (src/serving.rs:478-489, :1341). Per-visit I/O is bounded — VISIT_OPS = 16 ops or 64 KiB per connection visit, whichever comes first, combined across both directions (src/serving.rs:105-106) — timers rejoin the turn at most every TIMER_RECHECK_EVERY = 256 ready-slots or I/O ops (src/serving.rs:111), and per-turn DNS progress advances toward the shared deadline by at most DNS_ADVANCE_BOUND = 8 cooperative steps (src/runtime.rs:24, :421-440), so a chatty or stalled peer can never starve traffic within a turn. Every dispatched token is generation-tagged — low bits are the local id, high bits the slot generation — so a stale event for a reused slot index is dropped before any socket is touched (src/serving.rs:152-162).

Registration tokens are disjoint by construction: the listener holds token 0, client sockets occupy 1..=512, each upstream uses UPSTREAM_BASE + index, and DNS_LOCAL and SIGNAL_LOCAL are reserved. Low bits select the source and high bits carry the slot generation, so a reserved source can never alias a connection; the SIGTERM self-pipe event is handled before every connection event (src/serving.rs:67, :135-162, :1281, :1544-1558).

Slot reuse is metadata-only with one deliberate retention: on tunnel close, SlotWorkspace::reset rebuilds the parser, inspector, gate, capture, deadlines, and other slot metadata through their constructors, but the two retained 128 KiB traffic slabs are not zeroized and are never written out by any current path; they outlive the tunnel by design (src/serving.rs:774-803). The reuse is therefore bounded to within-slot state, with retained buffers a storage decision rather than a disclosure path.

8. Observability and failure

8.1 The boot-owned log ring

Logging is a fixed 256-slot × 2 KiB ring (512 KiB) owned at boot (QUEUE_SLOTS = 256, SLOT_BYTES = 2 * 1024, src/log.rs:53-54), retained as LogStore for process lifetime (src/log.rs:1429-1441), encoded in place, and drained by a single nonblocking write_vectored under a per-turn budget of 16 fragments / 64 KiB (SINK_MAX_OPS = 16, SINK_MAX_BYTES = 64 * 1024, src/log.rs:66-67, :2045-2123). Three properties are architectural:

  1. The sink can never stall serving. fd 1 is made nonblocking once, after boot, by the binary only (prepare_stdout, src/log.rs:1579-1590), and write_vectored either progresses or latches WouldBlock with a retained cursor and a 100 ms retry (LOG_RETRY, src/log.rs:72, :2085-2107). tests/stdout_stall.rs and tests/monitor_stdout.rs are the executable form of this claim.
  2. Drops are always counted, never silent. Ring-full and encode-failure both drop_one (src/log.rs:2163-2174), a hard sink error drops the whole queue through the same counter (:2094-2101), and exit paths strand-count the residue (strand_queued, src/log.rs:1668-1677).
  3. Priority classes exist. A reserved record can displace the newest normal record on a full ring rather than being dropped (enqueue_reserved, src/log.rs:2205-2266) — the mechanism that keeps shutdown/fatal evidence from being evicted by a monitor burst.

8.2 The terminal sink state and its failure consequences

Once the sink latches failed, next_drain returns None forever (src/log.rs:1637-1646): a broken stdout permanently ends observability. There is no second sink: boot diagnostics use stderr (src/main.rs:65-80, :145-148), but once the log store owns stdout there is no fallback channel (src/log.rs:1403-1410). After a hard stdout failure the process may continue with no external log-loss signal: the latch does not exit the process, open another output channel, or by itself alter exit status, and the in-memory dropped counter cannot be emitted through the failed sink (src/log.rs:2094-2101). The sink cannot stall serving; an unrecoverable sink failure is a counted but externally silent loss.

8.3 Incident reporting

IncidentReport is the second observability axis: 32 preallocated per-name windows (names: [NameReport; ALLOWLIST_MAX], src/incident_report.rs:99-119) with REPORT_WINDOW_SECS = 3600 recorded rotation (src/incident_report.rs:14), coalesced skipped windows, sticky per-window incident snapshots, and eligible-binding transition tracking (src/incident_report.rs:99-181, :242-250). Its per-turn pass over all names (src/serve.rs:423-485) is O(32) and bounded, but it runs every turn regardless of whether any window is near a boundary — a small, constant, always-on cost.

8.4 Degradation is observable, never silent

Four counted fact families exist precisely so degradation is observable: resolver_degraded, dns_anomaly, downgrade_to_plain, and probe_relocations are all folded into the monitor (src/enforcement/monitor.rs:16-19), which means a resolver silently degrading is structurally impossible — any relocation or downgrade is a counted fact. This is the positive corollary of “no silent acceptance”: the operator is told, in the fixed monitor record, when the DNS path is less healthy than it was.

8.5 Exit codes and degradation surfaces

Process exit and per-request HTTP degradation are the two fixed failure surfaces; both are typed and unconditional. Exit 0 has two reachable producers: a drained serving shutdown after gate-opened tunnels complete (ShutdownExit::Drained ⇒ 0, src/serving.rs:186, applied through src/runtime.rs:374-377) and a startup Terminated decision (SIGTERM within the startup window), which emits the shutdown record and exits 0 (src/main.rs:104-107). Exit 70 (EX_SOFTWARE) is forced shutdown with undrained tunnels at the deadline (ShutdownExit::Forced ⇒ 70, src/serving.rs:187) and startup serving failures — no bound listener, attach failure, or serve error — each exiting EX_SOFTWARE (src/main.rs:89-107). Every owner.run_startup error maps to EX_CONFIG = 78: StartupError::{Dns, Cache, Listener} — DNS transport/storage, readiness evaluation, and listener bind — plus boot storage, preallocation, and stdout-sink setup failures (src/boot.rs:7; src/main.rs:62-80, :109-112; src/serve.rs:117-128); the startup DNS verdict exits EX_TEMPFAIL = 75 (src/main.rs:103). The terminal-sink latch of §8.2 is the one failure surface where log loss is counted but unrecoverable and externally unreportable while the process runs (src/log.rs:1637-1646, :2094-2101).

9. Security and trust

9.1 Threat model in one paragraph

The spec’s threat model (docs/alumina-proxy.md §Threat model) is a compromised trusted application — the client is trusted at rest and the operator holds full privilege, but compromise is assumed inevitable, so the proxy’s task is to identify the compromise and protect against further exploitation purely through egress. The design consequence is a Golden Path: a correctly configured, healthy workload produces zero deviations, so any observed deviation is by construction a signal.

9.2 Authorization-before-forwarding (the two barriers again)

9.3 TLS and the ClientHello profile

The ClientHello surface is deliberately narrow. Validation enforces a TLS 1.3 profile with no ECH, exactly one SNI that must normalize-equal the approved hostname (L8 — non-host_name server_name entries rejected), and a minimum initial TLS record payload (L9) to reject degenerate framing (src/client_hello.rs:526-528). The inspector holds the flattened message across feeds, copying each record payload exactly once regardless of fragmentation (src/client_hello.rs:410-419). The JA4 fingerprint is retained per slot (the Option<ClientHello> inside ChInspector) as the baseline for the ja4 gate — a per-class gate whose Block{All} scope is legal and reachable, in contrast to early_data’s connection-only block scope (see §6.2; the ja4 grammar keeps the full scope set in src/enforcement/policy.rs:131-135).

9.4 Trust boundary summary — pin-or-nothing, no silent downgrade

Three trust statements summarize the boundary:

  • DoT is pin-or-nothing. With a pin, the peer is authenticated by SPKI + SNI/SAN matching and TLS 1.2/1.3 handshake-signature verification — possession of the pinned certificate's private key (src/startup_dns.rs:839-888). Without a pinned SPKI, chain validation fails deterministically (empty root store) and the resolver is unusable with a startup warning — there is no CA-validated mode in the current build (src/startup_dns.rs:863-870); operator documentation must state this plainly.
  • Failover never downgrades identity. Relocations cannot silently swap a DoT entry to plain DNS; a downgrade is counted as a dp fact (src/startup_dns.rs:3200-3221).
  • Trust is homogeneous or boot fails. A mixed-trust resolver set is rejected at configuration time (src/config.rs:829-836).
