Alumina — Architecture of the DNS-bound exit-gate proxy

A source-grounded description of the as-built system at a fixed revision: the two forwarding barriers, the single-reactor serving loop, the typed enforcement lattice, the fixed-storage memory envelope, and the DoT-bound startup-to-serving DNS path that decides whether the process may listen at all.

All line citations are to that revision and were checked at HEAD; none are copied from another document. Reviewed source equals current source: git diff --stat 3f587e947fa8f050954b2f1fa7ec6b47012ac769..HEAD -- src tests Cargo.toml Cargo.lock is empty (no tracked code, test, or manifest delta), so every citation below names the code that ships at HEAD.

Identity: alumina is a single-binary, config-file driven, DNS-conditional CONNECT proxy. After a startup DNS window of at most 90 s it opens the listener early once every name is usable, else Full or Degraded at the deadline; it enforces a two-barrier forwarding gate per tunnel; it allocates its retained working set once at boot and never frees it — the plain-DNS profile, with a DoT resolver additionally allocating per connect (F-02); and it treats every enforcement deviation as a counted, observable fact rather than a silent pass.

⚠ Critical discoveries at a glance

Eleven source-grounded discoveries (F-01…F-11) are detailed in the critical discoveries register; six open unknowns (U-01…U-06) are listed in the residual unknowns section. The headline items an operator or next maintainer must know before touching this system:

  • F-01 (S2) — an inert operator knob: the [early_data] All-scope enforcement gate cannot arm in production configuration; it is documented, parsed, stored, and consumed, but the only reachable raw effects never fire it. Not a bypass, but a semantics gap.
  • F-02 (S2) — a contract wording gap: “no post-boot heap allocation” holds for the plain-DNS profile only; a DoT resolver allocates on every connect and, on the one warm successful-exchange fixture, up to eight allocations and up to eight deallocations (a calibrated fixture bound, not a universal or total bound). Resolving the fixed-profile mismatch is an owner decision (alumina-szmy0.11).
  • F-03 (S2) — capacity: the retained boot floor is ≈ 204.6 MiB (≈ 409 KiB/tunnel), not the 128 MiB traffic-store headline; the printed lower bound is 214 665 002 bytes.
  • F-04 (S2) — design economy: the per-slot inspector retains 128 KiB (two 64 KiB buffers) to inspect a 16 KiB handshake cap — 64 MiB of the 76.6 MiB serving workspace is inspector headroom.
  • F-05…F-11: two declared-but-unused direct dependencies; a fragile positional two-call exchange protocol; non-zeroized slot reuse; a 21-module public surface for two consumers; terminal silent sink failure; a strong single-clock discipline; per-entry CNAME bailiwick confinement.

1. System purpose and boundary

Alumina is the castle’s exit gate. The specification is explicit (docs/alumina-proxy.md §Design philosophy): it does not police ingress, guard an interior, or inspect payloads; it guards the single exit through which a trusted-at-rest application reaches the outside world, with a fixed and opinionated design rather than a surface of configuration choices. The trust model is not distrust of the system: the application and the operator are trusted at rest, and the operator holds full privilege over both. Alumina exists because compromise is inevitable — when the application is compromised, the proxy’s task is to identify the compromise and protect against further exploitation purely through egress, which is the limit of its visibility and responsibility.

From that task follows the core promise that shapes the whole codebase: no silent acceptance of adversarial behavior and likewise no silent acceptance of internally inconsistent evidence. In the idiomatic deployment the only client is the trusted application on a fixed golden path, so a correctly configured, healthy workload produces zero deviations; the enforcement machinery that follows exists to turn any deviation into a typed, counted fact with a documented effect.

1.1 Boundary: what the binary is allowed to do

  • Fixed input, no policy from the environment. The only configuration input is config.toml relative to the working directory (src/main.rs:22, CONFIG_PATH); no CLI arguments or environment variables are read as policy. The configuration document is size-bounded (≤ 16 KiB at src/config.rs:15, CONFIG_DOC_LIMIT, schema-strict: an unknown key is an error), read once at boot through config::load_config_document (load entry at src/config.rs:706; strict schema and unknown-key rejection at :739-783).
  • Privilege floor. Preflight refuses root, refuses any non-empty effective/permitted/ambient capability set, and requires no_new_privs before the process may proceed (src/preflight.rs:96-116). Exit codes are fixed and documented: 75 EX_TEMPFAIL for the startup DNS verdict, 70 EX_SOFTWARE (given as program exit), 78 EX_CONFIG for configuration failure (src/main.rs:23-24, src/boot.rs:7).
  • Listener conditionality. The listener is opened only when the startup window’s canonical readiness rule holds — the unresolved count must be at most the configured allowance, otherwise the process exits with status 75 (src/serve.rs:97-102, StartupDecision::{Serve,Exit75,Terminated}). A first observed SIGTERM short-circuits the window and never binds.
  • Egress only. Upstream tunnels carry approved hostname traffic; ingress policing, payload inspection, and inter-client traffic are explicitly outside scope (spec §Design philosophy, §non-goals).

Register note — observed as-built for every claim in this subsection; the fixed-input and privilege-floor statements are additionally spec intent (docs/alumina-proxy.md §Configuration & DNS, §Security hardening). The two agree.

1.2 Deployment boundary

The idiomatic deployment places alumina on the same host as the trusted application, listening on the configured listen address (the reference deployment uses a private endpoint), with the application pointed at it as its HTTP CONNECT proxy, and the process holding no elevated privileges. Upstream, the proxy performs its own DNS resolution — a plain-DNS or DoT exchange per query over a retained connection — and connects to the resolved peer on the allowlisted port. Figure 1 shows the boundary and the three surfaces that cross it (config in, tunnel traffic, DNS).

Two deployment facts recorded in source deserve emphasis. First, the startup window is the process’s single admission decision: it runs for at most 90 s, opening the listener early once every allowlist name is usable and, at the deadline, serving Full when none are unresolved or Degraded within the configured allowance, exiting 75 above it; a first-observed SIGTERM short-circuits the window as Terminated and never lets it bind (STARTUP_WINDOW_SECS: u64 = 90, src/startup_dns.rs:49; the readiness rule is the canonical decision of docs/alumina-proxy.md:108). Second, the process is single-threaded for both DNS and serving: one reactor loop, one owner of the poll, one set of timers (src/runtime.rs, src/serving.rs; the worker owns tunnel state inside the same thread — WorkerClock and slot tables live in src/worker.rs). There is no dedicated DoT thread: the only std::thread invocation in production code is the thread::sleep that parks the single thread inside the startup DNS driver (src/startup_dns.rs:25, :2929; resolve_window runs synchronously on the reactor thread before the listener opens, and the serving-time DNS work is cooperative per-turn advance, not a second thread). No thread is ever spawned in production — the only std::thread::spawn/Builder sites in src/serve.rs:1248 and :2170 are #[cfg(test)] doubles. The single thread observes traffic, log, DNS, and shutdown readiness in one combined wait (docs/alumina-proxy.md:146).

2.1 F-01 — the [early_data] All-scope gate is inert (S2)

The enforcement layer attaches one All-scope gate per violation class: bad_handshake, illegal_fqdn, early_data, and ja4 (GateSet, src/enforcement/state.rs:71-77). Each gate’s counter is noted only when the raw decided effect is Effect::Block { scope: All } (src/enforcement/state.rs:272-278). For EarlyUpstreamData the raw effect comes from the per-FQDN control, and the configuration parser rejects any early_data block with a scope other than connection (src/config.rs:1110-1115): ConfigError::EarlyDataBlockScopeInvalid is returned for fqdn or all block scopes. The code comment documents this as the “F-02 close”: an upstream-sourced early-data signal cannot select a per-domain or process-wide latch.

Consequence: the only reachable raw effects for EarlyUpstreamData are BaselineOnly, Unknown, Notify, or Block { Connection } — never Block { All } — so the early_data gate’s counter is never noted and its crossed flag never arms. The section is still parsed (src/config.rs:798-805), validated (:963-999), stored in GateSet, and wired into the counter table (src/enforcement/state.rs:242-246). The unit test that appears to prove reachability builds a ControlTable directly with early_data = Block{All} (src/enforcement/state.rs:1415-1450) — a table state the production parser cannot produce — so the test masks the unreachability rather than refuting it.

The per-connection control still fires, so this is a semantics defect, not an open bypass. Every other property of the layer — first-fact latching, counted Unknown, per-class isolation — is unaffected.

2.2 F-02 — the allocation contract holds for plain DNS only (S2)

The system’s zero-allocation story has a plain-DNS profile and a DoT profile, and the DoT profile allocates. build_tls_connection (src/startup_dns.rs:1098-1120) allocates on every DoT connect: Arc::new(provider), a full ClientConfig (containing Arcs and Vecs), target.fqdn.as_str().to_owned() (a String), an Arc<AluminaServerCertVerifier>, and the rustls ClientConnection with its internal buffers; the connection itself is moved into a Box at :2090-2104.

The warm path still allocates, but bounded: the repository’s own witness — a single warm successful-exchange fixture — asserts up to eight allocations and up to eight deallocations independently against WARM_DOT_ALLOC_BOUND = 8 (src/startup_dns/dot_tests.rs:1340-1348, :1416-1423). That is a calibrated fixture bound, never a universal protocol bound and never an eight-total-event maximum; the fixture counts allocation events on that exchange (per-TLS-upgrade allocation, with close/reconnect paths dropping TLS state, src/startup_dns.rs:2096-2102), which is total heap activity there, distinct from the retained named storage the inventory reports. The boot-window zero-allocation witness is explicit that it applies to the bare-IP/plain-DNS resolver only (src/startup_dns/tests.rs:1217-1224). The claim “no post-boot heap alloc/dealloc” is therefore true for the plain profile and false as written for a DoT profile — a contract-wording problem with a real consequence: a reviewer can read a green alloc-witness run as proof of a global property. Resolving the fixed-profile mismatch is an owner decision (owning bead alumina-szmy0.11); this document does not resolve it. The open conformance question — whether the DoT allocation profile conforms as-is, or an authorised change to the fixed profile follows — is that owner decision; no outcome is chosen here.

2.3 F-03 — retained boot floor ≈ 204.6 MiB, not 128 MiB (S2)

The traffic store alone is 128 MiB: TUNNEL_SLOTS = 512 × BUFFERS_PER_SLOT = 2 × BUFFER_BYTES = 128 * 1024 (src/inventory.rs:9-12), i.e. 134 217 728 bytes. But the retained serving workspaces add 80 310 272 bytes (SERVING_WORKSPACE_BYTES = 512 × SLOT_WORKSPACE_BYTES, src/inventory.rs:36, where SLOT_WORKSPACE_BYTES = size_of::<ConnectParser>() + size_of::<ChInspector>() = 156 856, pinned by the :273-285 ticket test). Together with the DNS named buffers (137 002 bytes = 512 + 16 386 + 120 104, src/inventory.rs:41-44), the printed lower bound is 214 665 002 bytes ≈ 204.7 MiB (src/main.rs:34-40; recorded measurement). Dividing the traffic plus workspace across 512 slots gives ≈ 419 000 bytes ≈ 409 KiB per tunnel.

The inventory is deliberately a lower bound over retained named buffers and explicitly not an RSS estimate (src/inventory.rs:173-196): it excludes per-slot metadata, transient scratch, kernel socket buffers, and allocator fragmentation. Real RSS is therefore strictly higher; see U-03. See also §8 for the full envelope.

2.4 F-04 — inspector headroom: 64 MiB to inspect a 16 KiB cap (S2)

ChInspector retains two [u8; 64 * 1024] buffers (buf and scratch, src/client_hello.rs:410-419) per slot, sized to MAX_CLIENT_HELLO = 64 * 1024 (:6). The inspected handshake, however, is bounded at MAX_HANDSHAKE_LEN = 16 * 1024 (:18) with a per-record payload cap of RECORD_PAYLOAD_LIMIT = 16 * 1024 (:9) — a deliberate interop bound (RFC 8446 §5.1) that rejects rather than reassembles a spec-legal multi-record ClientHello larger than 16 KiB.

The arithmetic: 2 × 64 KiB × 512 slots = 64 MiB of the 76.6 MiB serving workspace is single-connection inspector headroom (≈ 83%). This is not a defect — it may be exactly the margin an adversarial fragmentation fixture needs — but it is the cheapest memory lever in the system and the one most likely to break a fixture if changed. R-6.

2.5 F-05 — two declared-to-import unused dependencies (S3)

rustls-pki-types = "=1.15.1" and rustls-webpki = { version = "=0.103.16", default-features = false, features = ["ring", "std"] } appear in [dependencies] (Cargo.toml:199-200), but a grep over src/ and tests/ finds no direct rustls_pki_types or rustls_webpki import: the source uses the rustls::pki_types re-export (src/startup_dns.rs:36, src/startup_dns/dot_tests.rs:9). They may be retained for a future trust-anchor intake (the verifier comment at src/startup_dns.rs:812-820 anticipates future trust anchors), but as declared today each is an unused pin. R-4.

2.6 F-06 — the positional two-call exchange-class protocol (S3)

StartupDns::start_exchange initialises an ActiveExchange with serving: false, probe: false (src/startup_dns.rs:2971-3007) — the class is not a parameter of the single call. The serving and probe marks are applied by two separate later calls (mark_serving_started, src/runtime.rs:345; mark_probe_started at src/startup_dns.rs:3341, :3411). The runtime’s per-turn cancel_retained_startup_exchange cancels exactly the exchanges that are neither serving nor probe (src/startup_dns.rs:1613-1621, driven from src/runtime.rs:258-262).

This is a fragile seam: the class of an in-flight exchange is whatever two earlier calls last said, so reordering — e.g. starting an exchange, marking it serving, then starting a probe without checking active.is_some() — silently reassigns class. Today every call site is correct and the guard (ExchangeActive, :2977-2979) rejects overlap, but the type makes the mistake easy. R-5 makes the class a parameter of start_exchange.

4. CONNECT and the tunnel sequence

A connection is admitted, parsed, validated, gated, and relayed through the slot’s Stage state machine (src/serving.rs:340-351). The stage machine is a typed, non-public enum with ten states — Idle, ReadingConnect, RunningDecision, Dialing, SendingConnected, ValidatingHello, WritingHello, Relay, Refusing(&'static [u8]), and Closing. Note that this observed as-built set has ten variants; the review register that precedes this document lists nine — the ten-variant set below is the source truth and the discrepancy is flagged in Appendix B.

4.1 Admission and the capacity answer

Admission is bounded by MAX_TUNNELS = TUNNEL_SLOTS = 512 and pending setups by MAX_PENDING_SETUPS = 128 (src/worker.rs:42-45); the spec’s historical “640” figure is explicitly rejected in the code comment (“never 640”). Upstream attempts are paced per tunnel at MAX_UPSTREAM_ATTEMPTS = 4, with an absolute setup deadline of SETUP_DEADLINE_SECS = 10 that is never reset, and per-attempt connect deadlines of CONNECT_DEADLINE_SECS = 2 clipped to the setup deadline (src/worker.rs:48-55).

On admission failure the code writes the fixed BODY_503 = "HTTP/1.1 503 Service Unavailable … no capacity\n" and records a RejectReason::Capacity log (src/serving.rs:1808-1836; body constant at :201-202). Accept re-arms are backed off 100 ms after a transient failure so a hot loop cannot spin (ACCEPT_BACKOFF, src/serving.rs:96-98). A successful admission assigns the slot’s fresh generation, freezes the setup deadline, registers the client on the reactor, and moves the stage to ReadingConnect (src/serving.rs:1819-1836).

4.2 The CONNECT head parse

The head is bounded by MAX_HEADER_LINES = 16 (src/connect.rs:13; the “too many header lines” rejection at :103, :289) and ends at the first CRLFCRLF (:185). Two hardening details are architectural: a bare line feed (a 0x0a not preceded by 0x0d) and a bare carriage return are both rejected rather than tolerated (src/connect.rs:332-340), as required by the spec’s L3 bare-CR rejection. The result limits the parser to the head only — tunnel bytes after the delimiter are never treated as metadata.

4.3 Refusal classes and fixed bodies

The refusal surface is a typed Refusal enum with five cases — BadRequest, Forbidden, NoResolvedAddresses, DialFailed, SetupTimeout — mapping one-to-one onto fixed HTTP bodies so a refusal reason is never reverse-inferred from a byte match (src/serving/policy.rs:8-24). Table 3 lists the mapping.

5. The two-barrier forwarding gate

gate.rs is the authority over byte flow, and it is a pure state machine: no sockets, no I/O, small, fixed-offset, deterministic, and unit-testable (src/gate.rs:1-8). The bytes themselves live in the boot-owned per-slot workspace, so the gate makes decisions only. There are two barriers, and each is an invariant from the spec (docs/alumina-proxy.md §Authorization-Before-Forwarding):

  • Barrier A (client → upstream): no client bytes, including ClientHello, are forwarded before complete validation with exactly one SNI normalized-equal to the approved CONNECT hostname, no ECH, and the TLS 1.3 profile. crate::client_hello::validate supplies the verdict; the gate tracks the hello boundary in the stream.
  • Barrier B (upstream → client): no upstream bytes are forwarded before the gate opens. A successful CONNECT response alone authorizes neither direction.

5.1 The gate state machine

The gate returns a typed UpstreamWrite verdict per client write: BlockedByBarrierA while the hello is not yet fully validated; WritingHello { total } when exactly the validated hello prefix may pass; GateOpened { crossing, relay_from_open } for the single transition that crosses H and may include coalesced trailing bytes; and Open once fully relayed (src/gate.rs:41-67). Upstream activity while barrier B is closed is typed as Activity::{Data, Eof, Reset} (src/gate.rs:74-78); only observation of such activity terminates setup — WouldBlock/readiness alone is not activity (D4, src/gate.rs:66-78).

5.2 The witness-minted hello boundary

ValidatedHello { end } is mintable only with a HelloAccepted witness, which only client_hello::validate can produce — so the gate can never be told a caller-invented hello boundary (src/gate.rs:114-142; the type-level invariant is recorded in Appendix A). A test-only test_new constructor exists under #[cfg(test)] and can never be reached in a production build (src/gate.rs:131-137).

5.3 Gate opening is atomic with the crossing write

The gate opens atomically in the same transition whose successful client→upstream write accounting reaches the end of the validated ClientHello (H), before any subsequent upstream read (D3, src/gate.rs:217-244). A single successful write may cross H and carry coalesced trailing bytes; those trailing bytes are relay-from-open and are already forwarded by that same write (relay_from_open). Ordered progress is kept by monotonic committed offsets, so a partial successful write advances only its own bytes. This is the mechanism that makes “no silent acceptance” hold in the streaming direction: bytes cannot leak across the barrier before the hello is fully validated and authorized.

5.4 GatePhase: the typed tunnel lifecycle

GatePhase is the pure lifecycle carrier of the two-barrier gate — the phase plus the byte-offset ledger for both barriers live in TunnelGate (src/gate.rs:73-90, :93-94). The order is monotonic — AwaitConnect → Connecting → AwaitResponse → Validating → RelayActive — and Terminated is reachable only from the pre-open phases; every terminator forbids forwarding in both directions (TerminateReason, src/gate.rs:63-68).

6. DNS, DoT, and the refresh path

Alumina performs its own resolution over one retained transport with one outstanding query — StartupDns is a hand-rolled nonblocking state machine over a single reusable connection (src/startup_dns.rs:1147-1282). It carries four control planes: the refresh schedule per name × family, resolver failover on counted failure, failback after relocation, and sensor probes that never apply cache state. This section covers the classifier, the DoT profile, the startup decision, and the refresh/retry schedule.

6.1 Resolver classification: FQDN ⇒ DoT, bare IP ⇒ plain, no silent fallback

A resolver entry is either a bare IP (port 53, plain DNS) or an IP-with-attached-FQDN (port DOT_PORT 853, DoT). The FQDN presence is both the DoT signal and the port signal, and there is no silent plain-DNS fallback for a DoT entry (src/resolver.rs:215-235). Trust homogeneity across the resolver set is enforced at configuration time — a mix of trust classes is rejected rather than degraded (ConfigError::MixedResolverTrust, src/config.rs:829-836). The “F-02 close” is a separate guard on the early_data control’s block scope — only connection is legal, so an upstream-sourced early-data signal cannot select a per-domain or process-wide latch (src/config.rs:1074-1082, see F-01).

6.2 DoT trust: pin-or-nothing

The DoT client pins via #pin-sha256= and authenticates the peer three ways: SNI/SAN matching against the server name, a SHA-256 digest of the end-entity certificate’s SPKI compared against the pin when one is configured, and TLS 1.2/1.3 handshake-signature verification with the configured provider algorithms — the peer must prove possession of the pinned certificate’s private key (src/startup_dns.rs:827-859, :861-877). Certificate validity-window exclusion is best-effort and counted only when the DER validity parse succeeds (expired_pin_certs, :846-848); the DER walk fails open, so a parse anomaly reports no warning rather than a rejection (:1074-1085) — pin-or-nothing and fail-open validity parsing stay distinct facts. Without a pin, chain validation runs against an explicitly empty root store and therefore always fails — a deliberate “no trust anchors yet” position that surfaces as startup warnings (src/startup_dns.rs:851-857, src/main.rs:127-143). The result is deliberate: a pin is the only trust. “IP#fqdn without pin” is a deterministically unusable resolver rather than a degraded one — which is a defensible choice that any operator documentation must state plainly.

6.3 The startup decision and its register

The canonical readiness rule (spec docs/alumina-proxy.md:108) is: open the listener when the unresolved count is at most the configured allowance, else exit EX_TEMPFAIL (75). The window is a maximum 90 s (src/startup_dns.rs:49): early closure opens Full the moment every name is usable, while at the deadline it opens Full (zero unresolved) or Degraded (within the allowance). The decision is typed as StartupDecision::{Serve(ServingMode), Exit75{unresolved}, Terminated} (src/serve.rs:97-102): a first-observed SIGTERM short-circuits the window as Terminated, which never binds or attaches a listener. A single 90-second exchange report is carried by StartupOutcome (src/serve.rs:104-112).

Only fully validated outcomes reach the cache: dns::apply_outcome prepares the schedule delta before mutating the cache (src/dns.rs:366-428; prepared deltas at src/schedule.rs:358-391, :502-537), so a DeadlineOverflow leaves both resources untouched. Responses are matched on tid + question fields (qname + qtype + qclass) (src/dns.rs:983-1027); QR/opcode/TC are validated from the response flags, and RCODE is classified or rejected — NOERROR/NXDOMAIN are handled, every other RCODE is refused (:1199-1230) — so RCODE is validated, not a query-equality field; DNAME and trailing bytes are rejected everywhere (:1181-1183).

6.4 Per-entry CNAME bailiwick (F-11)

Each allowlist name derives its own bailiwick: itself plus only the CNAME suffixes it declared. Coverage is per-entry, so one entry’s declared suffixes never widen a neighbour’s trust (src/dns.rs:863-953), and same-bare-name entries across ports must declare byte-identical suffix lists or boot fails with DivergentCnameBailiwick (src/config.rs:1244-1262). The flat union of declared suffixes is bounded by the fixed ALLOWLIST_MAX (32) slot bound, and overflow is fail-stop (src/dns.rs:863-953).

7. Enforcement: violations, effects, gates

The enforcement stack is deliberately small and typed: a violation lattice, a pure violation→effect projection, per-class counted gates, and a monitor that folds counted facts into a fixed record. Its purpose is to make “no silent acceptance” mechanically true — an internally inconsistent observation is reported as Unknown, never silently treated as a pass.

7.1 The violation lattice

There are six top-level Violation cases (src/enforcement/policy.rs:89-97): AnyIllegal { cause } (with four AnyIllegalCause payload classes — KIND_COUNT = 4, :84-87), EarlyUpstreamData, Ja4Change, EvidenceInsufficient, Unattributed, and MissingParseResult. This observed as-built set has six variants, in agreement with the review register that precedes this document (“the violation lattice has six cases”) — there is no count discrepancy here.

The last three cases exist precisely to keep “unknown” out of “harmless”: all three map to Effect::Unknown { reason } (src/enforcement/policy.rs:136-145) and none consumes the first-slot latch. That distinction is the mechanism that makes the “no silent acceptance” invariant honest: evidence that is internally inconsistent is reported as unknown rather than treated as a pass.

7.2 The per-class gates

Gates are per-class: bad_handshake, illegal_fqdn, early_data, and ja4 form GateSet (src/enforcement/state.rs:71-77). Each is an AllScopeGate whose threshold and window_secs are NonZero: NonZero makes only zero parameter values unrepresentable and says nothing about whether a gate can ever arm (src/enforcement/state.rs:26-46). Defaults are threshold 1 in a 900-second window (:12-17).

Arming differs by class. An AnyIllegal counter is noted on every class fact; an early-data or ja4 counter is noted only when the raw decided effect is Effect::Block { scope: All }, and only a raw Effect::Block { scope: All } is gated into an all-scope action (src/enforcement/state.rs:262-334). Each class’s gate counts only that class’s facts: the per-class isolation between bad_handshake and illegal_fqdn is enforced by which counter each cause notes (src/enforcement/state.rs:264-286).

7.3 Typed ordinals and the monitor

DomainOrdinal is a 0-based configured-allowlist ordinal whose payload is a range-bounded u8 index; no table identity is stored, and from_index takes no table (src/enforcement/action.rs:98-132). On lookup the ordinal is validated against the current table’s entry count, so a table with the same or a larger count accepts the value and an out-of-range ordinal yields Unknown/no control (src/enforcement/action.rs:206-230): the type proves an index/range discipline, not table provenance, and attacker-controlled strings are never keys. The monitor (src/enforcement/monitor.rs) folds counted facts into FactCounters — observed as-built counter families: any_illegal (per cause), early_data and ja4 (per ordinal), unknown, resolver degraded, dns anomaly, downgrade-to-plain, probe relocations, expired pin certs, ja4 seed and change, folded by ten note_fact_* recorder methods (src/enforcement/monitor.rs:178-290). Bounded Unix-time windows rotate the IncidentReport at REPORT_WINDOW_SECS = 3600 (recorded measurement; the review register’s “3800 s” does not match source src/incident_report.rs:14).

Counting is not uniform. The monitor’s FactCounters counters saturate and are bounded, and the monitor record itself is encoded in place into the fixed log slot budget; a WindowedCounter gate counter, in contrast, is a plain u32 increment (self.count += 1, src/enforcement/state.rs:148-160) — a saturating add is not what bounds it. Anomaly kinds are discrete (DnsAnomalyKind) so a new sensor can never default to an unrelated class.

The number printed is 214 665 002 bytes ≈ 204.7 MiB, printed as “inventory named fixed buffers (lower bound): traffic 134217728 + serving workspace 80310272 + dns named buffers 137002” (recorded measurement).

  • Included: per-slot traffic buffers; retained parser + inspector (including the retained JA4 arrays as the Option<ClientHello> inside each ChInspector); DNS transport query/response/parse buffers; everything size_of over the retained types yields — with no second hand-maintained factor.
  • Excluded by design: per-slot gate/capture/cursors and the approved hostname, transient scratch, the reserved log queue, kernel socket buffers, allocator fragmentation, and rustls/ring heap. The bound is a lower bound over retained named buffers, never an RSS estimate (src/inventory.rs:173-181).

8.2 The zero-allocation discipline and its DoT caveat

The serving steady state is allocation-free by construction after boot: the slot table is built once by collect() over an exact-size iterator (src/serving.rs:1028-1035, see U-02), and the per-turn event buffer is a fixed POLL_EVENTS_CAP array, not a reallocated Vec (run_once coalesces into a stack array, src/serving.rs:1291-1305). The reactor’s per-turn events buffer is replaced with a zero-capacity buffer and restored — the property depends on mio not allocating for with_capacity(0) (see U-01), src/serving.rs:1263, :1307).

F-02 is the honest restatement: it is not “the process never allocates after boot”; it is “the plain-DNS profile never allocates after boot, and the DoT profile allocates per connect (per-TLS-upgrade, src/startup_dns.rs:2096-2102) — with, on its one warm successful-exchange fixture, up to eight allocations and up to eight deallocations while the transport stays realloc-free; that is total heap activity on that exchange, distinct from the retained named storage the inventory reports, and it is a calibrated fixture bound, not a universal or total bound” (src/startup_dns/dot_tests.rs:1340-1348, :1416-1423). The boot-window zero-allocation witness says so in words (src/startup_dns/tests.rs:1217-1224). Resolving the fixed-profile mismatch is an owner decision (owning bead alumina-szmy0.11); this document does not resolve it.

8.3 The serving concurrency and scheduling envelope

The reactor is a single poll owner (poll: Poll on the Serving struct, src/serving.rs:917). Each turn reads a fixed POLL_EVENTS_CAP = 1024-event snapshot into the boot-reused buffer (src/serving.rs:117), coalescing the tokens into one fixed CoalescedBatch — a two-pass structure whose first pass folds arrivals in order and whose second pass re-dispatches each slot contiguously within a single complete visit (src/serving.rs:478-489, :1341). Per-visit I/O is bounded — VISIT_OPS = 16 ops or 64 KiB per connection visit, whichever comes first, combined across both directions (src/serving.rs:105-106) — timers rejoin the turn at most every TIMER_RECHECK_EVERY = 256 ready-slots or I/O ops (src/serving.rs:111), and per-turn DNS progress advances toward the shared deadline by at most DNS_ADVANCE_BOUND = 8 cooperative steps (src/runtime.rs:24, :419-440), so a chatty or stalled peer can never starve traffic within a turn. Every dispatched token is generation-tagged — low bits are the local id, high bits the slot generation — so a stale event for a reused slot index is dropped before any socket is touched (src/serving.rs:152-162).

9. Observability and failure

9.1 The boot-owned log ring

Logging is a fixed 256-slot × 2 KiB ring (512 KiB) owned at boot (QUEUE_SLOTS = 256, SLOT_BYTES = 2 * 1024, src/log.rs:53-54), retained as LogStore for process lifetime (src/log.rs:1429-1441), encoded in place, and drained by a single nonblocking write_vectored under a per-turn budget of 16 fragments / 64 KiB (SINK_MAX_OPS = 16, SINK_MAX_BYTES = 64 * 1024, src/log.rs:66-67, :2045-2123). Three properties are architectural:

  1. The sink can never stall serving. fd 1 is made nonblocking once, after boot, by the binary only (prepare_stdout, src/log.rs:1579-1590), and write_vectored either progresses or latches WouldBlock with a retained cursor and a 100 ms retry (LOG_RETRY, src/log.rs:72, :2085-2107). tests/stdout_stall.rs and tests/monitor_stdout.rs are the executable form of this claim.
  2. Drops are always counted, never silent. Ring-full and encode-failure both drop_one (src/log.rs:2163-2174), a hard sink error drops the whole queue through the same counter (:2094-2101), and exit paths strand-count the residue (strand_queued, src/log.rs:1668-1677).
  3. Priority classes exist. A reserved record can displace the newest normal record on a full ring rather than being dropped (enqueue_reserved, src/log.rs:2205-2266) — the mechanism that keeps shutdown/fatal evidence from being evicted by a monitor burst.

9.2 The terminal sink state and the failure register

F-09 (S4, accepted-risk). Once the sink latches failed, next_drain returns None forever (src/log.rs:1637-1646): a broken stdout permanently ends observability. There is no second sink: boot diagnostics use stderr (src/main.rs:65-80, :145-148), but once the log store owns stdout there is no fallback channel (src/log.rs:1403-1410), so the only surviving signals are the exit code and the dropped counter. This is a defensible deliberate choice; it should be recorded as accepted risk, not discovered during an incident. R-7.

9.3 Incident reporting

IncidentReport is the second observability axis: 32 preallocated per-name windows (names: [NameReport; ALLOWLIST_MAX], src/incident_report.rs:99-119) with REPORT_WINDOW_SECS = 3600 recorded rotation (src/incident_report.rs:14), coalesced skipped windows, sticky per-window incident snapshots, and eligible-binding transition tracking (src/incident_report.rs:99-181, :242-250). Its per-turn pass over all names (src/serve.rs:431-485) is O(32) and bounded, but it runs every turn regardless of whether any window is near a boundary — a small, constant, always-on cost.

9.4 Degradation is observable, never silent

Four counted fact families exist precisely so degradation is observable: resolver_degraded, dns_anomaly, downgrade_to_plain, and probe_relocations are all folded into the monitor (src/enforcement/monitor.rs:16-19), which means a resolver silently degrading is structurally impossible — any relocation or downgrade is a counted fact with a documented register. This is the positive corollary of “no silent acceptance”: the operator is told, in the fixed monitor record, when the DNS path is less healthy than it was.

9.5 Exit codes and degradation surfaces

Process exit and per-request HTTP degradation are the two fixed failure surfaces; both are typed and unconditional. The shutdown pair comes from ShutdownExit: Drained ⇒ 0 and Forced ⇒ 70 (src/serving.rs:178-187), applied through src/runtime.rs:374-376. Boot and startup failures exit the documented constants — EX_CONFIG = 78 at src/boot.rs:7, EX_TEMPFAIL = 75 and EX_SOFTWARE = 70 at src/main.rs:23-24 — and the terminal-sink latch (F-09) is the one unannounced observability failure: once stdout latches failed, log loss is counted but unrecoverable (src/log.rs:1637-1646).

10. Security and trust

10.1 Threat model in one paragraph

The spec’s threat model (docs/alumina-proxy.md §Threat model) is a compromised trusted application — the client is trusted at rest and the operator holds full privilege, but compromise is assumed inevitable, so the proxy’s task is to identify the compromise and protect against further exploitation purely through egress. The design consequence is a Golden Path: a correctly configured, healthy workload produces zero deviations, so any observed deviation is by construction a signal.

10.3 TLS and the ClientHello profile

The ClientHello surface is deliberately narrow. Validation enforces a TLS 1.3 profile with no ECH, exactly one SNI that must normalize-equal the approved hostname (L8 — non-host_name server_name entries rejected), and a minimum initial TLS record payload (L9) to reject degenerate framing (src/client_hello.rs:526-528). The inspector holds the flattened message across feeds, copying each record payload exactly once regardless of fragmentation (src/client_hello.rs:410-419). The JA4 fingerprint is retained per slot (the Option<ClientHello> inside ChInspector) as the baseline for the ja4 gate — a per-class gate whose Block{All} scope is legal and reachable, unlike early_data (F-01) (Table 8; the ja4 grammar keeps the full scope set in src/enforcement/policy.rs:131-135).

10.4 Trust boundary summary — pin-or-nothing, no silent downgrade

Three trust statements summarize the boundary:

  • DoT is pin-or-nothing. With a pin, the peer is authenticated by SPKI + SNI/SAN matching and TLS 1.2/1.3 handshake-signature verification — possession of the pinned certificate's private key (src/startup_dns.rs:827-859, :861-877). Without a pinned SPKI, chain validation fails deterministically (empty root store) and the resolver is unusable with a startup warning — there is no CA-validated mode in the current build (src/startup_dns.rs:851-857). R-1 proposes documenting this as operator doctrine.
  • Failover never downgrades identity. Relocations cannot silently swap a DoT entry to plain DNS; a downgrade is counted as a dp fact (src/startup_dns.rs:3216-3230).
  • Trust is homogeneous or boot fails. A mixed-trust resolver set is rejected at configuration time (src/config.rs:829-836).

U-02Risk The Vec<SlotWorkspace> is built by collect() from an exact-size iterator (src/serving.rs:1028-1035), so it is one boot allocation; any later growth would allocate post-boot. Depends on Vec’s exact size_hint path — true for this code but not enforced by a type.
U-03Unknown Real RSS includes allocator fragmentation, rustls/ring heap, and the kernel socket buffers for up to 512 × 2 sockets; none of it is modelled by BootInventory, which is explicitly a lower bound (src/inventory.rs:173-181). Requires measurement; out of scope for a source-only reading. See R-3.
U-04Unknown Whether the [early_data] gate is intended to become reachable again if Block{All} is ever legalised for early data (the “F-02 close” comment at src/config.rs:1074-1082 suggests the restriction is intentional and permanent). Intent is not inferable from code; treated as an inert knob, which is the as-built truth. R-2
U-05Risk A DoT deployment refreshes on a single connection with a 5 s exchange deadline; a failed handshake forces a full reconnect (and a fresh rustls config) on the next exchange, with no persistent re-handshake backoff separate from the schedule ladder. Design appears intentional (schedule backoff is [1,2,4,8,16,30], src/schedule.rs:16); flagged as a latency/CPU cost under resolver flapping, not a defect.
U-06Risk SlotWorkspace::reset leaves prior tunnel bytes in the retained 128 KiB slabs for process lifetime (src/serving.rs:774-803). No path writes them out today, but the buffers outlive the tunnel by design (process::exit skips drops). Memory-disclosure only if a future path misuses buf_len; no such path found.
