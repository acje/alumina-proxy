Alumina — Architecture of the DNS-bound exit-gate proxy

A source-grounded description of the as-built system: the two forwarding barriers, the single-reactor serving loop, the typed enforcement lattice, the fixed-storage memory envelope, and the DoT-bound startup-to-serving DNS path that decides whether the process may listen at all.

Provenance: a static, source-derived description of the cited implementation against the governing specification; it asserts no machine content-hash binding to a current revision.

Identity: alumina is a single-binary, config-file driven, DNS-conditional CONNECT proxy. After a startup DNS window of at most 90 s it opens the listener early once every name is usable, else Full or Degraded at the deadline; it enforces a two-barrier forwarding gate per tunnel; it allocates its retained working set once at boot and never frees it — the fixed-memory contract is scoped to first-party execution paths, with dependency behavior a separately accounted, bounded seam (the DoT/TLS alloc profile in particular); and it treats every enforcement deviation as a counted, observable fact rather than a silent pass.

Method: this document is a static reading of the source. Every architectural claim cites src/*.rs, tests/*.rs, or the governing specification (docs/alumina-proxy.md, SHA-256 38ffbda51b293918617a4cfe1195280a56e1e4c8237818d5b74843c2f20e5592). Values the code itself prints or asserts are recorded as measured. No review apparatus — findings, severities, proposals, or open questions — is carried here; the architecture is described as it is built.

Acronyms. DoT = DNS over TLS. SPKI = Subject Public Key Info. JA4 = string hash of TLS client fingerprint features. SNI = Server Name Indication. FQDN = fully qualified domain name. MiB = 10242 bytes.

1. System purpose and boundary

Alumina is the castle’s exit gate. The specification is explicit (docs/alumina-proxy.md §Design philosophy): it does not police ingress, guard an interior, or inspect payloads; it guards the single exit through which a trusted-at-rest application reaches the outside world, with a fixed and opinionated design rather than a surface of configuration choices. The trust model is not distrust of the system: the application and the operator are trusted at rest, and the operator holds full privilege over both. Alumina exists because compromise is inevitable — when the application is compromised, the proxy’s task is to identify the compromise and protect against further exploitation purely through egress, which is the limit of its visibility and responsibility.

From that task follows the core promise that shapes the whole codebase: no silent acceptance of adversarial behavior and likewise no silent acceptance of internally inconsistent evidence. In the idiomatic deployment the only client is the trusted application on a fixed golden path, so a correctly configured, healthy workload produces zero deviations; the enforcement machinery that follows exists to turn any deviation into a typed, counted fact with a documented effect.

1.1 Boundary: what the binary is allowed to do

  • Fixed input, no policy from the environment. The only configuration input is config.toml relative to the working directory (src/main.rs:22, CONFIG_PATH); no CLI arguments or environment variables are read as policy. The configuration document is size-bounded (≤ 16 KiB at src/config.rs:15, CONFIG_DOC_LIMIT, schema-strict: an unknown key is an error), read once at boot through config::load_config_document (load entry at src/config.rs:521; strict schema and unknown-key rejection in from_table at :577-625).
  • Privilege floor. Preflight refuses root, refuses any non-empty effective/permitted/ambient capability set, and requires no_new_privs before the process may proceed (src/preflight.rs:96-116). Exit codes are fixed and documented: 74 EX_IOERR for an unrecoverable stdout sink failure at the serving owner-turn boundary, 75 EX_TEMPFAIL for the startup DNS verdict, 70 EX_SOFTWARE (given as program exit), 78 EX_CONFIG for configuration failure (src/runtime.rs:30, :300-302; src/main.rs:23-24, src/boot.rs:7).
  • Listener conditionality. The listener is opened only when the startup window’s canonical readiness rule holds — the unresolved count must be at most the configured allowance, otherwise the process exits with status 75 (src/serve.rs:100, :983-1001, StartupDecision::{Serve,Exit75,Terminated}). A first observed SIGTERM short-circuits the window and never binds.
  • Egress only. Upstream tunnels carry approved hostname traffic; ingress policing, payload inspection, and inter-client traffic are explicitly outside scope (spec §Design philosophy, §non-goals).

1.2 Deployment boundary

The idiomatic deployment places alumina on the same host as the trusted application, listening on the configured listen address (the reference deployment uses a private endpoint), with the application pointed at it as its HTTP CONNECT proxy, and the process holding no elevated privileges. Upstream, the proxy performs its own DNS resolution — a plain-DNS or DoT exchange per query over a retained connection — and connects to the resolved peer on the allowlisted port. Figure 1 shows the boundary and the three surfaces that cross it (config in, tunnel traffic, DNS).

Two deployment facts recorded in source deserve emphasis. First, the startup window is the process’s single admission decision: it runs for at most 90 s, opening the listener early once every allowlist name is usable and, at the deadline, serving Full when none are unresolved or Degraded within the configured allowance, exiting 75 above it; a first-observed SIGTERM short-circuits the window as Terminated and never lets it bind (STARTUP_WINDOW_SECS: u64 = 90, src/startup_dns.rs:54; the readiness rule is the canonical rule at docs/alumina-proxy.md:110). Second, the process is single-threaded for both DNS and serving: one reactor loop, one owner of the poll, one set of timers (src/runtime.rs, src/serving.rs; the worker owns tunnel state inside the same thread — WorkerClock and slot tables live in src/worker.rs). There is no dedicated DoT thread: the only std::thread invocation in production code is the thread::sleep that parks the single thread inside the startup DNS driver (src/startup_dns.rs:2533, :2639; resolve_window runs synchronously on the reactor thread before the listener opens, at src/startup_dns.rs:2533, and the serving-time DNS work is cooperative per-turn advance, not a second thread). No thread is ever spawned in production — the only std::thread::spawn/Builder sites in production-adjacent code are #[cfg(test)] doubles (src/serve/startup_integration.rs:68). The single thread observes traffic, log, DNS, and shutdown readiness in one combined wait (docs/alumina-proxy.md:146).

Clock authority is single and explicit: one now0 origin plus whole-second offsets threads through worker, cache, DNS, and serving, with the retained worker re-anchored to the DNS epoch at the mount_clock seam when a startup window (or a test) establishes its own elapsed base (src/serve.rs:225; WorkerClock at src/worker.rs:97-105; the window anchor read back via window_start, src/startup_dns.rs:1304).

2. Component ownership

Alumina’s crate root exports 21 public modules (src/lib.rs:4-28) under crate-level deny(clippy::unwrap_used, clippy::expect_used) (src/lib.rs:1-2), which is the first and strongest architectural verb: production code may not unwrap; every expect must carry a proven-bound justification and an #[expect] with a reason (e.g. src/serving.rs:509, src/config.rs:573, src/cache.rs:369-372). The public surface has three consumers: the serving binary (src/main.rs), the test corpus, and the dev-only src/bin/parser_bench.rs developer harness, a distinct binary importing alumina::client_hello::{ChInspector, Inspect, ja4_fingerprint} to drive those two parsing seams in a tight loop (src/bin/parser_bench.rs:1-9, :45; src/lib.rs:4-28). Figure 2 groups the modules into ownership layers and notes the dependency seams that cross the layer boundaries: the DNS outcome adapter mutates reactor-core Cache/Schedules state through the private body dns::publication::apply_outcome (src/dns/publication.rs:17-104), named-re-exported as dns::apply_outcome (src/dns.rs:11); the serving-surface inspector depends on the private-root hostname type FixedHostname (src/client_hello.rs:3), which config names-re-exports rather than owns (src/config.rs:18); and the gate’s two-barrier authority depends on the serving-surface HelloAccepted witness (src/gate.rs:27). Ownership is directional by layer; calls are not exclusively top-down — the seams above are real dependencies, not a strict acyclic layering.

The crate root declares four private modules, the shared kernels and adapter homes that the public surface re-exports rather than owns: enforcement (src/lib.rs:12; a directory module whose mod.rs re-declares the policy/state/action/monitor submodules), hostname (src/lib.rs:17, src/hostname.rs), incident_report (src/lib.rs:18, src/incident_report.rs), and name_rules (src/lib.rs:30-65) — the 21 declared public modules are in addition to these four root-private ownings.

hostname.rs is the single owner of the untrusted-network hostname carrier: FixedHostname with private bytes/len storage, copy semantics, and the normalize-only constructor that lowercases, strips one trailing dot, and applies the shared label rules (src/hostname.rs:7-73). The old public path still resolves: config names-re-exports the same item as config::FixedHostname (src/config.rs:18), so CONNECT and other consumers keep reading the allowlist type while ClientHello imports the canonical hostname carrier with no configuration reference (src/client_hello.rs:3).

name_rules (src/lib.rs:30-65) is the shared hostname-grammar byte kernel: the 253-byte full-name bound (FQDN_MAX_LEN, :31), the 63-byte label bound (MAX_LABEL, :32), a closed four-variant label classifier (LabelFault: Empty/TooLong/ BadHyphen/DisallowedByte, :34-39) behind the crate-private classify_label (:41-58), and the IP-literal-shape predicate is_ip_literal_shape (:60-64). The DNS wire codec is a separate protocol scope, not unified with this policy: it applies its own independent 63-byte wire-label bound on query encoding (write_qname, src/dns.rs:369-403) and on response-name reads inside parse_response (src/dns.rs:937-1094). The boundary adapters keep their intentional strictness — config Fqdn rejects uppercase labels and strips one trailing dot, FixedHostname folds case and strips one trailing dot while accepting an optional single dot only at the very end, and the resolver Fqdn orders wildcard → IDN → syntax rejection and does not normalize — so the shared kernel is a rule-only predicate, never an acceptance authority.

The TLS trust-verification stack is a deliberately minimal and bounded seam. Cargo.toml declares three direct DoT-related manifest entries — rustls, rustls-webpki, and ring (Cargo.toml:208, :209-213, :214-219); two of them, rustls and ring, are direct source imports (src/startup_dns.rs:31-38 for rustls; :754-755 for the ring digest): rustls supplies the TLS 1.3 client (default-features = false), and ring is promoted to a direct dependency so the strict SPKI pin can hash the server’s SubjectPublicKeyInfo directly (rustls keeps its digest surface crate-private). rustls-pki-types is not declared directly — it arrives via rustls and the source imports only the rustls::pki_types re-export, never rustls_pki_types itself (Cargo.toml:209-212; src/startup_dns.rs:36). rustls-webpki is retained as the sole feature-enabler of the ring provider in the resolved graph, not as a source import (Cargo.toml:209-213).

3. CONNECT and the tunnel sequence

A connection is admitted, parsed, validated, gated, and relayed through the slot’s Stage state machine (src/serving.rs:340-351). The stage machine is a typed, non-public enum with ten states — Idle, ReadingConnect, RunningDecision, Dialing, SendingConnected, ValidatingHello, WritingHello, Relay, Refusing(&'static [u8]), and Closing. Nine nominal steps: Accept (not a Stage variant) plus eight Stage variants — ReadingConnect, RunningDecision, Dialing, SendingConnected, ValidatingHello, WritingHello, Relay, Closing; ten enum variants overall, with Idle and the alternate Refusing branch completing the set.

3.1 Admission and the capacity answer

Admission is bounded by MAX_TUNNELS = TUNNEL_SLOTS = 512 and pending setups by MAX_PENDING_SETUPS = 128 (src/worker.rs:42-45); the spec’s historical “640” figure is explicitly rejected in the code comment (“never 640”). Upstream attempts are paced per tunnel at MAX_UPSTREAM_ATTEMPTS = 4, with an absolute setup deadline of SETUP_DEADLINE_SECS = 10 that is never reset, and per-attempt connect deadlines of CONNECT_DEADLINE_SECS = 2 clipped to the setup deadline (src/worker.rs:48-55).

On admission failure the code writes the fixed BODY_503 = "HTTP/1.1 503 Service Unavailable … no capacity\n" and records a RejectReason::Capacity log (src/serving.rs:1848-1860; body constant at :202). Accept re-arms are backed off 100 ms after a transient failure so a hot loop cannot spin (ACCEPT_BACKOFF, src/serving.rs:98). A successful admission assigns the slot’s fresh generation, freezes the setup deadline, registers the client on the reactor, and moves the stage to ReadingConnect (src/serving.rs:1848-1879).

Peer attribution is resolved once per attempt, before the domain-block precheck: run_decision (src/serving.rs:2411-2425) performs the exact-pair lookup — requested host, approved port, and configured control ordinal — via WorkerView::resolve (src/worker.rs:774-783), then samples Instant::now() and hands the resolved context to the worker created at boot (src/serve.rs:176-184). The resolved context carries the request/view binding; the selection consumes that single view — alongside the slot and now — with no independently constructed second view argument (src/worker.rs:809-813, :866-895), and peer_state is bound to the same copied clock (src/worker.rs:834). Each retry re-resolves the pair fresh from the immutable configuration; only the resolved context and its freshness observation are not persisted — the worker’s attempt ledger and the committed slot identity (src/serving.rs:2453-2455) do remain. A pre-Peer refusal carries the requested hostname without setting approved; the reject emitter accepts either the requested or the approved hostname — one hostname, never a second host/port pair (src/serving/reject.rs:17-27, :48-65). The public PeerDecision/ConnectPhase field sets are unchanged (src/worker.rs:255-290).

Handles are linear and typed — SlotIndex during setup, TunnelIndex after graduation, consumed on release — so a stale handle can never free a reused slot (src/worker.rs:312-341, :590-615).

3.2 The CONNECT head parse

The head is bounded by MAX_HEADER_LINES = 16 (src/connect.rs:13; the “too many header lines” rejection at :103, :289) and ends at the first CRLFCRLF (:185). Two hardening details are architectural: a bare line feed (a 0x0a not preceded by 0x0d) and a bare carriage return are both rejected rather than tolerated (src/connect.rs:332-340), as required by the spec’s L3 bare-CR rejection. The result limits the parser to the head only — tunnel bytes after the delimiter are never treated as metadata.

3.4 Tunnel lifetimes and the shutdown deadline

The setup deadline starts at accept and is never reset (SETUP_DEADLINE_SECS, src/worker.rs:51), and connect attempts are clipped to it. The relay idle deadline is 300 s, starting at gate open and reset only on successful tunnel-byte writes — never by readiness alone (IDLE_SECS, src/serving.rs:84). The first orderly EOF starts a 5 s drain that is never reset (DRAIN_SECS, src/serving.rs:88). The first SIGTERM stops admission, closes pending setups, cancels the DNS transport, and fixes an 8 s grace that later signals cannot extend (SHUTDOWN_GRACE, src/serving.rs:93; on_sigterm, src/serving.rs:1584-1597). The single poll timeout folds every deadline into one wait, and the expiry sweep runs before dispatch (poll_timeout, src/serving.rs:3193-3245; expire_sweep, src/serving.rs:3263). A drained shutdown exits 0, a forced close exits 70, resources are released exactly once, and the process exits without deallocating (ShutdownExit, src/serving.rs:178-196).

4. The two-barrier forwarding gate

gate.rs is the authority over byte flow, and it is a pure state machine: no sockets, no I/O, small, fixed-offset, deterministic, and unit-testable (src/gate.rs:1-8). The bytes themselves live in the boot-owned per-slot workspace, so the gate makes decisions only. There are two barriers, and each is an invariant from the spec (docs/alumina-proxy.md §Authorization-Before-Forwarding):

  • Barrier A (client → upstream): no client bytes, including ClientHello, are forwarded before complete validation with exactly one SNI normalized-equal to the approved CONNECT hostname, no ECH, and the TLS 1.3 profile. crate::client_hello::validate supplies the verdict; the gate tracks the hello boundary in the stream.
  • Barrier B (upstream → client): no upstream bytes are forwarded before the gate opens. A successful CONNECT response alone authorizes neither direction.

4.1 The gate state machine

The gate returns a typed UpstreamWrite verdict per client write: BlockedByBarrierA while the hello is not yet fully validated; WritingHello { total } when exactly the validated hello prefix may pass; GateOpened { crossing, relay_from_open } for the single transition that crosses H and may include coalesced trailing bytes; and Open once fully relayed (src/gate.rs:41-67). Upstream activity while barrier B is closed is typed as Activity::{Data, Eof, Reset} (src/gate.rs:54-58); only observation of such activity terminates setup — WouldBlock/readiness alone is not activity (D4, src/gate.rs:246-256).

4.2 The witness-minted hello boundary

ValidatedHello { end } is mintable only with a HelloAccepted witness, which only client_hello::validate can produce — so the gate can never be told a caller-invented hello boundary (src/gate.rs:114-142; the type-level invariant is recorded in Appendix A). A test-only test_new constructor exists under #[cfg(test)] and can never be reached in a production build (src/gate.rs:131-137).

The serving slot holds no copy of the validated boundary: the phase-guarded on_hello_validated records the end in the gate alone (src/gate.rs:196-201), and gate.hello_end() (src/gate.rs:267) is the single read authority — the serving path asks the gate for it (src/serving.rs:2665) and the workspace carries no mirror.

4.3 Gate opening is atomic with the crossing write

The gate opens atomically in the same transition whose successful client→upstream write accounting reaches the end of the validated ClientHello (H), before any subsequent upstream read (D3, src/gate.rs:217-244). A single successful write may cross H and carry coalesced trailing bytes; those trailing bytes are relay-from-open and are already forwarded by that same write (relay_from_open). Ordered progress is kept by monotonic committed offsets, so a partial successful write advances only its own bytes. This is the mechanism that makes “no silent acceptance” hold in the streaming direction: bytes cannot leak across the barrier before the hello is fully validated and authorized.

4.4 GatePhase: the typed tunnel lifecycle

GatePhase is the pure lifecycle carrier of the two-barrier gate — the phase plus the byte-offset ledger for both barriers live in TunnelGate (src/gate.rs:73-90, :93-94). The order is monotonic — AwaitConnect → Connecting → AwaitResponse → Validating → RelayActive — and Terminated is reachable only from the pre-open phases; every terminator forbids forwarding in both directions (TerminateReason, src/gate.rs:63-68).

5. DNS, DoT, and the refresh path

Alumina performs its own resolution over one retained transport with one outstanding query — StartupDns is a hand-rolled nonblocking state machine over a single reusable connection (src/startup_dns.rs:1074). It carries four control planes: the refresh schedule per name × family, resolver failover on counted failure, failback after relocation, and sensor probes that never apply cache state. This section covers the classifier, the DoT profile, the startup decision, the exchange lifecycle, and the refresh/retry schedule.

5.1 Resolver classification: FQDN ⇒ DoT, bare IP ⇒ plain, no silent fallback

A resolver entry is either a bare IP (port 53, plain DNS) or an IP-with-attached-FQDN (port DOT_PORT 853, DoT). The FQDN presence is both the DoT signal and the port signal, and there is no silent plain-DNS fallback for a DoT entry (Nameserver::port() src/resolver.rs:202-208). Trust homogeneity across the resolver set is enforced at configuration time — a mix of trust classes is rejected rather than degraded (ConfigError::MixedResolverTrust, src/config.rs:652). A separate guard restricts the early_data control’s block scope to connection only — an upstream-sourced early-data signal therefore cannot select a per-domain or process-wide latch (src/config.rs:921-928; see §6.2).

5.2 DoT trust: pin-or-nothing

The DoT client pins via #pin-sha256= and authenticates the peer three ways: SNI/SAN matching against the server name, a SHA-256 digest of the end-entity certificate’s SPKI compared against the pin when one is configured, and TLS 1.2/1.3 handshake-signature verification with the configured provider algorithms — the peer must prove possession of the pinned certificate’s private key (src/startup_dns.rs:743-774; the verifier at verify_server_cert :743 with SAN/name matching at :752 and the pin digest at :754-760, and signature checks at :776-792). Certificate validity-window exclusion is best-effort and counted only when the DER validity parse succeeds (:761-762, expired_pin_certs); the DER walk fails open (cert_outside_validity_window, :995), so a parse anomaly reports no warning rather than a rejection — pin-or-nothing and fail-open validity parsing stay distinct facts. Without a pin, chain validation runs against an explicitly empty root store and therefore always fails — a deliberate “no trust anchors yet” position that surfaces as startup warnings (src/startup_dns.rs:766-772, src/main.rs:127-143). The result is deliberate: a pin is the only trust. “IP#fqdn without pin” is a deterministically unusable resolver rather than a degraded one.

5.3 The startup decision and its report

The canonical readiness rule (spec docs/alumina-proxy.md:110) is: open the listener when the unresolved count is at most the configured allowance, else exit EX_TEMPFAIL (75). The window is a maximum 90 s (src/startup_dns.rs:54): early closure opens Full the moment every name is usable, while at the deadline it opens Full (zero unresolved) or Degraded (within the allowance). The decision is typed as StartupDecision::{Serve(ServingMode), Exit75{unresolved}, Terminated} (src/serve.rs:100): a first-observed SIGTERM short-circuits the window as Terminated, which never binds or attaches a listener. A single 90-second exchange report is carried by StartupOutcome (src/serve.rs:109-119).

The startup window is driven cooperatively by the single serving poll: Serving::run_startup_window attaches the retained DNS transport to the serving poll before selection starts and advances the exchange per turn with an ExchangeClass::Startup exchange (src/serving/startup.rs:27-131, :129), so a first observed SIGTERM during the window is seen within one bounded poll instead of being invisible for the window’s full duration.

Only fully validated outcomes reach the cache: the private outcome-application body dns::publication::apply_outcome (src/dns/publication.rs:17-104, named-re-exported as dns::apply_outcome at src/dns.rs:11) prepares the schedule delta before mutating the cache (prepare/commit deltas at src/schedule.rs:358-389 positive, :502-533 negative; map_schedule error projection at src/dns/publication.rs:99-104), so a DeadlineOverflow leaves both resources untouched. Responses are matched on tid + question fields (qname + qtype + qclass) (src/dns.rs:952-994); QR/opcode/TC are validated from the response flags, and RCODE is classified or rejected — NOERROR/NXDOMAIN are handled, every other RCODE is refused (:1100-1131) — so RCODE is validated, not a query-equality field; DNAME and trailing bytes are rejected everywhere (:1041, :1052, :1072).

The startup integration fixtures drive the real startup path: each successful fixture builds its config through the #[cfg(test)]-only constructor that selects a loopback kernel-assigned listener port (0) instead of a pre-probed port (src/serve/startup_integration.rs:25-27; the constructor Config::with_kernel_assigned_test_listener at src/config.rs:1329-1337). The port-0 value exists only in that cfg(test) constructor: the public document parser still rejects port 0 (src/config.rs:114-116), so operator listen remains numeric 1..=65535 and the production bind is unchanged (src/serve.rs:1182). Startup still exercises the real window, readiness, and normal post-readiness bind — the kernel owns the actual listener the bind returns, and the full-serve and kernel-assigned-listener controls assert and connect to that returned address (src/serve/startup_integration.rs:139-156, :352-374). The exit-75 fixture holds an occupied configured address and asserts no listener is bound (src/serve/startup_integration.rs:183-186); a normal-config control asserts an occupied configured address yields the Listener AddrInUse bind error (src/serve/startup_integration.rs:389-395) and that the public parser rejects a zero listen port with ConfigError::InvalidListen (src/serve/startup_integration.rs:396-406). These fixtures add no public API, no listener-ownership change, and no buffer or profile expansion.

5.4 Per-entry CNAME bailiwick

Each allowlist name derives its own bailiwick: itself plus only the CNAME suffixes it declared. Coverage is per-entry, so one entry’s declared suffixes never widen a neighbour’s trust (src/dns.rs:832-898), and same-bare-name entries across ports must declare byte-identical suffix lists or boot fails with DivergentCnameBailiwick (src/config.rs:1064). The flat union of declared suffixes is bounded by the fixed ALLOWLIST_MAX (32) slot bound, and overflow is fail-stop (src/dns.rs:832-898).

5.5 The typed exchange lifecycle

ExchangeClass — Startup, Serving, or Probe — is a parameter of the single start_exchange call, so an exchange’s class is fixed at its start seam rather than by a later mark (the class is stored on the ActiveExchange; start_exchange at src/startup_dns.rs:2673-2684). The retained-resolver refresh path requests a Serving exchange (src/runtime.rs:363-371; start_dns_exchange in src/serve.rs:762), and a cooperative startup window requests Startup (src/serving/startup.rs:129). Per-turn cleanup cancels exactly the Startup-class retained work while serving exchanges stay outstanding: cancel_retained_startup_exchange (src/startup_dns.rs:1535-1542, driven from src/runtime.rs:281) is scoped to the startup class by the typed lifecycle, so no servicing or probe exchange is ever cancelled as leftover startup work. Overlap fails closed: a second start_exchange while one is active returns ExchangeActive and leaves the outstanding exchange, its schedule accounting, and its connection untouched (src/startup_dns.rs:2683-2685).

Transport registration is owned by a private child: Registration is an opaque #[repr(transparent)] wrapper over a two-mode enum — Private, for this transport's own DNS-private poll, or Shared, at the serving owner's single poll token with the armed-interest cache — cache writes and register/re-register/deregister policy branches live there; during I/O-performing synchronization the armed cache is updated only after a successful registry call, while lifecycle invalidation clears it without a registry call where appropriate (src/startup_dns/registration.rs:18, :25, :115). The root state machine keeps the fd and watch token and passes borrowed &Registry/&mut TcpStream into semantic lifecycle calls — begin_connect, private update_interest, shared sync_desired, fallible close versus infallible abandon — so no root site writes the armed cache directly and shared attach is guarded against double-registration (:61, :88, :171, :194; src/startup_dns.rs:1586-1587, :1714-1721, :1733). Interest differs by mode even in one phase: a private connect registers READABLE | WRITABLE while the shared phase-intent map asks only WRITABLE for Connecting and read-only once the query is sent (src/startup_dns/registration.rs:68-69; sync_shared / shared_desired_interest, src/startup_dns.rs:1733, :1747), and each lifecycle edge resets the exchange frame's filled/written/msglen cursor once (reset_exchange_frame, src/startup_dns.rs:1501) after close's deregister outcome clears the cache (:1473-1490).

The DoT serving path refreshes on a single connection with a 5 s exchange deadline (EXCHANGE_DEADLINE_SECS, src/startup_dns.rs:53): a failed handshake forces a full reconnect — and a fresh rustls configuration — on the next exchange (:1918-1952, upgrade_to_tls; build_tls_connection at :1016-1046), with retries governed by the schedule backoff ladder [1,2,4,8,16,30] (src/schedule.rs:16). The kept failure reason distinguishes a pin SPKI mismatch, a SAN/name mismatch, and a missing trust anchor from generic rustls protocol/socket/EOF causes: the cause is captured at the handshake probe and preserved through the initial flight into note_failure. Failover relocates to the next resolver on counted failures (on_exchange_failed, src/startup_dns.rs:3250-3319); failback returns after a 900 s grace with three consecutive successes (FAILBACK_AFTER_SECS, src/startup_dns.rs:603; maybe_begin_failback at :2891-2921, on_exchange_succeeded at :3320-3351). Sensor probes run behind the post-window sweep and sustained-negative corroboration and never apply cache state (maybe_begin_sweep :2945-3032, sweep_next_probe :3033-3096, step_corroboration :3097-3249). A relocation that would downgrade a DoT entry from TLS to plain DNS is counted as a dp monitor fact and never performed silently (note_downgrade_if_dot_to_plain, src/startup_dns.rs:2923-2942; Nameserver::port() src/resolver.rs:202-208).

The retained transport also records a fixed configured-resolver origin on its incident notes, captured at the failure instant so provenance survives failover: every non-probe exchange failure captures the zero-based configured-resolver index active when the exchange failed — before the failover state machine relocates or restores it — into a per-name, per-family latest-failure table (last_failed, src/startup_dns.rs:1112) and onto IncidentNote::Open (src/startup_dns.rs:3377); a serving recovery names the resolver that actually performed it, read at the published-success path (src/startup_dns.rs:2313; an absent resolver set is None, never the primary). The origin is recorded by note_failure (src/startup_dns.rs:3353) from the bounded active-resolver index only, never from untrusted integers, and the per-name, per-family write lands only after the schedule validates the failure; probes never write it and recovery never clears it (historical sticky), while a serving exchange's success never relocates or resets the active index — only the failback counter advances. The per-event actor is emitted immediately with the failed-exchange cause: the serving-loop exchange_failed record's resolver= names the active-resolver index captured before that advance — a pure-sensor Probe or corroboration failure too, since those never write the name-history table, and none of that capture mutates any name, report, or probe metadata; the per-event exchange_failed actor is captured before the advance that settles it (ServeStorage::advance_dns_serving, src/serve.rs:575-585), driven by the bounded DNS_ADVANCE_BOUND serve loop (src/runtime.rs:437-449); the cooperative startup window calls advance_dns directly and never emits exchange_failed. The incident-open and incident-recovery records instead carry the actor captured at the event itself, never a saved-table read at emission: note_failure places the failing origin into IncidentNote::Open (src/startup_dns.rs:3377-3383), the published-success path places the resolver that actually served into IncidentNote::Recovered (src/startup_dns.rs:2313; a recovery after failover reads 1 where the failure origin read 0), and drain_incident_notes (src/serve.rs:696-731) hands each carried actor straight to the incident_open/ incident_recovered emitters. Only the per-family summary pairs a_resolver/aaaa_resolver beside each family reason, read from the immutable ClosedWindow failure snapshot — projected by ClosedWindow::to_summary (src/incident_report.rs:98-131), which turns the captured closed.incident[i] origin/reason, last_positive, per-family counters and window_end into summary fields and converts absolute freshness/retirement deadlines to remaining seconds against the single sample; emit_incident_summary (src/serve.rs:478-510) supplies the SummaryCache live-cache facts (src/incident_report.rs:138-144), never a live current-actor lookup at encoding; every record carries resolver=0… or explicit resolver="unknown" when metadata is absent — no resolver field appears beside a healthy family (no reason present). Eligible loss/recovery records remain name-scoped and never fabricate a resolver.

The startup_warning record (serializer at src/log/encoding.rs:116-142) carries the first observed exchange failure's typed cause in reason= and is enqueued at most once, only after the first observed failure: a failure-free startup window enqueues none, and the best-effort sink may drop before its drain, so delivery is not guaranteed. It is latched behind the first counted failure, where StartupDns::resolve_window emits it on the first ExchangeResult::Failed (src/startup_dns.rs:2617, where WindowLedger::mark_failed returns the one-per-ledger first-failure capture at :501-521), and the cooperative Serving::run_startup_window reaches the same record through ServeStorage::startup_warning_first (src/serving/startup.rs:92-99, src/serve.rs:736-747). The once-guard means reason= is populated only by an actually observed failure — never fabricated for an unattempted or successful exchange — while startup_name stays immutable and startup_final keeps its existing schema.

In the post-window probe sweep's resolver_probe verdict log, the verdict not_probed means the resolver was skipped by the sweep, not that it was unused or failed: the resolver already exercised as the active resolver during the startup window must carry not_probed (docs/alumina-proxy.md:640,647), separate from ok/failed outcome verdicts. No new verdict or record field is added beyond that existing taxonomy.

The reconnect cost of that single-connection refresh path is an as-built measured quantity on the pinned native Linux release binary 4cce1daab61f (§7.2) against a strict-pinned loopback DoT responder (127.0.0.1#dot.test#pin-sha256=Neh7ibmf4XjPYrBqu/hlbW4Ibp23X3uuja0AU85JHgY, port 853), five fresh supervised processes per workload, every process serving the same four successful exchanges (two startup A, two immediate serving AAAA; the qtype multiset was witnessed per run and the run was refused otherwise). Under warm reuse — the responder keeps the accepted connection open — all four exchanges complete on the one retained TLS1.3 connection, with a measured proxy CPU delta of zero clock ticks (CLK_TCK 100, i.e. below the 10 ms tick resolution) per run and no schedule backoff entered. Under resolver flap — the responder closes the connection after each successful answer — each exchange takes a new accepted connection and fresh TLS1.3 handshake: four connections and four handshakes per run against one in warm reuse (4× on the connection/handshake axis). Per-connection connect+TLS+first-query setup stays 0.5–5 ms in both workloads, so the amplified cost is not per-connect latency but the failure-backoff wait: the flap runs show 2.0–3.0 s inter-response gaps against sub-ms in warm reuse, i.e. the schedule backoff ladder [1,2,4,8,16,30] is entered on the serving refreshes, and median wall per four-exchange run rises from ≈1.3 s (warm reuse) to ≈5.3 s (flap), while the measured proxy CPU delta for the whole four-exchange flap run is a median 0.03 s (range 0.02–0.08 s) — CPU is not the amplifier; wall/backoff latency is. Conditions: loopback transport with no packet loss (the only fault injected is a TCP close after each answer), a single responder and single listener, and the fixed four-exchange workload; both workloads share a ≈1 s startup-settlement-to-first-serving-refresh cadence that sits inside the wall figures but is not part of the flap cost. The 5 s exchange deadline and the [1,2,4,8,16,30] ladder are unchanged; this paragraph records the measured cost of the existing behaviour with its conditions and adds no mechanism and carries no acceptance verdict.

6. Enforcement: violations, effects, gates

The enforcement stack is deliberately small and typed: a violation lattice, a pure violation→effect projection, per-class counted gates, and a monitor that folds counted facts into a fixed record. Its purpose is to make “no silent acceptance” mechanically true — an internally inconsistent observation is reported as Unknown, never silently treated as a pass.

6.1 The violation lattice

There are six top-level Violation cases (src/enforcement/policy.rs:89-97): AnyIllegal { cause } (with four AnyIllegalControl payload classes — COUNT = 4, src/enforcement/action.rs:86-95), EarlyUpstreamData, Ja4Change, EvidenceInsufficient, Unattributed, and MissingParseResult.

The last three cases exist precisely to keep “unknown” out of “harmless”: all three map to Effect::Unknown { reason } (src/enforcement/policy.rs:136-145) and none consumes the first-slot latch. That distinction is the mechanism that makes the “no silent acceptance” invariant honest: evidence that is internally inconsistent is reported as unknown rather than treated as a pass.

6.2 The per-class gates

Gates are per-class: bad_handshake, illegal_fqdn, early_data, and ja4 form GateSet (src/enforcement/state.rs:71-77), but the configuration surface accepts only the three sections [bad_handshake], [illegal_fqdn], and [ja4] (src/config.rs:585-624) and rejects an [early_data] gate section at load (reject at :616-617); the GateSet’s early_data slot is always the default (AllScopeGate::default(), :622). Each is an AllScopeGate whose threshold and window_secs are nonzero (NonZeroU32/NonZeroU64): the nonzero types make only zero parameter values unrepresentable and say nothing about whether a gate can ever arm (src/enforcement/state.rs:26-46). Defaults are threshold 1 in a 900-second window (:12-17).

Arming differs by class. An AnyIllegal counter is noted on every class fact; an early-data or ja4 counter is noted only when the raw decided effect is Effect::Block { scope: All }, and only a raw Effect::Block { scope: All } is gated into an all-scope action (src/enforcement/state.rs:262-334). Each class’s gate counts only that class’s facts: the per-class isolation between bad_handshake and illegal_fqdn is enforced by which counter each cause notes (src/enforcement/state.rs:264-286).

The [early_data] gate section is rejected at config load with exit 78 (ConfigError::EarlyDataGateRejected, src/config.rs:468, raised at :616-617), so no boot succeeds carrying it and the all-scope early-data bar cannot be configured at all. The rejection is structural, not an oversight: a per-class all-scope counter is noted only when the raw decided effect is Effect::Block { scope: All } (src/enforcement/state.rs:262-278), and the configuration parser rejects any early_data block whose scope is not connection (ConfigError::EarlyDataBlockScopeInvalid, src/config.rs:921-928; the parser doc comment at :1056-1062 records that restriction). An upstream-sourced early-data signal therefore cannot select a per-domain or process-wide latch (docs/alumina-proxy.md:1018-1020). The only reachable raw effects for EarlyUpstreamData are therefore BaselineOnly, Unknown, Notify, or Block { Connection } — never Block { All } — so the early_data gate’s counter is never noted and its crossed flag never arms. A unit test that builds a ControlTable directly with early_data = Block { All } (src/enforcement/state/tests.rs:1123) exercises the plumbing under a table state the production parser cannot produce, so it documents the unreachability rather than a live path. The per-connection early-data control and the per-FQDN early_data keys remain configurable and fire normally; the gate section itself is a rejected surface, not an inert knob left in place.

6.3 Typed ordinals and the monitor

DomainOrdinal is a 0-based configured-allowlist ordinal whose payload is a range-bounded u8 index; no table identity is stored, and from_index takes no table (src/enforcement/action.rs:98-132). On lookup the ordinal is validated against the current table’s entry count, so a table with the same or a larger count accepts the value and an out-of-range ordinal yields Unknown/no control (src/enforcement/action.rs:206-230): the type proves an index/range discipline against the current table, not table provenance, and attacker-controlled strings are never keys. The monitor (src/enforcement/monitor.rs) folds counted facts into FactCounters — the observed as-built counter families: any_illegal (per cause), early_data and ja4 (per ordinal), unknown, resolver degraded, dns anomaly, downgrade-to-plain, probe relocations, expired pin certs, ja4 seed and change — folded by ten note_fact_* recorder methods (src/enforcement/monitor.rs:178-290). Bounded Unix-time windows rotate the IncidentReport at REPORT_WINDOW_SECS = 3600 (recorded; src/incident_report.rs:14).

Ordinal attribution for the late enforcement readers is an owned projection, not a second lookup. After an approved-slot presence guard, serving resolves the committed identity — the report_name field the peer-commitment branch wrote together with approved and approved_port (src/serving.rs:2453-2455) and that reset clears together with them (src/serving.rs:778-806) — through one fixed ControlTable::ordinal projection (slot_ordinal, src/serving.rs:2324). The three late consumers — the domain-sweep closure (src/serving.rs:2317), the early-upstream-data violation (src/serving.rs:2672-2675), and the JA4 baseline (src/serving.rs:2792-2794) — all read through this same owned projection, so the pair is not re-looked-up late in the request; the hostname-logging, destination-IP deferral, and JA4 deferred-recording guards keep their existing meaning. There is no extra mirror, cache, or field.

Counting is not uniform. The monitor’s FactCounters counters saturate and are bounded, and the monitor record itself is encoded in place into the fixed log slot budget; a WindowedCounter gate counter, in contrast, is a plain u32 increment (self.count += 1, src/enforcement/state.rs:148-160) — a saturating add is not what bounds it. Anomaly kinds are discrete (DnsAnomalyKind) so a new sensor can never default to an unrelated class.

  • Included: per-slot traffic buffers; retained parser + inspector (including the retained JA4 arrays as the Option<ClientHello> inside each ChInspector); DNS transport query/response/parse buffers; everything size_of over the retained types yields — with no second hand-maintained factor.

The printed bound deliberately excludes the remaining retained fixed structures. Their retained capacities: a worker slot table [SlotState; 512] plus free_heap [u16; 512] (src/worker.rs:372-379), a deadline-presence bitmap [u64; 8] = 64 B (src/serving.rs:892-903), the preallocated POLL_EVENTS_CAP = 1024-event snapshot (src/serving.rs:117), the JA4 baseline [[Ja4BaselineEntry;16];32] = 512 × 36 B = 18 432 B (src/serving.rs:584-619), the 64-entry capture ring (src/enforcement/monitor.rs:11-115), 32 incident windows plus 512 slot markers (src/incident_report.rs:301), and the enforcement control table [Control;4] with two [PerFqdnControl;32] (src/enforcement/action.rs:161-232).

Across 512 slots the two arrays’ retained capacity is 64 MiB of the 76.6 MiB serving workspace, ≈ 83%. That capacity is retained capacity with distinct roles, not reclaimable headroom: each 64 KiB buffer is 4× the 16 KiB message bound, and a saving claim would require a concrete record-framing/resizing model rather than arithmetic on the cap.

7.2 The zero-allocation discipline and the DoT seam

The serving steady state is allocation-free by construction after boot: the slot table is built once by collect() over an exact-size iterator (src/serving.rs:1068-1076), so it is one boot allocation and any later growth would allocate post-boot. Per turn, run_once coalesces the poll batch into a fixed stack items array ([(Token, Readiness); POLL_EVENTS_CAP], src/serving.rs:1328) — a separate stack-owned buffer, not a reallocated Vec. Distinct from that, the reactor’s boot-retained per-turn events buffer is swapped with Events::with_capacity(0) and restored after polling (src/serving.rs:1303, :1347); that swap/restore property depends on mio not allocating for a zero-capacity buffer and on epoll_wait writing into the pre-existing buffer, and it is exercised by the steady-state allocation witnesses in src/serving/tests.rs.

The measured witness basis below is historical evidence, recorded on the native Linux candidate at its original revision (HEAD 3a7b4a9451f78c, release 4cce1daab61f, toolchain 1.99.0, alloc-witness enabled). It is a record of the measurement conditions at the time, not a claim of current-candidate native measurement. Two focused alloc-witness tests assert Counts::all_zero() — allocations, deallocations, reallocations, and unphased counts all zero — over the Runtime::turn → Serving::run_once poll/pump paths: hot_relay_turns_compose_with_bounded_stalled_dns (src/runtime/tests.rs:177, Serving phase, 17 hot relays + stalled DNS + backlog + expiry across 900 owner turns) and due_refresh_owner_path_spends_zero_allocations (src/runtime/tests.rs:2722, BackgroundRefresh phase, 200 owner turns). A separate pointer-transfer witness, not a numeric allocation witness, covers the second claim: serving_consumes_boot_traffic_buffers_by_value_not_reallocation (src/serving/tests.rs:128) asserts the boot traffic slabs transfer into the slot workspaces by value: slots[0].buf and slots[511].down keep the TrafficStorage allocation pointers, so no second traffic allocation occurs when the serving workspaces are built. The mio allocation matrix (tests/mio_matrix.rs, alloc-witness-only) measures the same dependency seam: the retained Events heap buffer is attributed to its boot allocation, a later named phase never carries its release, and steady poll/registry/outbound-connect operations stay all_zero(). These counts cover only the executed paths above; they are not a universal bound on unexercised code or dependency-behaviour seams. The swap/restore itself is measured by the owning witnesses asserting zero heap activity once the boot-held events buffer exists; the fixed stack items coalescing array is never a heap allocation at any phase.

The honest restatement of the fixed-memory contract is: first-party execution paths do not allocate or deallocate heap storage after boot (boot init is exempt; shutdown exits without deallocating), with one authorised first-party exception: each DoT dial builds its TLS state at the per-connect setup seam build_tls_connection (src/startup_dns.rs:1016-1046, called at :1932 in upgrade_to_tls :1918-1952), which the specification records as the authorised first-party allocation point (docs/alumina-proxy.md:625-627). Dependency behaviour is a separate bounded seam outside the first-party scope: the pinned rustls performs bounded per-record allocations on an established DoT connection (docs/alumina-proxy.md:625-627). On the retained serving refresh’s one warm successful-exchange fixture, the transport itself must not allocate or reallocate (counts.reallocs == 0), while the bounded rustls seam — the dependency scope — may allocate at most WARM_DOT_ALLOC_BOUND = 8 and deallocate at most 8 independently (src/startup_dns/dot_tests.rs:1381-1393, :1438-1484; per-TLS-upgrade allocation at src/startup_dns.rs:1918-1952). That is a calibrated fixture bound — total heap activity on that single warm exchange, distinct from the retained named storage the inventory reports — never a universal or total-event maximum. The boot-window zero-allocation witness is explicit that it applies to the bare-IP/plain-DNS path only (src/startup_dns/tests.rs:1247-1252, :1283-1284).

7.3 The serving concurrency and scheduling envelope

The reactor is a single poll owner (poll: Poll on the Serving struct, src/serving.rs:957). Each turn reads a fixed POLL_EVENTS_CAP = 1024-event snapshot into the boot-reused buffer (src/serving.rs:117), coalescing the tokens into one fixed CoalescedBatch — a two-pass structure whose first pass folds arrivals in order and whose second pass re-dispatches each slot contiguously within a single complete visit (src/serving.rs:478-489, :1381). Per-visit I/O is bounded — VISIT_OPS = 16 ops or 64 KiB per connection visit, whichever comes first, combined across both directions (src/serving.rs:105-106) — timers rejoin the turn at most every TIMER_RECHECK_EVERY = 256 ready-slots or I/O ops (src/serving.rs:111), and per-turn DNS progress advances toward the shared deadline by at most DNS_ADVANCE_BOUND = 8 cooperative steps (src/runtime.rs:24, :437-449), so a chatty or stalled peer can never starve traffic within a turn. Every dispatched token is generation-tagged — low bits are the local id, high bits the slot generation — so a stale event for a reused slot index is dropped before any socket is touched (src/serving.rs:152-162).

The deterministic visit-budget fixture (run_budget_visit_fixture, src/serving/tests.rs:3794-3928) proves the shared per-visit ledger as built: a full 32 KiB read window, observed via a non-consuming peek within the unchanged 2-second bound, yields one 32 KiB read plus an equal flush and a saturated VisitState ledger of exactly 65,536 bytes (src/serving/tests.rs:3931-3955); a 32,664-byte prefix yields a 65,328-byte ledger with 208 bytes remaining — not exhausted — and is rescheduled under the same independent 16-op/64 KiB caps while the wire payload pattern is conserved byte-for-byte (src/serving/tests.rs:3958-3982; read_room at src/serving.rs:2010).

Registration tokens are disjoint by construction: the listener holds token 0, client sockets occupy 1..=512, each upstream uses UPSTREAM_BASE + index, and DNS_LOCAL and SIGNAL_LOCAL are reserved. Low bits select the source and high bits carry the slot generation, so a reserved source can never alias a connection; the SIGTERM self-pipe event is handled before every connection event (src/serving.rs:67, :135-162, :1317-1322, :1584-1597).

Socket-token pairing is centralized: SlotWorkspace::side_pair(index, Side) returns the (&mut TcpStream, Token) borrowed pair for the chosen side, and the client/upstream register and reregister helpers — register_client, register_upstream, reregister_client, reregister_upstream — all obtain socket and token through that single seam (Side at src/serving.rs:699, side_pair at :808, helpers at :1892-1939), so per-side token arithmetic lives in exactly one place.

Slot reuse is metadata-only with one deliberate retention: on tunnel close, SlotWorkspace::reset rebuilds the parser, inspector, gate, capture, deadlines, and other slot metadata through their constructors, but the two retained 128 KiB traffic slabs are not zeroized and are never written out by any current path; they outlive the tunnel by design (src/serving.rs:778-806). The reuse is therefore bounded to within-slot state, with retained buffers a storage decision rather than a disclosure path.

8. Observability and failure

8.1 The boot-owned log ring

Logging is a fixed 256-slot × 2 KiB ring (512 KiB) owned at boot (QUEUE_SLOTS = 256, SLOT_BYTES = 2 * 1024, src/log.rs:53-54), retained as LogStore for process lifetime (src/log.rs:526-528), encoded in place, and drained by a single nonblocking write_vectored under a per-turn budget of 16 fragments / 64 KiB (SINK_MAX_OPS = 16, SINK_MAX_BYTES = 64 * 1024, src/log.rs:66-67, :1161-1233). Three properties are architectural:

Written bytes commit across one private boundary: drain_sink gathers the fragment set and passes consume_gathered only the written byte count and fragment count; the consumer derives self.front and the saved cursor.off (or 0) once on entry, before any front advance or watermark callback, and reports a mid-record partial so the drain resumes at the exact residue — a zero-written outcome is valid (src/log.rs:1161, :1242-1256).

  1. The sink can never stall serving. fd 1 is made nonblocking once, after boot, by the binary only (prepare_stdout, src/log.rs:678), and write_vectored either progresses or latches a recoverable backpressure condition — WouldBlock, Interrupted, or a zero-progress write — keeping the retained cursor and the 100 ms retry (LOG_RETRY, src/log.rs:72, :1196-1210). None of the three sets the persistent failed latch, so none can trigger the sink-failure exit (sink_has_failed, src/log.rs:796). tests/stdout_stall.rs and tests/monitor_stdout.rs witness the full-pipe case; the injected Interrupted and zero-progress cases are witnessed by logging_writev_interrupted_keeps_cursor_and_stream_identical and logging_writev_zero_progress_keeps_cursor_and_stream_identical (src/log/tests.rs:2181-2207).
  2. Drops are always counted, never silent. Ring-full and encode-failure both drop_one (src/log.rs:1378), a hard sink error drops the whole queue through the same counter (:1204-1211), and exit paths strand-count the residue (strand_queued, src/log.rs:767).
  3. Priority classes exist. A reserved record can displace the newest normal record on a full ring rather than being dropped (enqueue_reserved, src/log.rs:1318) — the mechanism that keeps shutdown/fatal evidence from being evicted by a monitor burst. The displacement victim is never a begun span: a front record with an in-progress sink cursor (cursor.off > 0) finishes unchanged before it can be evicted, an unstarted (off 0) front stays eligible, and when every held record is reserved the newest reserved record is the bounded-not-lossless fallback — displace_reserved (src/log.rs:1360-1376); the witnessed legal-input cases run through a scripted Partial(NonZeroUsize) sink in src/log/tests.rs:2205-2294.

8.2 The terminal sink state and its failure consequences

Once the sink latches failed, next_drain returns None forever (src/log.rs:736): a broken stdout permanently ends observability. There is no second sink: boot diagnostics use stderr (src/main.rs:65-80, :145-148), but once the log store owns stdout there is no fallback channel (src/log.rs:678). The latch is sticky state: no later drain consumes or clears it, so a non-owner drain — the startup-window drains (src/serve.rs:1174, src/serving/startup.rs:166, src/startup_dns.rs:2628, :2824) or the resolver-probe drain (src/serve.rs:880) — that latches the sink is still observed by the first serving owner turn (sink_has_failed, src/log.rs:796). The serving owner therefore exits EX_IOERR (74) at the owner-turn boundary: after the per-turn drain it reads that latch and exits in place unless shutdown has begun (src/runtime.rs:300-302); a shutdown-phase drain (src/runtime.rs:145-153, :413-417) is exit-free, and the shutdown verdict always wins over a latched sink. The in-memory dropped counter cannot itself be emitted through the failed sink, so the process-level exit is the operator’s log-loss signal. The failed latch still cannot stall serving: the owner exits rather than linger with observability permanently lost, and recoverable backpressure — a would-block, interrupted, or zero-progress write — never sets the latch and never exits.

Both shutdown record paths converge on one private, allocation-free finisher, emit_terminal_shutdown_finish (src/runtime.rs:32-42): it snapshots the log_dropped() counter first, writes the single shutdown_final(secs, status, dropped) record, force-runs the monitor summary (report_monitor_if_due(now, true)), then performs exactly one bounded sink drain (SINK_MAX_OPS 16 / SINK_MAX_BYTES 64 KiB, src/log.rs:66-67). Each caller samples the clock once and passes the grouped (now, secs) pair with an explicit ShutdownStatus — no new invariant type. The pre-attach owner (Preallocated::emit_shutdown_and_drain, src/runtime.rs:145-153) samples now/cache_secs before the mutable Serving::shutdown_exit() can force-close sockets, and a not-yet-settled exit (None) becomes the caller-side default Drained; the attached owner (Runtime::emit_shutdown_record_and_drain, src/runtime.rs:413-417) receives the already-settled ShutdownExit from the serve loop and passes its pure status. Delivery is best-effort, never guaranteed: on a full ring a reserve-priority record can displace, and a broken sink drops the drain outright — the single bounded drain is the last synchronised flush before exit, not a delivery promise.

8.3 Incident reporting

IncidentReport is the second observability axis: 32 preallocated per-name windows (names: [NameReport; ALLOWLIST_MAX], src/incident_report.rs:149-169) with REPORT_WINDOW_SECS = 3600 recorded rotation (src/incident_report.rs:14), coalesced skipped windows, sticky per-window incident snapshots, and eligible-binding transition tracking (src/incident_report.rs:149-235, :299-304). Its per-turn pass over all names (src/serve.rs:424-476) is O(32) and bounded, but it runs every turn regardless of whether any window is near a boundary — a small, constant, always-on cost.

8.4 Degradation is observable, never silent

Four counted fact families exist precisely so degradation is observable: resolver_degraded, dns_anomaly, downgrade_to_plain, and probe_relocations are all folded into the monitor (src/enforcement/monitor.rs:16-19), which means a resolver silently degrading is structurally impossible — any relocation or downgrade is a counted fact. This is the positive corollary of “no silent acceptance”: the operator is told, in the fixed monitor record, when the DNS path is less healthy than it was.

8.5 Exit codes and degradation surfaces

Process exit and per-request HTTP degradation are the two fixed failure surfaces; both are typed and unconditional. Exit 0 has two reachable producers: a drained serving shutdown after gate-opened tunnels complete (ShutdownExit::Drained ⇒ 0, src/serving.rs:186, applied through src/runtime.rs:400-403) and a startup Terminated decision (SIGTERM within the startup window), which emits the shutdown record and exits 0 (src/main.rs:104-107). Exit 70 (EX_SOFTWARE) is forced shutdown with undrained tunnels at the deadline (ShutdownExit::Forced ⇒ 70, src/serving.rs:187) and startup serving failures — no bound listener, attach failure, or serve error — each exiting EX_SOFTWARE (src/main.rs:89-107). Every owner.run_startup error maps to EX_CONFIG = 78: StartupError::{Dns, Cache, Listener} — DNS transport/storage, readiness evaluation, and listener bind — plus boot storage, preallocation, and stdout-sink setup failures (src/boot.rs:7; src/main.rs:62-80, :109-112; src/serve.rs:119-130); the startup DNS verdict exits EX_TEMPFAIL = 75 (src/main.rs:103). Exit 74 (EX_IOERR) is an unrecoverable stdout sink failure: the per-turn drain passes the queue, and once the sticky failed latch is set the owner exits in place at the turn unless shutdown has begun (src/runtime.rs:30, :300-302), which is the operator’s log-loss signal for the terminal-sink latch of §8.2 — the one failure surface where log loss is counted and observability ends, so the process exits rather than continue externally unreportable (src/log.rs:736, :1204-1211).

9. Security and trust

9.1 Threat model in one paragraph

The spec’s threat model (docs/alumina-proxy.md §Threat model) is a compromised trusted application — the client is trusted at rest and the operator holds full privilege, but compromise is assumed inevitable, so the proxy’s task is to identify the compromise and protect against further exploitation purely through egress. The design consequence is a Golden Path: a correctly configured, healthy workload produces zero deviations, so any observed deviation is by construction a signal.

9.3 TLS and the ClientHello profile

The ClientHello surface is deliberately narrow. Validation enforces a TLS 1.3 profile with no ECH: the record-layer legacy version must be the TLS 1.2 compatibility value (scan_available, src/client_hello.rs:514-520, :610) and the offered supported_versions must contain non-GREASE TLS 1.3 only (validate_versions, src/client_hello.rs:712-727); an encrypted_client_hello extension is marked present at parse (:677) and rejected by validate (:887-888). Nothing is stored back — no context, cache reference, or lease in the slot and no selected-peer lease across retries; a retry re-resolves from the same cache. Every granted peer folds its per-grant freshness observation into the monitor — Stale sets, Fresh clears (src/serving.rs:2444-2450) — and only incident admission counting is guarded by connect_family.is_none() (src/serving.rs:2488-2499); a stale observation never denies a retry, which may select another servable candidate (src/worker.rs:887-908). The mutable peer-freshness consumer (src/serving.rs:2478) performs no cache lookup of its own.

9.4 Trust boundary summary — pin-or-nothing, no silent downgrade

Three trust statements summarize the boundary:

  • DoT is pin-or-nothing. With a pin, the peer is authenticated by SPKI + SNI/SAN matching and TLS 1.2/1.3 handshake-signature verification — possession of the pinned certificate's private key (src/startup_dns.rs:743-774). Without a pinned SPKI, chain validation fails deterministically (empty root store) and the resolver is unusable with a startup warning — there is no CA-validated mode in the current build (src/startup_dns.rs:766-772).
  • Failover never downgrades identity. Relocations cannot silently swap a DoT entry to plain DNS; a downgrade is counted as a dp fact (src/startup_dns.rs:2923-2942).
  • Trust is homogeneous or boot fails. A mixed-trust resolver set is rejected at configuration time (src/config.rs:652).
