Alumina — Architecture of the DNS-bound exit-gate proxy

A source-grounded description of the as-built system: the two forwarding barriers, the single-reactor serving loop, the typed enforcement lattice, the fixed-storage memory envelope, and the DoT-bound startup-to-serving DNS path that decides whether the process may listen at all.

Provenance: a static, source-derived description of the cited implementation against the governing specification; it asserts no machine content-hash binding to a current revision.

Identity: alumina is a single-binary, config-file driven, DNS-conditional CONNECT proxy. After a startup DNS window of at most 90 s it opens the listener early once every name is usable, else Full or Degraded at the deadline; it enforces a two-barrier forwarding gate per tunnel; it allocates its retained working set once at boot and never frees it — the fixed-memory contract is scoped to first-party execution paths, with dependency behavior a separately accounted, bounded seam (the DoT/TLS alloc profile in particular); and it treats every enforcement deviation as a counted, observable fact rather than a silent pass.

Method: this document is a static reading of the source. Every architectural claim cites src/*.rs, tests/*.rs, or the governing specification (docs/alumina-proxy.md, SHA-256 a3e0d9d5683afeaef495fd574e825a1a49a357907ecb6ff430e88f41fb2377f1). Values the code itself prints or asserts are recorded as measured. No review apparatus — findings, severities, proposals, or open questions — is carried here; the architecture is described as it is built.

Acronyms. DoT = DNS over TLS. SPKI = Subject Public Key Info. JA4 = string hash of TLS client fingerprint features. SNI = Server Name Indication. FQDN = fully qualified domain name. MiB = 10242 bytes.

1. System purpose and boundary

Alumina is the castle’s exit gate. The specification is explicit (docs/alumina-proxy.md §Design philosophy): it does not police ingress, guard an interior, or inspect payloads; it guards the single exit through which a trusted-at-rest application reaches the outside world, with a fixed and opinionated design rather than a surface of configuration choices. The trust model is not distrust of the system: the application and the operator are trusted at rest, and the operator holds full privilege over both. Alumina exists because compromise is inevitable — when the application is compromised, the proxy’s task is to identify the compromise and protect against further exploitation purely through egress, which is the limit of its visibility and responsibility.

From that task follows the core promise that shapes the whole codebase: no silent acceptance of adversarial behavior and likewise no silent acceptance of internally inconsistent evidence. In the idiomatic deployment the only client is the trusted application on a fixed golden path, so a correctly configured, healthy workload produces zero deviations; the enforcement machinery that follows exists to turn any deviation into a typed, counted fact with a documented effect.

1.1 Boundary: what the binary is allowed to do

  • Fixed input, no policy from the environment. The only configuration input is config.toml relative to the working directory (src/main.rs:21, CONFIG_PATH); no CLI arguments or environment variables are read as policy. The configuration document is size-bounded (≤ 16 KiB at src/config/mod.rs:17, CONFIG_DOC_LIMIT, schema-strict: an unknown key is an error), read once at boot through config::load_config_document (load entry at src/config/mod.rs:537; strict schema and unknown-key rejection in from_table at :593-614).
  • Privilege floor. Preflight refuses root, refuses any non-empty effective/permitted/ambient capability set, and requires no_new_privs before the process may proceed (src/boot/preflight.rs:96-116). Exit codes are fixed and documented: 74 EX_IOERR for an unrecoverable stdout sink failure at the serving owner-turn boundary, 75 EX_TEMPFAIL for the startup DNS verdict, 70 EX_SOFTWARE (given as program exit), 78 EX_CONFIG for configuration failure (src/runtime/owner.rs:28, :375-377; src/main.rs:22-23, src/boot/mod.rs:9).
  • Listener conditionality. The listener is opened only when the startup window’s canonical readiness rule holds — the unresolved count must be at most the configured allowance, otherwise the process exits with status 75 (src/runtime/storage.rs:263-273, :1427-1444, :1512-1526, StartupDecision::{Serve,Exit75,Terminated}). A first observed SIGTERM short-circuits the window and never binds.
  • Egress only. Upstream tunnels carry approved hostname traffic; ingress policing, payload inspection, and inter-client traffic are explicitly outside scope (spec §Design philosophy, §non-goals).

1.2 Deployment boundary

The idiomatic deployment places alumina on the same host as the trusted application, listening on the configured listen address (the reference deployment uses a private endpoint), with the application pointed at it as its HTTP CONNECT proxy, and the process holding no elevated privileges. Upstream, the proxy performs its own DNS resolution — a plain-DNS or DoT exchange per query over a retained connection — and connects to the resolved peer on the allowlisted port. Figure 1 shows the boundary and the three surfaces that cross it (config in, tunnel traffic, DNS).

Two deployment facts recorded in source deserve emphasis. First, the startup window is the process’s single admission decision: it runs for at most 90 s, opening the listener early once every allowlist name is usable and, at the deadline, serving Full when none are unresolved or Degraded within the configured allowance, exiting 75 above it; a first-observed SIGTERM short-circuits the window as Terminated and never lets it bind (STARTUP_WINDOW_SECS: u64 = 90, src/dns/transport.rs:55; the readiness rule is the canonical rule at docs/alumina-proxy.md:110). Second, the process is single-threaded for both DNS and serving: one reactor loop, one owner of the poll, one set of timers (src/runtime/owner.rs, src/runtime/reactor.rs; the worker owns tunnel state inside the same thread — WorkerClock and slot tables live in src/runtime/tunnel.rs). There is no dedicated DoT thread: the only std::thread invocation in production code is the thread::sleep that parks the single thread inside the startup DNS driver (src/dns/transport.rs:2932, :2818; resolve_window runs synchronously on the reactor thread before the listener opens, at src/dns/transport.rs:2818, and the serving-time DNS work is cooperative per-turn advance, not a second thread). No thread is ever spawned in production — the only std::thread::spawn/Builder sites in production-adjacent code are #[cfg(test)] doubles (src/runtime/storage/startup_integration.rs:68). The single thread observes traffic, log, DNS, and shutdown readiness in one combined wait (docs/alumina-proxy.md:146). Both waits are bounded — the serving poll and the startup DNS wait each cap at 16 poll invocations per call, Interrupted results included, and yield normally on exhaustion (Serving::SERVING_POLL_INTERRUPT_ALLOWANCE at src/runtime/reactor.rs:1302, in run_once at src/runtime/reactor.rs:1319; StartupDns::POLL_INTERRUPTED_ALLOWANCE at src/dns/transport.rs:1932, in wait_dns_readiness at src/dns/transport.rs:1944).

Clock authority is single and explicit: one now0 origin plus whole-second offsets threads through worker, cache, DNS, and serving, with the retained worker re-anchored to the DNS epoch at the mount_clock seam when a startup window (or a test) establishes its own elapsed base (src/runtime/storage.rs:574-578; WorkerClock at src/runtime/tunnel.rs:88-96; the window anchor read back via window_start, src/dns/transport.rs:1386-1392).

2. Component ownership

Alumina’s crate root exports 11 public domain modules (src/lib.rs:4-15) under crate-level deny(clippy::unwrap_used, clippy::expect_used) (src/lib.rs:1-2), which is the first and strongest architectural verb: production code may not unwrap; every expect must carry a proven-bound justification and an #[expect] with a reason (e.g. src/runtime/reactor.rs:510, src/config/mod.rs:545, src/dns/cache.rs:315-318). The public surface has three consumers: the serving binary (src/main.rs), the test corpus, and the dev-only src/bin/parser_bench.rs developer harness, a distinct binary importing alumina::inspection::{ChInspector, Inspect, ja4_fingerprint} to drive those two parsing seams in a tight loop (src/bin/parser_bench.rs:1-9, :45; src/inspection/mod.rs:4-5). Figure 2 groups the modules into ownership layers and notes the dependency seams that cross the layer boundaries: the DNS outcome adapter mutates reactor-core Cache/Schedules state through the public body dns::publication::apply_outcome (src/dns/publication.rs:45), which delegates through the crate-private apply_route to apply_route_observed (:70-97) that optionally stages reply-derived evidence; named-re-exported as dns::apply_outcome (src/dns/mod.rs:4); the serving-surface inspector depends on the names-owned hostname type FixedHostname (src/inspection/client_hello.rs:3), which the public names root exports rather than config (src/names/mod.rs:4); and the gate’s two-barrier authority depends on the serving-surface HelloAccepted witness (src/runtime/gate.rs:27). Ownership is directional by layer; calls are not exclusively top-down — the seams above are real dependencies, not a strict acyclic layering.

The sole private root module is enforcement (src/lib.rs:9), whose directory module declares the policy/state/action/monitor children. The public domain roots keep their implementation children crate-private: inspection (src/lib.rs:10; the canonical CONNECT/ClientHello tree src/inspection/{connect,client_hello}.rs with the private connect/client_hello child directories for sibling unit tests and the ja4 fingerprint), and names (src/lib.rs:13; src/names/{hostname,rules}.rs). Incident reporting is a crate-private DNS child (src/dns/mod.rs:12, src/dns/incident_report.rs), with its retained value owned by runtime storage, not a public root alias.

hostname.rs is the single owner of the untrusted-network hostname carrier: FixedHostname with private bytes/len storage, copy semantics, and the normalize-only constructor that lowercases, strips one trailing dot, and applies the shared label rules (src/names/hostname.rs:42-73, rules at src/names/rules.rs:11-34). The public path is names::FixedHostname, alongside names::FQDN_MAX_LEN (src/names/mod.rs:4); configuration no longer exports hostname aliases. CONNECT and other consumers import the canonical carrier, while ClientHello imports the canonical hostname carrier with no configuration reference (src/inspection/client_hello.rs:3).

name_rules (src/names/rules.rs:1-34) is the shared hostname-grammar byte kernel: the 253-byte full-name bound (FQDN_MAX_LEN, src/names/rules.rs:1), the 63-byte label bound (MAX_LABEL, :2), a closed four-variant label classifier (LabelFault: Empty/TooLong/ BadHyphen/DisallowedByte, :4-9) behind the crate-private classify_label (:11-28), and the IP-literal-shape predicate is_ip_literal_shape (:30-34). The DNS wire codec is a separate protocol scope, not unified with this policy: it applies its own independent 63-byte wire-label bound on query encoding (write_qname, src/dns/wire.rs:367-403) and on response-name reads inside parse_response (read_name/read_rr, src/dns/wire.rs:492-561, called from the parser :1217-1432). The boundary adapters keep their intentional strictness — config Fqdn rejects uppercase labels and strips one trailing dot before its own payload reaches the shared FixedHostname normalizer as a no-op (src/config/mod.rs:22, :42-74), FixedHostname itself folds case and strips one trailing dot while accepting an optional single dot only at the very end, and the resolver Fqdn orders wildcard → IDN → syntax rejection and reaches the same FixedHostname payload normalizer as a no-op, never letting the normalizer alter acceptance — so the shared kernel is a rule-only predicate, never an acceptance authority.

The TLS trust-verification stack is a deliberately minimal and bounded seam. Cargo.toml declares three direct DoT-related manifest entries — rustls, rustls-webpki, and ring (Cargo.toml:208, :209-213, :214-219); two of them, rustls and ring, are direct source imports (src/dns/transport.rs:31-38 for rustls; :806-812 for the ring digest): rustls supplies the TLS 1.3 client (default-features = false), and ring is promoted to a direct dependency so the strict SPKI pin can hash the server’s SubjectPublicKeyInfo directly (rustls keeps its digest surface crate-private). rustls-pki-types is not declared directly — it arrives via rustls and the source imports only the rustls::pki_types re-export, never rustls_pki_types itself (Cargo.toml:209-212; src/dns/transport.rs:36). rustls-webpki is retained as the sole feature-enabler of the ring provider in the resolved graph, not as a source import (Cargo.toml:209-213).

The current exact pins for configuration parsing and signal integration are toml = 1.2.0 with defaults disabled and only std/parse/serde, and signal-hook = 0.4.6 with defaults disabled (Cargo.toml:193, :201). The direct dev pin is libc = 0.2.191, shared with production dependencies in the resolved graph (Cargo.toml:226, Cargo.lock). The lock also selects toml_writer 1.2.0+spec-1.1.0; the selected parser features do not enable TOML display (Cargo.toml:193, Cargo.lock).

3. CONNECT and the tunnel sequence

A connection is admitted, parsed, validated, gated, and relayed through the slot’s Stage state machine (src/runtime/reactor.rs:341-352). The stage machine is a typed, non-public enum with ten states — Idle, ReadingConnect, RunningDecision, Dialing, SendingConnected, ValidatingHello, WritingHello, Relay, Refusing(&'static [u8]), and Closing. Nine nominal steps: Accept (not a Stage variant) plus eight Stage variants — ReadingConnect, RunningDecision, Dialing, SendingConnected, ValidatingHello, WritingHello, Relay, Closing; ten enum variants overall, with Idle and the alternate Refusing branch completing the set.

3.1 Admission and the capacity answer

Admission is bounded by MAX_TUNNELS = TUNNEL_SLOTS = 512 and pending setups by MAX_PENDING_SETUPS = 128 (src/runtime/tunnel.rs:44-47); the spec’s historical “640” figure is explicitly rejected in the code comment (“never 640”). Upstream attempts are paced per tunnel at MAX_UPSTREAM_ATTEMPTS = 4, with an absolute setup deadline of SETUP_DEADLINE_SECS = 10 that is never reset, and per-attempt connect deadlines of CONNECT_DEADLINE_SECS = 2 clipped to the setup deadline (src/runtime/tunnel.rs:50-57).

On admission failure the code writes the fixed BODY_503 = "HTTP/1.1 503 Service Unavailable … no capacity\n" and records a RejectReason::Capacity log (src/runtime/reactor.rs:1907-1919; body constant at :203). Accept re-arms are backed off 100 ms after a transient failure so a hot loop cannot spin (ACCEPT_BACKOFF, src/runtime/reactor.rs:99). A successful admission assigns the slot’s fresh generation, freezes the setup deadline, registers the client on the reactor, and moves the stage to ReadingConnect (src/runtime/reactor.rs:1907-1938).

Peer attribution is resolved once per attempt, before the domain-block precheck: run_decision (src/runtime/reactor.rs:2470-2484) performs the exact-pair lookup — requested host, approved port, and configured control ordinal — via WorkerView::resolve (src/runtime/tunnel.rs:773-782), then samples Instant::now() and hands the resolved context to the worker created at boot (src/runtime/storage.rs:349-364). The resolved context carries the request/view binding; the selection consumes that single view — alongside the slot and now — with no independently constructed second view argument (src/runtime/tunnel.rs:799-803, :873-902), and peer_state is bound to the same copied clock (src/runtime/tunnel.rs:824-829). Each retry re-resolves the pair fresh from the immutable configuration; only the resolved context and its freshness observation are not persisted — the worker’s attempt ledger and the committed slot identity (src/runtime/reactor.rs:2512-2514) do remain. A pre-Peer refusal carries the requested hostname without setting approved; the reject emitter accepts either the requested or the approved hostname — one hostname, never a second host/port pair (src/runtime/reactor/reject.rs:17-27, :48-65). The public PeerDecision/ConnectPhase field sets are unchanged (src/runtime/tunnel.rs:248-282).

Handles are linear and typed — SlotIndex during setup, TunnelIndex after graduation, consumed on release — so a stale handle can never free a reused slot (src/runtime/tunnel.rs:304-330, :581-607).

3.2 The CONNECT head parse

The head is bounded by MAX_HEADER_LINES = 16 (src/inspection/connect.rs:15; the “too many header lines” rejection at :64, :292) and ends at the first CRLFCRLF (:186). Two hardening details are architectural: a bare line feed (a 0x0a not preceded by 0x0d) and a bare carriage return are both rejected rather than tolerated (src/inspection/connect.rs:334-342), as required by the spec’s L3 bare-CR rejection. The result limits the parser to the head only — tunnel bytes after the delimiter are never treated as metadata.

3.4 Tunnel lifetimes and the shutdown deadline

The setup deadline starts at accept and is never reset (SETUP_DEADLINE_SECS, src/runtime/tunnel.rs:53), and connect attempts are clipped to it. The first SIGTERM stops admission, closes pending setups, cancels the DNS transport, and fixes an 8 s grace that later signals cannot extend (SHUTDOWN_GRACE, src/runtime/reactor.rs:94; on_sigterm, src/runtime/reactor.rs:1643-1656). 4. The two-barrier forwarding gate

runtime/gate.rs is the authority over byte flow, and it is a pure state machine: no sockets, no I/O, small, fixed-offset, deterministic, and unit-testable (src/runtime/gate.rs:1-8). The bytes themselves live in the boot-owned per-slot workspace, so the gate makes decisions only. There are two barriers, and each is an invariant from the spec (docs/alumina-proxy.md §Authorization-Before-Forwarding):

  • Barrier A (client → upstream): no client bytes, including ClientHello, are forwarded before complete validation with exactly one SNI normalized-equal to the approved CONNECT hostname, no ECH, and the TLS 1.3 profile. crate::client_hello::validate supplies the verdict; the gate tracks the hello boundary in the stream.
  • Barrier B (upstream → client): no upstream bytes are forwarded before the gate opens. A successful CONNECT response alone authorizes neither direction.

4.1 The gate state machine

The gate returns a typed UpstreamWrite verdict per client write: BlockedByBarrierA while the hello is not yet fully validated; WritingHello { total } when exactly the validated hello prefix may pass; GateOpened { crossing, relay_from_open } for the single transition that crosses H and may include coalesced trailing bytes; and Open once fully relayed (src/runtime/gate.rs:41-67). Upstream activity while barrier B is closed is typed as Activity::{Data, Eof, Reset} (src/runtime/gate.rs:54-58); only observation of such activity terminates setup — WouldBlock/readiness alone is not activity (D4, src/runtime/gate.rs:246-256).

4.2 The witness-minted hello boundary

ValidatedHello { end } is mintable only with a HelloAccepted witness, which only client_hello::validate can produce — so the gate can never be told a caller-invented hello boundary (src/runtime/gate.rs:114-142; the type-level invariant is recorded in Appendix A). A test-only test_new constructor exists under #[cfg(test)] and can never be reached in a production build (src/runtime/gate.rs:130-135).

The serving slot holds no copy of the validated boundary: the phase-guarded on_hello_validated records the end in the gate alone (src/runtime/gate.rs:196-201), and gate.hello_end() (src/runtime/gate.rs:267) is the single read authority — the serving path asks the gate for it (src/runtime/reactor.rs:2743-2747) and the workspace carries no mirror.

4.3 Gate opening is atomic with the crossing write

The gate opens atomically in the same transition whose successful client→upstream write accounting reaches the end of the validated ClientHello (H), before any subsequent upstream read (D3, src/runtime/gate.rs:217-244). A single successful write may cross H and carry coalesced trailing bytes; those trailing bytes are relay-from-open and are already forwarded by that same write (relay_from_open). Ordered progress is kept by monotonic committed offsets, so a partial successful write advances only its own bytes. This is the mechanism that makes “no silent acceptance” hold in the streaming direction: bytes cannot leak across the barrier before the hello is fully validated and authorized.

4.4 GatePhase: the typed tunnel lifecycle

GatePhase is the pure lifecycle carrier of the two-barrier gate — the phase plus the byte-offset ledger for both barriers live in TunnelGate (src/runtime/gate.rs:73-90, :93-94). The order is monotonic — AwaitConnect → Connecting → AwaitResponse → Validating → RelayActive — and Terminated is reachable only from the pre-open phases; every terminator forbids forwarding in both directions (TerminateReason, src/runtime/gate.rs:63-68).

5. DNS, DoT, and the refresh path

Alumina performs its own resolution over one retained transport with one outstanding query — StartupDns is a hand-rolled nonblocking state machine over a single reusable connection (src/dns/transport.rs:1127). It carries four control planes: the refresh schedule per name × family, resolver failover on counted failure, failback after relocation, and sensor probes that never apply cache state. This section covers the classifier, the DoT profile, the startup decision, the exchange lifecycle, and the refresh/retry schedule.

5.1 Resolver classification: FQDN ⇒ DoT, bare IP ⇒ plain, no silent fallback

A resolver entry is either a bare IP (port 53, plain DNS) or an IP-with-attached-FQDN (port DOT_PORT 853, DoT). The FQDN presence is both the DoT signal and the port signal, and there is no silent plain-DNS fallback for a DoT entry (Nameserver::port() src/dns/resolver.rs:192-198). Trust homogeneity across the resolver set is enforced at configuration time — a mix of trust classes is rejected rather than degraded (ConfigError::MixedResolverTrust, src/config/mod.rs:679-683). A separate guard restricts the early_data control’s block scope to connection only — an upstream-sourced early-data signal therefore cannot select a per-domain or process-wide latch (src/config/mod.rs:1001-1015; see §6.2).

5.2 DoT trust: pin-or-nothing

The DoT client pins via #pin-sha256= and authenticates the peer three ways: SNI/SAN matching against the server name, a SHA-256 digest of the end-entity certificate’s SPKI compared against the pin when one is configured, and TLS 1.2/1.3 handshake-signature verification with the configured provider algorithms — the peer must prove possession of the pinned certificate’s private key (src/dns/transport.rs:795-825; the verifier at verify_server_cert :795 with SAN/name matching at :804 and the strict pin comparison at :805-816, and signature checks at :828-844). Certificate validity-window exclusion is best-effort and counted only when the DER validity parse succeeds (:813-815, expired_pin_certs); the DER walk fails open (cert_outside_validity_window, :1047-1053), so a parse anomaly reports no warning rather than a rejection — pin-or-nothing and fail-open validity parsing stay distinct facts. Without a pin, chain validation runs against an explicitly empty root store and therefore always fails — a deliberate “no trust anchors yet” position that surfaces as startup warnings (src/dns/transport.rs:818-825, src/main.rs:121-137). The result is deliberate: a pin is the only trust. “IP#fqdn without pin” is a deterministically unusable resolver rather than a degraded one.

5.3 The startup decision and its report

The canonical readiness rule (spec docs/alumina-proxy.md:110) is: open the listener when the unresolved count is at most the configured allowance, else exit EX_TEMPFAIL (75). The window is a maximum 90 s (src/dns/transport.rs:55): early closure opens Full the moment every name is usable, while at the deadline it opens Full (zero unresolved) or Degraded (within the allowance). The decision is typed as StartupDecision::{Serve(ServingMode), Exit75{unresolved}, Terminated} (src/runtime/storage.rs:269-273): a first-observed SIGTERM short-circuits the window as Terminated, which never binds or attaches a listener. A single 90-second exchange report is carried by StartupOutcome (src/runtime/storage.rs:289-296).

The startup window is driven cooperatively by the single serving poll: Serving::run_startup_window attaches the retained DNS transport to the serving poll before selection starts and advances the exchange per turn with an ExchangeClass::Startup exchange (src/runtime/reactor/startup.rs:28-131, :129), so a first observed SIGTERM during the window is seen within one bounded poll instead of being invisible for the window’s full duration.

Both startup drivers share WindowLedger, which records an attempt for each configured-name and address-family pair and copies its fixed 32-by-2 Boolean array into StartupReport in allowlist ordinal order, with A before AAAA. It also retains each family's latest concluded published kind or failure independently of current cache usability. When no conclusion is retained, the attempt bit distinguishes an attempted family from an unattempted one; a prior conclusion can remain after a further attempt starts. Superseded exchanges do not replace a conclusion. The existing aggregate counts and per-name outcomes remain separate (src/dns/transport.rs:408-447, :472-484, :509-517, :536-567, :2769-2785, :2888-2912, src/runtime/reactor/startup.rs:77-94, src/dns/transport.rs:3928-3934).

The later queue encoder reads that value rather than the cache or clock; an invalid ordinal returns a cache error before enqueue, and a delayed record does not rewind the queue's current second. Both startup drivers invoke the shared settlement; at a full, degraded, or failed decision, after any required listener bind succeeds, it captures each entry at the same decision second and makes one boot-frame enqueue attempt. A listener bind failure attempts no boot frames. The decision second saturates at the clock limit, matching the ledger refresh clock rather than wrapping to an earlier instant. A frame includes the startup status, each family's attempted bit and last conclusion separately from the cached family facts; a capture error is reported as an unknown cache snapshot without altering the decision. Termination does not emit boot frames. Each allowlist name derives its own bailiwick: itself plus only the CNAME suffixes it declared. 5.5 The typed exchange lifecycle

ExchangeClass — Startup, Serving, or Probe — is a parameter of the single start_exchange call, so an exchange’s class is fixed at its start seam rather than by a later mark (the class is stored on the ActiveExchange; start_exchange_impl at src/dns/transport.rs:2970-3009). The retained-resolver refresh path requests a Serving exchange (prepare_serving_dns_turn at src/runtime/storage.rs:1731-1737; start_dns_exchange in src/runtime/storage.rs:1166-1188), and a cooperative startup window requests Startup (src/runtime/reactor/startup.rs:129). Per-turn cleanup cancels exactly the Startup-class retained work while serving exchanges stay outstanding: cancel_retained_startup_exchange (src/dns/transport.rs:1626-1634, driven from the storage-owned prepare_serving_dns_turn at src/runtime/storage.rs:1732) is scoped to the startup class by the typed lifecycle, so no servicing or probe exchange is ever cancelled as leftover startup work. Overlap fails closed: a second start_exchange while one is active returns ExchangeActive and leaves the outstanding exchange, its schedule accounting, and its connection untouched (src/dns/transport.rs:2978-2980).

The receive path turns one parsed reply into cache or probe state through an observer owned by src/dns/wire.rs: ParsedReply binds the parsed Outcome to the extreme-TTL flag, the raw header AD bit, and the retained supporting-TTL cap — pure copies of the TTL predicate, of the one asserted flag, and of the reusable workspace's conservative raw supporting-TTL minimum, all captured by that same successful parse and bound together in one private closed tagged carrier — the raw AD bit, the extreme flag, and an exact 32-bit supporting-TTL minimum, or the two flag bits alone when a validated negative has no covering SOA and the supporting lifetime is unknown (parse_reply, src/dns/wire.rs:1022; the same-parse capture body :1030-1048; the struct at :1008; the AD read at :1032 from the AD_FLAG mask :347; the workspace field :753 and its getter :786), so no effect is counted at capture time. The cap is a raw observation only: it keeps, for a fully validated positive, the minimum across the supporting CNAME-chain TTLs and the requested-family terminal address TTLs; for a fully validated NODATA or NXDOMAIN with a covering SOA, the minimum across the CNAME chain, the SOA TTL, and the SOA MINIMUM; a validated NXDOMAIN with no SOA carries None (the supporting lifetime is unknown); and a raw zero TTL is preserved un-clamped. A NODATA without a covering SOA is rejected, not retained as an unknown outcome. The positive Outcome.ttl already carried the same raw chain/address minimum, so ordinary positive-TTL publication is unchanged, and the negative supporting-chain minimum is a conservative raw-lifetime observation consumed only by the private negative signatures below — not the schedule's SOA-only TTL rule — a raw value that alone is not authentication yet still participates in the current assurance gate. The reconnect cost of that single-connection refresh path is an as-built measured quantity on the pinned native Linux release binary 4cce1daab61f (§7.2) against a strict-pinned loopback DoT responder (127.0.0.1#dot.test#pin-sha256=Neh7ibmf4XjPYrBqu/hlbW4Ibp23X3uuja0AU85JHgY, port 853), five fresh supervised processes per workload, every process serving the same four successful exchanges (two startup A, two immediate serving AAAA; the qtype multiset was witnessed per run and the run was refused otherwise). Under warm reuse — the responder keeps the accepted connection open — all four exchanges complete on the one retained TLS1.3 connection, with a measured proxy CPU delta of zero clock ticks (CLK_TCK 100, i.e. below the 10 ms tick resolution) per run and no schedule backoff entered. Under resolver flap — the responder closes the connection after each successful answer — each exchange takes a new accepted connection and fresh TLS1.3 handshake: four connections and four handshakes per run against one in warm reuse (4× on the connection/handshake axis). Per-connection connect+TLS+first-query setup stays 0.5–5 ms in both workloads, so the amplified cost is not per-connect latency but the failure-backoff wait: the flap runs show 2.0–3.0 s inter-response gaps against sub-ms in warm reuse, i.e. the schedule backoff ladder [1,2,4,8,16,30] is entered on the serving refreshes, and median wall per four-exchange run rises from ≈1.3 s (warm reuse) to ≈5.3 s (flap), while the measured proxy CPU delta for the whole four-exchange flap run is a median 0.03 s (range 0.02–0.08 s) — CPU is not the amplifier; wall/backoff latency is. Conditions: loopback transport with no packet loss (the only fault injected is a TCP close after each answer), a single responder and single listener, and the fixed four-exchange workload; both workloads share a ≈1 s startup-settlement-to-first-serving-refresh cadence that sits inside the wall figures but is not part of the flap cost. The 5 s exchange deadline and the [1,2,4,8,16,30] ladder are unchanged; this paragraph records the measured cost of the existing behaviour with its conditions and adds no mechanism and carries no acceptance verdict.

The refresh side of that schedule is owned by the same reactor turn: the non-shutdown branch of turn delegates the consolidated DNS lifecycle selection to storage via prepare_serving_dns_turn (src/runtime/owner.rs:358, src/runtime/storage.rs:1731-1737): it cancels a retained startup exchange, advances the post-window probe sweep, steps the corroboration, then starts a due serving refresh (start_due_serving_refresh, src/runtime/storage.rs:1215-1243). The per-turn DNS advance that follows runs the bounded eight-step cooperative loop (src/runtime/owner.rs:456-472), so refresh admission and resolution advance share one bounded turn. Each DoT query-write buffers the remaining length-prefixed plaintext through the rustls in-memory writer, a memory step never charged against the socket attempt budget, then flushes the outbound ciphertext nonblockingly under a fixed 16 socket attempts per advance (src/dns/transport.rs:3849, :3867, :3905-3925). 5.6 Cache lifetime and the generation guard

The cache stores validated bindings only, keyed by configured name × Family (A/Aaaa) with a fixed address capacity of MAX_ADDRESSES = 16 per name and family (src/dns/cache.rs:7). EntryState is a deadline-derived view, never stored: Empty | Fresh | Stale | Retired are computed from the freshness and retirement deadlines (src/dns/cache.rs:101-117). Every publish is generation-guarded: a validated in-flight result carries the current Generation, and publish_positive refuses any mismatch (StaleGeneration), so a stale publish can never overwrite a newer entry (src/dns/cache.rs:557-620).

Negative publications carry the same guard through a paired query-start capture owned by the cache: Cache::generations_before_query (src/dns/cache.rs:501-514) snapshots the queried family's entry generation and the other family's together from the live cache before any network work, shared by the startup and serving exchange paths (src/dns/transport.rs:3162-3167, src/runtime/storage.rs:1178-1182). The crate-private production route re-checks that pair before mutating: reject_obsolete_generation (src/dns/publication.rs:217-277, invoked at :109) refuses with StaleGeneration when an obsolete NXDOMAIN would overwrite newer state — comparing both families' current generations — or an obsolete NODATA would, comparing the queried family only and requiring the outcome's family to be the queried one. 6. Enforcement: violations, effects, gates

The enforcement stack is deliberately small and typed: a violation lattice, a pure violation→effect projection, per-class counted gates, and a monitor that folds counted facts into a fixed record. Its purpose is to make “no silent acceptance” mechanically true — an internally inconsistent observation is reported as Unknown, never silently treated as a pass.

6.1 The violation lattice

There are six top-level Violation cases (src/enforcement/policy.rs:89-97): AnyIllegal { cause } (with four AnyIllegalControl payload classes — COUNT = 4, src/enforcement/action.rs:86-95), EarlyUpstreamData, Ja4Change, EvidenceInsufficient, Unattributed, and MissingParseResult.

The last three cases exist precisely to keep “unknown” out of “harmless”: all three map to Effect::Unknown { reason } (src/enforcement/policy.rs:136-145) and none consumes the first-slot latch. That distinction is the mechanism that makes the “no silent acceptance” invariant honest: evidence that is internally inconsistent is reported as unknown rather than treated as a pass.

6.2 The per-class gates

Gates are per-class: bad_handshake, illegal_fqdn, early_data, and ja4 form GateSet (src/enforcement/state.rs:71-77), but the configuration surface accepts only the three sections [bad_handshake], [illegal_fqdn], and [ja4] (src/config/mod.rs:644-654) and rejects an [early_data] gate section at load (reject at :645-647); the GateSet’s early_data slot is always the default (AllScopeGate::default(), :651). Each is an AllScopeGate whose threshold and window_secs are nonzero (NonZeroU32/NonZeroU64): the nonzero types make only zero parameter values unrepresentable and say nothing about whether a gate can ever arm (src/enforcement/state.rs:26-46). Defaults are threshold 1 in a 900-second window (:12-17).

Arming differs by class. An AnyIllegal counter is noted on every class fact; an early-data or ja4 counter is noted only when the raw decided effect is Effect::Block { scope: All }, and only a raw Effect::Block { scope: All } is gated into an all-scope action (src/enforcement/state.rs:262-334). Each class’s gate counts only that class’s facts: the per-class isolation between bad_handshake and illegal_fqdn is enforced by which counter each cause notes (src/enforcement/state.rs:264-286).

The [early_data] gate section is rejected at config load with exit 78 (ConfigError::EarlyDataGateRejected, src/config/mod.rs:342, raised at :645-647), so no boot succeeds carrying it and the all-scope early-data bar cannot be configured at all. The rejection is structural, not an oversight: a per-class all-scope counter is noted only when the raw decided effect is Effect::Block { scope: All } (src/enforcement/state.rs:262-278), and the configuration parser rejects any early_data block whose scope is not connection (ConfigError::EarlyDataBlockScopeInvalid, src/config/mod.rs:1001-1015; the parser doc comment at :978-984 records that restriction). An upstream-sourced early-data signal therefore cannot select a per-domain or process-wide latch (docs/alumina-proxy.md:1018-1020). The only reachable raw effects for EarlyUpstreamData are therefore BaselineOnly, Unknown, Notify, or Block { Connection } — never Block { All } — so the early_data gate’s counter is never noted and its crossed flag never arms. A unit test that builds a ControlTable directly with early_data = Block { All } (src/enforcement/state/tests.rs:1123) exercises the plumbing under a table state the production parser cannot produce, so it documents the unreachability rather than a live path. The per-connection early-data control and the per-FQDN early_data keys remain configurable and fire normally; the gate section itself is a rejected surface, not an inert knob left in place.

6.3 Typed ordinals and the monitor

DomainOrdinal is a 0-based configured-allowlist ordinal whose payload is a range-bounded u8 index; no table identity is stored, and from_index takes no table (src/enforcement/action.rs:98-132). On lookup the ordinal is validated against the current table’s entry count, so a table with the same or a larger count accepts the value and an out-of-range ordinal yields Unknown/no control (src/enforcement/action.rs:206-230): the type proves an index/range discipline against the current table, not table provenance, and attacker-controlled strings are never keys. The monitor (src/enforcement/monitor.rs) folds counted facts into FactCounters — the observed as-built counter families: any_illegal (per cause), early_data and ja4 (per ordinal), unknown, resolver degraded, dns anomaly, downgrade-to-plain, probe relocations, expired pin certs, ja4 seed and change — folded by ten note_fact_* recorder methods (src/enforcement/monitor.rs:178-290). Bounded Unix-time windows rotate the IncidentReport at REPORT_WINDOW_SECS = 3600 (recorded; src/dns/incident_report.rs:14).

Ordinal attribution for the late enforcement readers is an owned projection, not a second lookup. After an approved-slot presence guard, serving resolves the committed identity — the report_name field the peer-commitment branch wrote together with approved and approved_port (src/runtime/reactor.rs:2512-2514) and that reset clears together with them (src/runtime/reactor.rs:779-807) — through one fixed ControlTable::ordinal projection (slot_ordinal, src/runtime/reactor.rs:2383). The three late consumers — the domain-sweep closure (src/runtime/reactor.rs:2376), the early-upstream-data violation (src/runtime/reactor.rs:2743-2758), and the JA4 baseline (src/runtime/reactor.rs:2866-2886) — all read through this same owned projection, so the pair is not re-looked-up late in the request; the hostname-logging, destination-IP deferral, and JA4 deferred-recording guards keep their existing meaning. There is no extra mirror, cache, or field.

Counting is not uniform. The monitor’s FactCounters counters saturate and are bounded, and the monitor record itself is encoded in place into the fixed log slot budget; a WindowedCounter gate counter, in contrast, is a plain u32 increment (self.count += 1, src/enforcement/state.rs:148-160) — a saturating add is not what bounds it. Anomaly kinds are discrete (DnsAnomalyKind) so a new sensor can never default to an unrelated class.

  • Included: per-slot traffic buffers; retained parser + inspector (including the retained JA4 arrays as the Option<ClientHello> inside each ChInspector); DNS transport query/response/parse buffers; everything size_of over the retained types yields — with no second hand-maintained factor.

The printed bound deliberately excludes the remaining retained fixed structures. That capacity is retained capacity with distinct roles, not reclaimable headroom: each 64 KiB buffer is 4× the 16 KiB message bound, and a saving claim would require a concrete record-framing/resizing model rather than arithmetic on the cap.

7.2 The zero-allocation discipline and the DoT seam

The serving steady state is allocation-free by construction after boot: the slot table is built once by collect() over an exact-size iterator (src/runtime/reactor.rs:1073-1080), so it is one boot allocation and any later growth would allocate post-boot. Per turn, run_once coalesces the poll batch into a fixed stack items array ([(Token, Readiness); POLL_EVENTS_CAP], src/runtime/reactor.rs:1387) — a separate stack-owned buffer, not a reallocated Vec. Distinct from that, the reactor’s boot-retained per-turn events buffer is swapped with Events::with_capacity(0) and restored after polling (src/runtime/reactor.rs:1321, :1406); that swap/restore property depends on mio not allocating for a zero-capacity buffer and on epoll_wait writing into the pre-existing buffer, and it is exercised by the steady-state allocation witnesses in src/runtime/reactor/tests.rs.

The measured witness basis below is historical evidence, recorded on the native Linux candidate at its original revision (HEAD 3a7b4a9451f78c, release 4cce1daab61f, toolchain 1.99.0, alloc-witness enabled). It is a record of the measurement conditions at the time, not a claim of current-candidate native measurement. Two focused alloc-witness tests assert Counts::all_zero() — allocations, deallocations, reallocations, and unphased counts all zero — over the Runtime::turn → Serving::run_once poll/pump paths: hot_relay_turns_compose_with_bounded_stalled_dns (src/runtime/owner/tests.rs:2911, Serving phase, 17 hot relays + stalled DNS + backlog + expiry across 900 owner turns) and due_refresh_owner_path_spends_zero_allocations (src/runtime/owner/tests.rs:4007, BackgroundRefresh phase, 200 owner turns). A separate pointer-transfer witness, not a numeric allocation witness, covers the second claim: serving_consumes_boot_traffic_buffers_by_value_not_reallocation (src/runtime/reactor/tests.rs:1041-1050) asserts the boot traffic slabs transfer into the slot workspaces by value: slots[0].buf and slots[511].down keep the TrafficStorage allocation pointers, so no second traffic allocation occurs when the serving workspaces are built. The mio allocation matrix (tests/mio_matrix.rs, alloc-witness-only) measures the same dependency seam: the retained Events heap buffer is attributed to its boot allocation, a later named phase never carries its release, and steady poll/registry/outbound-connect operations stay all_zero(). These counts cover only the executed paths above; they are not a universal bound on unexercised code or dependency-behaviour seams. The swap/restore itself is measured by the owning witnesses asserting zero heap activity once the boot-held events buffer exists; the fixed stack items coalescing array is never a heap allocation at any phase.

The honest restatement of the fixed-memory contract is: first-party execution paths do not allocate or deallocate heap storage after boot (boot init is exempt; shutdown exits without deallocating), with one authorised first-party exception: each DoT dial builds its TLS state at the per-connect setup seam build_tls_connection (src/dns/transport.rs:1068-1087, called at :2100 in upgrade_to_tls :2085-2121), which the specification records as the authorised first-party allocation point (docs/alumina-proxy.md:625-627). Dependency behaviour is a separate bounded seam outside the first-party scope: the pinned rustls performs bounded per-record allocations on an established DoT connection (docs/alumina-proxy.md:625-627). On the retained serving refresh’s one warm successful-exchange fixture, the transport itself must not allocate or reallocate (counts.reallocs == 0), while the bounded rustls seam — the dependency scope — may allocate at most WARM_DOT_ALLOC_BOUND = 8 and deallocate at most 8 independently (src/dns/transport/dot_tests.rs:1452, :1572-1576; per-TLS-upgrade allocation at src/dns/transport.rs:2085-2121). That is a calibrated fixture bound — total heap activity on that single warm exchange, distinct from the retained named storage the inventory reports — never a universal or total-event maximum. The boot-window zero-allocation witness is explicit that it applies to the bare-IP/plain-DNS path only (src/dns/transport/tests.rs:1745, :1771, :1778).

7.3 The serving concurrency and scheduling envelope

The reactor is a single poll owner (poll: Poll on the Serving struct, src/runtime/reactor.rs:958). Each turn reads a fixed POLL_EVENTS_CAP = 1024-event snapshot into the boot-reused buffer (src/runtime/reactor.rs:118), coalescing the tokens into one fixed CoalescedBatch — a two-pass structure whose first pass folds arrivals in order and whose second pass re-dispatches each slot contiguously within a single complete visit (src/runtime/reactor.rs:479-489, :1440). Per-visit I/O is bounded — VISIT_OPS = 16 ops or 64 KiB per connection visit, whichever comes first, combined across both directions (src/runtime/reactor.rs:106-107) — timers rejoin the turn at most every TIMER_RECHECK_EVERY = 256 ready-slots or I/O ops (src/runtime/reactor.rs:112), and per-turn DNS progress advances toward the shared deadline by at most DNS_ADVANCE_BOUND = 8 cooperative steps (src/runtime/owner.rs:22, :456-472), so a chatty or stalled peer can never starve traffic within a turn. Every dispatched token is generation-tagged — low bits are the local id, high bits the slot generation — so a stale event for a reused slot index is dropped before any socket is touched (src/runtime/reactor.rs:153-163).

Two sources fold into the turn's wait with distinct roles. ServeStorage::refresh_wake is the pure DNS schedule contribution (src/runtime/storage.rs:553-572): fed the caller-supplied Instant and the shutdown-derived suspension condition (overdue_suspended — a scalar query context, not an admission flag or permission), it returns None while an exchange is in flight or while no slot is selectable — nothing scheduled, or only a consumed pending slot — and otherwise maps the due through schedule_due_instant (src/runtime/storage.rs:537-540): an overdue due wakes now, or now + 100 ms while the post-boot probing sweep is active or the owner is suspended, and a future due always maps exactly, even while suspended. It never samples a clock and never selects or mutates work. Serving::poll_timeout itself is not pure (src/runtime/reactor.rs:3272-3308): it samples now, commits the cached slot-only next_expiry snapshot from slot deadlines alone (src/runtime/reactor.rs:3283), then folds the global minimum over slot, DNS-exchange, shutdown, log and schedule wakes and returns that Duration. run_once then folds the assurance wake and caller timeout into the final wait (src/runtime/reactor.rs:1323-1345); that wait is global, never slot-only. The distinct startup-window ledger, window-clipped deadline and sibling-release selection (src/runtime/reactor/startup.rs:104-127) remain a separate scheduling seam.

The deterministic visit-budget fixture (run_budget_visit_fixture, src/runtime/reactor/tests.rs:265-403) proves the shared per-visit ledger as built: a full 32 KiB read window, observed via a non-consuming peek within the unchanged 2-second bound, yields one 32 KiB read plus an equal flush and a saturated VisitState ledger of exactly 65,536 bytes (src/runtime/reactor/tests.rs:5772-5797); a 32,664-byte prefix yields a 65,328-byte ledger with 208 bytes remaining — not exhausted — and is rescheduled under the same independent 16-op/64 KiB caps while the wire payload pattern is conserved byte-for-byte (src/runtime/reactor/tests.rs:5799-5824; read_room at src/runtime/reactor.rs:2069).

Registration tokens are disjoint by construction: the listener holds token 0, client sockets occupy 1..=512, each upstream uses UPSTREAM_BASE + index, and DNS_LOCAL and SIGNAL_LOCAL are reserved. Low bits select the source and high bits carry the slot generation, so a reserved source can never alias a connection; the SIGTERM self-pipe event is handled before every connection event (src/runtime/reactor.rs:68, :136-163, :1375-1380, :1642-1655).

Socket-token pairing is centralized: SlotWorkspace::side_pair(index, Side) returns the (&mut TcpStream, Token) borrowed pair for the chosen side, and the client/upstream register and reregister helpers — register_client, register_upstream, reregister_client, reregister_upstream — all obtain socket and token through that single seam (Side at src/runtime/reactor.rs:700, side_pair at :809, helpers at :1951-1998), so per-side token arithmetic lives in exactly one place.

Slot reuse is metadata-only with one deliberate retention: on tunnel close, SlotWorkspace::reset rebuilds the parser, inspector, gate, capture, deadlines, and other slot metadata through their constructors, but the two retained 128 KiB traffic slabs are not zeroized and are never written out by any current path; they outlive the tunnel by design (src/runtime/reactor.rs:779-807). The reuse is therefore bounded to within-slot state, with retained buffers a storage decision rather than a disclosure path.

8. Observability and failure

8.1 The boot-owned log ring

Logging is a fixed 256-slot × 2 KiB ring (512 KiB) owned at boot (QUEUE_SLOTS = 256, SLOT_BYTES = 2 * 1024, src/log/mod.rs:53-54), retained as LogStore for process lifetime (src/log/mod.rs:536-548, constructed at :643-648, :674-701), encoded in place, and drained by a single nonblocking write_vectored under a per-turn budget of 16 fragments / 64 KiB (SINK_MAX_OPS = 16, SINK_MAX_BYTES = 64 * 1024, src/log/mod.rs:66-67, src/log/sink.rs:100-179). Three properties are architectural:

Written bytes commit across one private boundary: drain_sink gathers the fragment set and passes consume_gathered only the written byte count and fragment count; the consumer derives self.front and the saved cursor.off (or 0) once on entry, before any front advance or watermark callback, and reports a mid-record partial so the drain resumes at the exact residue — a zero-written outcome is valid (src/log/sink.rs:100-179, :180-194).

  1. The sink can never stall serving. fd 1 is made nonblocking once, after boot, by the binary only (prepare_stdout, src/log/sink.rs:16-31), and write_vectored either progresses or latches a recoverable backpressure condition — WouldBlock, Interrupted, or a zero-progress write — keeping the retained cursor and the 100 ms retry (LOG_RETRY, src/log/mod.rs:72, clamp in src/log/sink.rs:100-179). None of the three sets the persistent failed latch, so none can trigger the sink-failure exit (sink_has_failed, src/log/sink.rs:87-99). tests/stdout_stall.rs and tests/monitor_stdout.rs witness the full-pipe case; the injected Interrupted and zero-progress cases are witnessed by logging_writev_interrupted_keeps_cursor_and_stream_identical and logging_writev_zero_progress_keeps_cursor_and_stream_identical (src/log/tests.rs:2267-2277).
  2. Drops are always counted, never silent. Ring-full and encode-failure both drop_one (src/log/queue.rs:100-116, :229-237), a hard sink error drops the whole queue through the same counter (src/log/sink.rs:100-179), and exit paths strand-count the residue (strand_queued, src/log/sink.rs:61-73).
  3. Priority classes exist. A reserved record can displace the newest normal record on a full ring rather than being dropped (enqueue_reserved, src/log/queue.rs:172-199) — the mechanism that keeps shutdown/fatal evidence from being evicted by a monitor burst. The displacement victim is never a begun span: a front record with an in-progress sink cursor (cursor.off > 0) finishes unchanged before it can be evicted, an unstarted (off 0) front stays eligible, and when every held record is reserved the newest reserved record is the bounded-not-lossless fallback — displace_reserved (src/log/queue.rs:212-228); the witnessed legal-input cases run through a scripted Partial(NonZeroUsize) sink in src/log/tests.rs:180-282.

8.2 The terminal sink state and its failure consequences

Once the sink latches failed, next_drain returns None forever (src/log/sink.rs:32-47): a broken stdout permanently ends observability. There is no second sink: boot diagnostics use stderr (src/main.rs:64-79, :139-142), but once the log store owns stdout there is no fallback channel (src/log/sink.rs:16-31). The latch is sticky state: no later drain consumes or clears it, so a non-owner drain — the startup-window drains (src/runtime/storage.rs:1647-1653, src/runtime/reactor/startup.rs:166, src/dns/transport.rs:2921, :3177-3179) or the resolver-probe drain (src/runtime/storage.rs:1323-1324) — that latches the sink is still observed by the first serving owner turn (sink_has_failed, src/log/sink.rs:87-99). The serving owner therefore exits EX_IOERR (74) at the owner-turn boundary: after the per-turn drain it reads that latch and exits in place unless shutdown has begun (src/runtime/owner.rs:375-377); a shutdown-phase drain (src/runtime/owner.rs:201-209, :419-423) is exit-free, and the shutdown verdict always wins over a latched sink. The in-memory dropped counter cannot itself be emitted through the failed sink, so the process-level exit is the operator’s log-loss signal. The failed latch still cannot stall serving: the owner exits rather than linger with observability permanently lost, and recoverable backpressure — a would-block, interrupted, or zero-progress write — never sets the latch and never exits.

Both shutdown record paths converge on one private, allocation-free finisher, emit_terminal_shutdown_finish (src/runtime/owner.rs:30-40): it snapshots the log_dropped() counter first, writes the single shutdown_final(secs, status, dropped) record, force-runs the monitor summary (report_monitor_if_due(now, true)), then performs exactly one bounded sink drain (SINK_MAX_OPS 16 / SINK_MAX_BYTES 64 KiB, src/log/mod.rs:66-67). Each caller samples the clock once and passes the grouped (now, secs) pair with an explicit ShutdownStatus — no new invariant type. The pre-attach owner (Preallocated::emit_shutdown_and_drain, src/runtime/owner.rs:201-209) samples now/cache_secs before the mutable Serving::shutdown_exit() can force-close sockets, and a not-yet-settled exit (None) becomes the caller-side default Drained; the attached owner (Runtime::emit_shutdown_record_and_drain, src/runtime/owner.rs:419-423) receives the already-settled ShutdownExit from the serve loop and passes its pure status. Delivery is best-effort, never guaranteed: on a full ring a reserve-priority record can displace, and a broken sink drops the drain outright — the single bounded drain is the last synchronised flush before exit, not a delivery promise.

8.3 Incident reporting

IncidentReport is the second observability axis: 32 preallocated per-name windows (names: [NameReport; ALLOWLIST_MAX], src/dns/incident_report.rs:149-169) with REPORT_WINDOW_SECS = 3600 recorded rotation (src/dns/incident_report.rs:14), coalesced skipped windows, sticky per-window incident snapshots, and eligible-binding transition tracking (src/dns/incident_report.rs:149-235, :299-304). Its per-turn pass over all names (src/runtime/storage.rs:784-858) is O(32) and bounded, but it runs every turn regardless of whether any window is near a boundary — a small, constant, always-on cost.

The eligibility fold passes the cache lookup result to the incident owner. A successful result updates the existing transition tracker; a lookup error leaves that tracker untouched and attempts one dns_assurance_fault with phase=incident and the typed cache reason. This does not change the separate window rotation or recovery pass (src/runtime/storage.rs:800-855, src/log/mod.rs:614-631; docs/alumina-proxy.md:1857-1867). The foreign-index, full-ring, and serving-phase allocation witnesses exercise that boundary (src/runtime/storage/tests.rs:100, :146, :182).

8.4 Degradation is observable, never silent

Four counted fact families exist precisely so degradation is observable: resolver_degraded, dns_anomaly, downgrade_to_plain, and probe_relocations are all folded into the monitor (src/enforcement/monitor.rs:16-19), which means a resolver silently degrading is structurally impossible — any relocation or downgrade is a counted fact. This is the positive corollary of “no silent acceptance”: the operator is told, in the fixed monitor record, when the DNS path is less healthy than it was.

8.5 Exit codes and degradation surfaces

Process exit and per-request HTTP degradation are the two fixed failure surfaces; both are typed and unconditional. Exit 0 has two reachable producers: a drained serving shutdown after gate-opened tunnels complete (ShutdownExit::Drained ⇒ 0, src/runtime/reactor.rs:187, applied through src/runtime/owner.rs:406-409) and a startup Terminated decision (SIGTERM within the startup window), which emits the shutdown record and exits 0 (src/main.rs:99-101). Exit 70 (EX_SOFTWARE) is forced shutdown with undrained tunnels at the deadline (ShutdownExit::Forced ⇒ 70, src/runtime/reactor.rs:188) and startup serving failures — attach failure, or serve error — each exiting EX_SOFTWARE (src/main.rs:88-94). Every owner.run_startup error maps to EX_CONFIG = 78: StartupError::{Dns, Cache, Listener} — DNS transport/storage, readiness evaluation, and listener bind — plus boot storage, preallocation, and stdout-sink setup failures (src/boot/mod.rs:9; src/main.rs:61-79, :103-106; src/runtime/storage.rs:298-309); the startup DNS verdict exits EX_TEMPFAIL = 75 (src/main.rs:97). Exit 74 (EX_IOERR) is an unrecoverable stdout sink failure: the per-turn drain passes the queue, and once the sticky failed latch is set the owner exits in place at the turn unless shutdown has begun (src/runtime/owner.rs:28, :375-377), which is the operator’s log-loss signal for the terminal-sink latch of §8.2 — the one failure surface where log loss is counted and observability ends, so the process exits rather than continue externally unreportable (src/log/sink.rs:32-47, :100-179).

9. Security and trust

9.1 Threat model in one paragraph

The spec’s threat model (docs/alumina-proxy.md §Threat model) is a compromised trusted application — the client is trusted at rest and the operator holds full privilege, but compromise is assumed inevitable, so the proxy’s task is to identify the compromise and protect against further exploitation purely through egress. The design consequence is a Golden Path: a correctly configured, healthy workload produces zero deviations, so any observed deviation is by construction a signal.

9.3 TLS and the ClientHello profile

The ClientHello surface is deliberately narrow. Validation enforces a TLS 1.3 profile with no ECH: the record-layer legacy version must be the TLS 1.2 compatibility value (scan_available, src/inspection/client_hello.rs:503-507, :599) and the offered supported_versions must contain non-GREASE TLS 1.3 only (validate_versions, src/inspection/client_hello.rs:701-716); an encrypted_client_hello extension is marked present at parse (:666) and rejected by validate (:876-877). Exactly one SNI host_name is required and it must normalize-equal the approved hostname, with non-host_name server_name entries rejected (parse_server_names, L8, src/inspection/client_hello.rs:764-806; the count and equality checks in validate at :879-886), and a minimum initial TLS record payload (L9) rejects degenerate framing (src/inspection/client_hello.rs:519-521). The inspector holds the flattened message across feeds, copying each record payload exactly once regardless of fragmentation (src/inspection/client_hello.rs:480-547). The JA4 fingerprint is computed by the private client_hello/ja4.rs child (ja4_fingerprint, src/inspection/client_hello/ja4.rs:54, re-exported unchanged at src/inspection/client_hello.rs:7) and retained per slot (the Option<ClientHello> inside ChInspector) as the baseline for the ja4 gate — a per-class gate whose Block{All} scope is legal and reachable, in contrast to early_data’s connection-only block scope (see §6.2; the ja4 grammar keeps the full scope set in src/enforcement/policy.rs:131-135).

Query provenance is decision-scoped: the private ResolvedRequest carrier (src/runtime/tunnel.rs:799-803) borrows the &ConnectRequest and owns a copied WorkerView — temporary config/cache references and a copied clock (src/runtime/tunnel.rs:743-747) — plus the raw allowlist index minted by WorkerView::resolve (src/runtime/tunnel.rs:773-782). The context’s last read is peer_state (src/runtime/reactor.rs:2508), before the mutable freshness consumer and the slot writes and dial that follow (src/runtime/reactor.rs:2509-2521), so it is not held to the end of the dial. Nothing is stored back — no context, cache reference, or lease in the slot and no selected-peer lease across retries; a retry re-resolves from the same cache. Every granted peer folds its per-grant freshness observation into the monitor — Stale sets, Fresh clears (src/runtime/reactor.rs:2503-2509) — and only incident admission counting is guarded by connect_family.is_none() (src/runtime/reactor.rs:2547-2558); a stale observation never denies a retry, which may select another servable candidate (src/runtime/tunnel.rs:873-902). The mutable peer-freshness consumer (src/runtime/reactor.rs:2537) performs no cache lookup of its own.

9.4 Trust boundary summary — pin-or-nothing, no silent downgrade

Three trust statements summarize the boundary:

  • DoT is pin-or-nothing. With a pin, the peer is authenticated by SPKI + SNI/SAN matching and TLS 1.2/1.3 handshake-signature verification — possession of the pinned certificate's private key (src/dns/transport.rs:795-825, :828-844). Without a pinned SPKI, chain validation fails deterministically (empty root store) and the resolver is unusable with a startup warning — there is no CA-validated mode in the current build (src/dns/transport.rs:818-825).
  • Failover never downgrades identity. Relocations cannot silently swap a DoT entry to plain DNS; a downgrade is counted as a dp fact (src/dns/transport.rs:3281-3293).
  • Trust is homogeneous or boot fails. A mixed-trust resolver set is rejected at configuration time (src/config/mod.rs:679-683).
